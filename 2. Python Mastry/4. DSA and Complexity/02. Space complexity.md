# 02. Space complexity

**Source:** [Python for Data Engineering Notes, page 42](<../Source/1793477658005.pdf#page=42>).

Space complexity asks how much **extra** memory an algorithm needs as the input grows. A running total keeps a few values: O(1) extra space. A copied list keeps one value per input item: O(n).

## List versus generator

Both calculations double and sum the same numbers. The list builds all doubled values first. The generator creates each doubled value only when the sum asks for it.

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=02&snippet=1>)

~~~python
numbers = range(1, 6)
as_list = [number * 2 for number in numbers]
as_generator = (number * 2 for number in numbers)
print(as_list)
print(sum(as_list), sum(as_generator))
~~~

Expected output:

~~~text
[2, 4, 6, 8, 10]
30 30
~~~

Both take O(n) time. The temporary list uses O(n) extra space; the generator's values use O(1) extra space. The generator can be consumed once. If you must revisit its values, create it again or store them.

## Call stacks count as space

Every unfinished recursive call waits for the next. That uses O(depth) stack space. A loop can carry the same running total in O(1) extra space.

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=02&snippet=2>)

~~~python
def recursive_total(values, position=0):
    if position == len(values):
        return 0
    return values[position] + recursive_total(values, position + 1)

def loop_total(values):
    total = 0
    for value in values:
        total += value
    return total

orders = [1198, 796, 1499]
print(recursive_total(orders), loop_total(orders))
~~~

Expected output:

~~~text
3493 3493
~~~

For thousands of items, Python recursion can hit its recursion limit. Prefer a loop for a long flat sequence. Recursion is more natural when the data itself is nested, such as a tree.

## Measure the extra memory

`tracemalloc` can compare peak allocations during two calculations. The exact KB values change by Python version and machine, so this snippet reports the stable relationship. The PDF measured roughly 39,496 KB for a one-million-number list and approximately 0 KB extra for the generator in its environment.

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=02&snippet=3>)

~~~python
import tracemalloc


def peak_kb(action):
    tracemalloc.start()
    action()
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return peak // 1024

n = 100_000
list_peak = peak_kb(lambda: sum([x * 2 for x in range(n)]))
generator_peak = peak_kb(lambda: sum(x * 2 for x in range(n)))
print('list uses more peak memory:', list_peak > generator_peak)
~~~

Expected output:

~~~text
list uses more peak memory: True
~~~

Both calculations are O(n) time, but the list allocates O(n) temporary values. The PDF also shows a 500-item recursive sum of 124,750, a 5,000-level recursive call raising `RecursionError`, and a loop that handles 10 million values. Python does not optimize tail calls away: deep recursion still uses stack frames. Use a loop or an explicit stack when depth can grow with a huge input.

| Extra structure | Extra space |
|---|---|
| A few counters | O(1) |
| A list, set, or dict with one entry per row | O(n) |
| A slice of k items | O(k) |
| d nested recursive calls | O(d) |
| A square table with n rows and n columns | O(n²) |

**Interview trade-off:** If asked for O(1) extra space after using a set, consider sorting the input in place and comparing neighbours or using two pointers. Say the price aloud: sorting costs O(n log n) time and may change the input. Whether a built-in sort is strictly O(1) auxiliary space depends on the sort implementation, so do not claim that for Python's `list.sort()`.

def order_amounts():
    for amount in (1198, 796, 1499):
