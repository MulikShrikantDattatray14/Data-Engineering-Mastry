# 01. Big-O in plain words

**Source:** [Python for Data Engineering Notes, page 41](<../Source/1793477658005.pdf#page=41>).

Big-O describes how work grows as the input grows. It does not predict seconds on your laptop. Imagine looking for an order ID in a growing list: a full scan may need to inspect every order, while a set can usually answer membership without scanning.

## Compare growth without a stopwatch

| Shape | Example | If the input doubles |
|---|---|---|
| O(1) | Read one known list position | About the same work |
| O(log n) | Halve a sorted search range | Roughly one extra check |
| O(n) | Read every order once | Roughly twice the work |
| O(n log n) | Sort the orders | A little more than twice |
| O(n²) | Compare every order with every other | Roughly four times |
| O(2ⁿ) | Try every subset | Quickly becomes impractical |

Use a small count to see the difference:

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=01&snippet=1>)

~~~python
import math

for n in (10, 100, 1_000):
    print(n, math.ceil(math.log2(n)), n, n * n)
~~~

Expected output (columns are input size, approximate binary-search checks, scan checks, pair checks):

~~~text
10 4 10 100
100 7 100 10000
1000 10 1000 1000000
~~~

## Count the operations in two duplicate checks

A nested loop checks pairs. A set remembers earlier IDs. Both answer the same question, but their work grows differently.

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=01&snippet=2>)

~~~python
def pair_checks(ids):
    checks = 0
    for i in range(len(ids)):
        for j in range(i + 1, len(ids)):
            checks += 1
            if ids[i] == ids[j]:
                return True, checks
    return False, checks

def set_checks(ids):
    seen = set()
    checks = 0
    for order_id in ids:
        checks += 1
        if order_id in seen:
            return True, checks
        seen.add(order_id)
    return False, checks

for n in (4, 8):
    ids = list(range(n))
    print(n, pair_checks(ids), set_checks(ids))
~~~

Expected output:

~~~text
4 (False, 6) (False, 4)
8 (False, 28) (False, 8)
~~~

The set needs O(n) extra memory. The pair check uses O(1) extra memory. The timing of a particular run may vary; these counts show the growth reliably.

## Rules for reading code

- Sequential passes add: O(n) + O(n) remains O(n).
- Nested passes multiply: n × n becomes O(n²).
- Constants disappear from the growth label: 3n + 5 becomes O(n).
- Keep the dominant term: n² + n becomes O(n²).
- With two independent inputs of sizes n and m, a nested comparison is O(nm).

A million records can fit an O(n) scan or O(n log n) sort far more comfortably than an O(n²) pair comparison. Always state both your input size and your assumptions.

## How large an input can each approach handle?

The PDF gives this rough interview guide. These are starting points, not machine guarantees; Python work per step, memory, and the time limit matter.

| Approximate input size | Often feasible growth | Typical approach |
|---:|---|---|
| Around 20 | O(2^n) or O(n!) | Enumerate small subsets or orders |
| 1,000–5,000 | O(n²) | Compare pairs when needed |
| 100,000–1,000,000 | O(n log n) or O(n) | Sort, hash, or scan once |
| Tens of millions | O(n) or O(log n) per query | Stream, binary-search sorted data, or distribute the work |

The PDF's sample timing for duplicate checks illustrates the growth: at n=1,000/2,000/4,000, its nested version took about 21.1/91.5/348.7 ms, while a set took about 0.09/0.35/0.44 ms. Those milliseconds vary by computer; the shape of growth is the lesson.
