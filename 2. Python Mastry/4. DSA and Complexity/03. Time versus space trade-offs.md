# 03. Time versus space trade-offs

**Source:** [Python for Data Engineering Notes, page 43](<../Source/1793477658005.pdf#page=43>).

Often you can make a query faster by keeping extra information. If the store repeatedly asks whether an order ID exists, a set costs memory but gives fast average lookups. If IDs are already sorted, binary search uses the existing list with little extra memory.

## Three ways to look up an ID

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=03&snippet=1>)

~~~python
from bisect import bisect_left

order_ids = [101, 104, 108, 114, 120]
known = set(order_ids)

def contains_sorted(values, target):
    position = bisect_left(values, target)
    return position < len(values) and values[position] == target

for target in (108, 109):
    print(target, target in order_ids, target in known, contains_sorted(order_ids, target))
~~~

Expected output:

~~~text
108 True True True
109 False False False
~~~

The list scan takes O(n) per lookup and no new index. The set takes O(n) memory to build and then average O(1) per lookup. Binary search takes O(log n) per lookup when the list is already sorted. The bounds check matters when the target is greater than every ID. The PDF compared 1,000 searches over one million sorted IDs: about 8,504 ms for list scanning, 0.71 ms for set lookup, and 2.11 ms for `bisect`, with the set taking substantially more memory. These are source-machine timings, not expected output on your computer.

## Prepare range sums once

Suppose reports repeatedly ask for sales over different day ranges. A prefix array stores the running totals. Subtract two entries to answer any inclusive range in O(1).

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=03&snippet=2>)

~~~python
from itertools import accumulate

daily_sales = [0, 1999, 0, 846, 0]
prefix = [0, *accumulate(daily_sales)]

def sales_between(first_day, last_day):
    return prefix[last_day + 1] - prefix[first_day]

print(prefix)
print(sales_between(1, 3), sum(daily_sales[1:4]))
~~~

Expected output:

~~~text
[0, 0, 1999, 1999, 2845, 2845]
2845 2845
~~~

Building the prefix takes O(n) time and memory. That is worthwhile for many repeated questions; for one range, summing directly is simpler. The PDF's ten-day sample `[0, 1999, 0, 0, 846, 0, 0, 2397, 0, 1598]` produces range sums 2,845 and 6,840; the prefix and direct sum agree.

| Problem | Spend memory for speed | Spend time to save memory | Choose the second option when... |
|---|---|---|---|
| Is an ID present? | Build a set: O(n) space, then O(1) average lookup | Search an already sorted list with `bisect`: O(log n) lookup, no extra index | The list is sorted or RAM is tight. |
| Find duplicates | Keep a set: O(n) time and space | Sort in place, then compare neighbours: O(n log n) time | You may modify the input and can afford the sort. |
| Top k of n values | Sort all n: O(n log n) time and O(n) copied output | Keep a size-k heap: O(n log k) time, O(k) space | n is huge or streaming and k is small. |
| Answer many range sums | Build prefix totals: O(n) space, then O(1) per query | Sum each requested range: O(length of range) per query | There are only a few queries. |
| Repeat the same lookup | Cache results, using memory per distinct input | Recompute instead of storing results | Inputs rarely repeat or cache invalidation is hard. |
| Join two files | Hash the smaller side: O(n + m) average time, smaller side in RAM | Sort-merge: sorting cost, then stream both sorted inputs | Neither side fits in memory. |
| Process a file | Load all rows: O(n) RAM | Stream rows or chunks: bounded RAM | The input may outgrow memory, as in many DE tasks. |

For large files, mention chunking, partitioning, or an external merge as well as algorithmic cost. A hash join needs the smaller side in memory; a sort-merge join can stream sorted inputs.

## More from W3Schools

[W3Schools Binary Search](https://www.w3schools.com/python/python_dsa_binarysearch.asp) shows how a sorted collection lets you discard half the candidates at each step. Try this small version:

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=03&snippet=3>)

~~~python
ids = [101, 104, 108, 114]
left, right = 0, len(ids) - 1
target = 114
while left <= right:
    middle = (left + right) // 2
    if ids[middle] == target:
        print("position", middle)
        break
    if ids[middle] < target:
        left = middle + 1
    else:
        right = middle - 1
~~~

Expected output:

~~~text
position 3
~~~
