# 04. What Python operations cost

**Source:** [Python for Data Engineering Notes, page 44](<../Source/1793477658005.pdf#page=44>).

A line that looks small can hide a full scan. For example, checking whether an item is in a list searches the list; doing that inside another loop may turn a simple filter into O(nm).

## Know the common costs

| Structure | Cheap operations | Expensive operations | Watch out |
|---|---|---|---|
| `list` | Index, `append`, end `pop`, `len`: O(1) amortized where relevant | Membership, front insert/pop, `remove`, `index`: O(n); slice of k items: O(k) | A Python list is an array. |
| `dict` | Key lookup, `get`, membership, assign, delete: O(1) average | Iterate all keys or copy: O(n) | Heavy hash collisions can worsen lookup. |
| `set` | Add, remove, membership: O(1) average | Union/intersection scale with input sizes | Elements must be hashable. |
| `collections.deque` | Add/remove at either end: O(1) | Middle indexing/search: O(n) | Use it for queues and windows. |
| `heapq` | Push/pop minimum: O(log n); peek at index 0: O(1) | `heapify`: O(n); arbitrary search: O(n) | It is a min-heap; negate numeric priorities for a max-heap. |
| `str` | `len`, indexing: O(1) | `replace`, `split`, substring search: O(n) or more by pattern; repeated `+=` copies | Strings are immutable. |
| `sorted` / `list.sort` | — | O(n log n) comparison sort | Sorting inside a loop may multiply that cost. |
| `bisect` | `bisect_left`: O(log n) | `insort`: O(n) due to list shifting | Input must stay sorted. |

These are typical complexity labels, not promises for every possible hash collision or data arrangement. A list slice makes a new list proportional to the slice length.

## A queue should remove from the left efficiently

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=04&snippet=1>)

~~~python
from collections import deque

orders = deque([101, 104, 108])
while orders:
    print("process", orders.popleft())
~~~

Expected output:

~~~text
process 101
process 104
process 108
~~~

A list's pop(0) would give the same order, but every removal shifts the remaining values. The deque keeps this queue operation O(1). The PDF measured about 728.8 ms for 100,000 list front-removals versus 10.5 ms with `deque.popleft()`; exact timings depend on the machine.

## Move repeated membership checks into a set

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=4&lesson=04&snippet=2>)

~~~python
orders = [101, 102, 103, 104, 105]
vip_ids = [102, 105]
vip_lookup = set(vip_ids)
print([order_id for order_id in orders if order_id in vip_lookup])
~~~

Expected output:

~~~text
[102, 105]
~~~

Building the set takes O(m) time and space for m VIP IDs. Filtering n orders then takes average O(n), rather than O(nm) with list membership. On the PDF's 50,000-order example, the list version took about 3,573 ms and the set version about 2.0 ms; both returned the same matching IDs.

Strings are immutable, so joining pieces after collection is preferable to repeatedly concatenating very long strings. A heap gives its smallest item at index zero, but searching for an arbitrary item in a heap still takes O(n). A bisect search is fast only because its list is sorted; inserting into that list still shifts values.
