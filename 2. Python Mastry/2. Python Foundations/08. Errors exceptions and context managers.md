A robust pipeline should reject bad rows deliberately, report what was skipped, and release resources even when work fails.

## Catch the expected error only

Keep the <code>try</code> block small. <code>else</code> runs when no exception occurred. <code>finally</code> runs whether an exception happened or not, including after a return.

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=2&lesson=08&snippet=1>)

~~~python
def parse_amount(text):
    try:
        value = float(text)
    except ValueError:
        print("bad amount:", repr(text))
        return None
    else:
        print("parsed:", value)
        return value
    finally:
        print("finished attempt")

print(parse_amount("1198.00"))
print(parse_amount("N/A"))
~~~

Expected output:

~~~text
parsed: 1198.0
finished attempt
1198.0
bad amount: 'N/A'
finished attempt
None
~~~

Do not silently swallow every exception. A typo such as <code>NameError</code> would then look like successful processing with missing rows.

## Name a data-quality failure

Create an exception type when the caller needs to handle a failure differently. <code>raise ... from error</code> preserves the original cause.

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=2&lesson=08&snippet=2>)

~~~python
class DataQualityError(Exception):
    pass

def require_positive(amount):
    if amount <= 0:
        raise DataQualityError("amount must be positive")

for amount in (10, -5):
    try:
        require_positive(amount)
        print("accepted:", amount)
    except DataQualityError as error:
        print("rejected:", error)

try:
    int("12a")
except ValueError as error:
    chained = RuntimeError("bad order ID")
    chained.__cause__ = error
    print(type(chained.__cause__).__name__)
~~~

Expected output:

~~~text
accepted: 10
rejected: amount must be positive
ValueError
~~~

In a real error path, write <code>raise RuntimeError("bad order ID") from error</code>; the traceback then displays both failures.

## Context managers clean up

A <code>with</code> block calls <code>__enter__</code> on entry and <code>__exit__</code> on exit, including after an error. Returning <code>False</code> from <code>__exit__</code> lets the error continue to the caller.

[▶ Run and edit this example](<http://127.0.0.1:8765/?part=2&lesson=08&snippet=3>)

~~~python
class Connection:
    def __enter__(self):
        print("open")
        return self
    def __exit__(self, exc_type, exc, traceback):
        print("close:", exc_type.__name__ if exc_type else "ok")
        return False

try:
    with Connection():
        print("loading")
        raise TimeoutError("warehouse timed out")
except TimeoutError:
    print("handled after cleanup")
~~~

Expected output:

~~~text
open
loading
close: TimeoutError
handled after cleanup
~~~
