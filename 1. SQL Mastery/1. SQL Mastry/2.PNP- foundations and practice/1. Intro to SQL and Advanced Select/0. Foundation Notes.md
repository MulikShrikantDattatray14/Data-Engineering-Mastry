## 1. Start with the same four rows

| OrderID | CustomerID | OrderDate | Total_Order_Amount |
|---:|---:|---|---:|
| 101 | 1 | 2025-01-04 | 120 |
| 102 | 1 | 2025-01-05 | NULL |
| 103 | 2 | 2025-02-01 | 80 |
| 104 | NULL | 2025-02-05 | 40 |

One row is one order header. CustomerID can be absent; an absent amount does not mean the order was worth zero.

## 2. SELECT and aliases

~~~sql
SELECT
    OrderID,
    Total_Order_Amount AS order_amount
FROM Orders
ORDER BY OrderID;
~~~

| OrderID | order_amount |
|---:|---:|
| 101 | 120 |
| 102 | NULL |
| 103 | 80 |
| 104 | 40 |

SELECT chooses output columns. AS changes the output heading; it does not change the source column. Use table aliases when two joined tables share a name such as CustomerID.

## 3. WHERE, AND, OR, and parentheses

~~~sql
SELECT OrderID, Total_Order_Amount
FROM Orders
WHERE Total_Order_Amount >= 80
ORDER BY OrderID;
~~~

Only orders 101 and 103 qualify. Order 104 is below 80; Order 102 has no amount, so the comparison is unknown and does not pass WHERE.

For two required conditions, use AND:

~~~sql
WHERE CustomerID = 1
  AND Total_Order_Amount >= 80
~~~

Only order 101 passes both. For alternatives, use OR. Put parentheses around mixed AND/OR rules so the intended grouping is visible:

~~~sql
WHERE Total_Order_Amount >= 80
  AND (CustomerID = 1 OR CustomerID = 2)
~~~

This also keeps orders 101 and 103. Without parentheses, AND is evaluated before OR, which can admit rows that do not meet the amount condition.

## 4. IN, ranges, and text patterns

IN is a compact way to list allowed values:

~~~sql
WHERE CustomerID IN (1, 2)
~~~

It keeps orders 101, 102, and 103. It does not include order 104 because NULL is not equal to either listed value.

For a complete January window, use an inclusive start and exclusive next-month boundary:

~~~sql
WHERE OrderDate >= '2025-01-01'
  AND OrderDate <  '2025-02-01'
~~~

This keeps 101 and 102. It also works when OrderDate includes a time component, because the upper boundary begins the next month.

LIKE uses percent for zero or more characters and underscore for exactly one character. With example values Tea, Team, and Top:

| Pattern | Matches | Why |
|---|---|---|
| 'Te%' | Tea, Team | Both begin with Te |
| 'Te_' | Tea | One character follows Te |
| '%op' | Top | Ends with op |

For a case-independent match across dialects, compare normalized text, for example LOWER(city) LIKE 'del%'. If surrounding spaces matter, use TRIM first. SQLite LIKE and PostgreSQL LIKE differ in default case behavior, so test the dialect you are using.

## 5. NULL needs its own checks

~~~sql
SELECT OrderID
FROM Orders
WHERE Total_Order_Amount IS NULL;
~~~

This returns OrderID 102. Use IS NOT NULL for known amounts. Writing Total_Order_Amount = NULL does not find missing values.

COALESCE can choose a display fallback, but it does not prove that the original value was zero:

~~~sql
SELECT OrderID,
       COALESCE(Total_Order_Amount, 0) AS shown_amount
FROM Orders
ORDER BY OrderID;
~~~

Order 102 displays 0 in this result, while the stored value remains NULL. Use a fallback only when the question's meaning supports it. Similarly, NULLIF(x, '') turns an empty string into NULL; it does not remove surrounding spaces unless TRIM is applied.

## 6. DISTINCT, CASE, and ORDER BY

DISTINCT removes repeated **selected rows**:

~~~sql
SELECT DISTINCT CustomerID
FROM Orders
ORDER BY CustomerID;
~~~

The sample has three distinct CustomerID values: 1, 2, and NULL. If another column is added to SELECT, distinctness is checked on the pair of columns, so the count can change.

CASE assigns a label to each row. Check missing values first when a missing amount needs its own label:

~~~sql
SELECT
    OrderID,
    CASE
        WHEN Total_Order_Amount IS NULL THEN 'missing'
        WHEN Total_Order_Amount >= 100 THEN 'large'
        ELSE 'smaller'
    END AS amount_label
FROM Orders
ORDER BY OrderID;
~~~

| OrderID | amount_label |
|---:|---|
| 101 | large |
| 102 | missing |
| 103 | smaller |
| 104 | smaller |

ORDER BY controls final output order. Add a stable tie-breaker when the first sort key can repeat. The ORDER BY inside a window function has a different job: it defines order for that window calculation.

## 7. LIMIT and dialect reminders

~~~sql
SELECT OrderID, Total_Order_Amount
FROM Orders
WHERE Total_Order_Amount IS NOT NULL
ORDER BY Total_Order_Amount DESC, OrderID ASC
LIMIT 2;
~~~

The filtered sample sorts as 101 (120), 103 (80), 104 (40), so the query returns 101 and 103. LIMIT keeps rows after sorting. If two amounts tie, OrderID chooses which one comes first.

The PrepNPlaced interview book uses PostgreSQL, while the advanced volume uses MySQL 8. Both use LIMIT here; SQLite also supports it. SQL Server uses TOP or OFFSET/FETCH instead. Date functions, string aggregation, and some window syntax differ more substantially; preserve the intended logic when translating a query.

## 8. Quick check before submitting

- Are you returning one row for the intended thing: an order, customer, product, or group?
- Does WHERE express every boundary and include or exclude NULL as required?
- Could AND/OR precedence change the result?
- Does DISTINCT apply to the columns you actually selected?
- Is ORDER BY present when output order or a top-N result is required?
- Are tied rows handled deterministically when only a fixed number may be returned?
- Does the query use functions supported by the SQL dialect you are running?
