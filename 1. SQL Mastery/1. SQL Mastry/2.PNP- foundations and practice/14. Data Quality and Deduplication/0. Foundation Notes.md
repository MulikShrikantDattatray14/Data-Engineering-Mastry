# Data Quality and Deduplication — Quick Revision Notes

**Main idea:** define what one valid row represents, then check keys, required values, references, dates, and totals. A row can fail more than one check. Inspect candidate changes before removing anything.

Sources: [Advanced SQL questions](<../Source Materials/Advanced_SQL_100_Query_Questions_Vol1 (2).pdf>) and [PrepNPlaced interview questions](<../Source Materials/Updated_100_SQL_Interview_Questions.pdf>). The tiny sample below is invented for learning; it is not a practice-question answer.

## 1. State the grain and the business key

Imagine an incoming event feed. One event is identified by the pair (user_id, event_time). event_id is just the feed row ID.

| event_id | user_id | event_time | received_at |
|---:|---:|---|---|
| 1 | 1 | 2026-01-03 09:00 | 2026-01-03 10:00 |
| 2 | 1 | 2026-01-03 09:00 | 2026-01-03 10:01 |
| 3 | 2 | 2026-01-04 11:00 | 2026-01-04 12:00 |
| 4 | 3 | NULL | 2026-01-04 13:00 |

Rows 1 and 2 have different event_id values but the same business key. They may represent one real event ingested twice. Row 4 lacks a required event_time. Define the business key before calling anything a duplicate; two identical amounts or names alone may be legitimate.

## 2. Find duplicate groups before choosing a survivor

    SELECT user_id, event_time, COUNT(*) AS copies
    FROM StagingEvents
    GROUP BY user_id, event_time
    HAVING COUNT(*) > 1;

| user_id | event_time | copies |
|---:|---|---:|
| 1 | 2026-01-03 09:00 | 2 |

GROUP BY shows the repeated key, not which physical row to keep. If the rule is “keep the earliest received row,” add a deterministic tiebreaker:

    ROW_NUMBER() OVER (
        PARTITION BY user_id, event_time
        ORDER BY received_at, event_id
    ) AS rn

| event_id | user_id | event_time | rn | decision |
|---:|---:|---|---:|---|
| 1 | 1 | 2026-01-03 09:00 | 1 | candidate survivor |
| 2 | 1 | 2026-01-03 09:00 | 2 | candidate duplicate |
| 3 | 2 | 2026-01-04 11:00 | 1 | candidate survivor |
| 4 | 3 | NULL | 1 | still needs validity checks |

ROW_NUMBER only applies the rule we supplied. It does not make row 4 valid. A unique event_id is not the same as a unique business event.

## 3. Run independent validity and reference checks

Suppose KnownUsers contains IDs 1 and 2. Row 4 has two separate problems: event_time is missing, and user_id 3 has no matching parent user.

| check | rows flagged | why |
|---|---|---|
| Missing required event_time | 4 | Event time is NULL |
| Duplicate business key | 2 | Same key as row 1; later received_at |
| Unknown user_id | 4 | No KnownUsers row for 3 |

Do not force every row into exactly one error category unless the report specifically requires it. A NULL foreign key may mean “unknown,” while a non-NULL foreign key with no parent is an orphan. Those are different cases.

Dates need rules too: event_time after received_at, an end before a start, or a timestamp outside the accepted range may be invalid. Express each rule separately so the failure can be explained.

## 4. Reconcile totals at the same grain

A header can say one total while its detail rows sum to another. First aggregate details to **one row per header key**, then compare one header row with one detail summary. Record these cases separately:

| case | meaning |
|---|---|
| Header but no detail | Possibly incomplete transaction |
| Detail but no header | Orphan detail |
| Both present, amounts differ | Reconciliation mismatch |
| Both present, amounts agree | Matched |

Joining raw header, detail, and payment attempts in one step can multiply detail rows and manufacture a false mismatch. Check row counts at each join.

## 5. Preview changes and make loads repeatable

Before a delete or merge, show the exact candidate rows with SELECT and count them. Keep the chosen survivor rule visible. For real changes, use a transaction and verify the post-change count before committing.

Incremental loads often use a watermark such as the latest processed timestamp. A late-arriving row can have an old event_time but a new received_at, so choose the watermark column carefully. A lookback window plus the business-key deduplication rule helps a rerun produce the same clean result rather than duplicate events.

## Quick revision

1. State the row grain and business key.
2. Profile missing values and duplicate keys separately.
3. Choose a survivor with a complete, deterministic ORDER BY.
4. Check orphan references and invalid dates independently.
5. Reconcile at matching grains; preview every destructive change.
