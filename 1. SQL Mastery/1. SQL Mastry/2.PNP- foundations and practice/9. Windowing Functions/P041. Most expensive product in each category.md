# PNP Q041. Most expensive product in each category

![NOT SOLVED YET](<../../_badges/not-solved-yet.svg>) ![MEDIUM](<../../_badges/medium.svg>)

## Question and image

**Source:** [100 SQL Interview Questions](<../Source Materials/Updated_100_SQL_Interview_Questions.pdf>), question 41, pp. 70–72. **Difficulty:** Medium.

**Business scenario.** The merchandising team is planning a premium banner on each category page. The banner shows the category's most expensive product by current Sale_Price . If two products tie for the top price, both go on the banner, because picking one at random would favour a brand without a reason.

**Task.** For each category, return the product or products with the highest Sale_Price . Keep every product that ties for first. Products whose CategoryID has no Category row are grouped under Unmapped . Products with no price cannot be the most expensive. Sort by category name, then ProductID .

**Expected output (as supplied):**

```text
CategoryName : the category's name, or Unmapped
ProductID , Product
Sale_Price
```

The source is a text-based PDF; no separate question image was supplied.

## Important learnings from P041

### 1. LEFT JOIN preserves products with missing category matches

Start from `Products` because the required output is about products. A `LEFT JOIN Category` preserves every product, including products whose `CategoryID` has no matching row in `Category`.

- `P.CategoryID` is the category ID recorded on the product.
- `C.CategoryID` is the category ID that actually matched in the Category table.
- When there is no match, the Category-side columns, including `C.CategoryID` and `C.CategoryName`, are `NULL`.
- Display the missing category label as `Unmapped`, for example with `COALESCE(C.CategoryName, 'Unmapped')`.

### 2. Exclude products with no price before ranking

The question explicitly says products with `Sale_Price IS NULL` cannot be the most expensive. Filter them before the window calculation:

```sql
WHERE P.Sale_Price IS NOT NULL
```

This removes unpriced products from the ranking while retaining priced products whose category lookup is unmatched.

### 3. Use RANK() to preserve ties

Use a window function because each product row must remain visible while prices are compared within a category:

```sql
RANK() OVER (
    PARTITION BY C.CategoryID
    ORDER BY P.Sale_Price DESC
) AS price_rank
```

- `PARTITION BY` creates independent ranking groups.
- `ORDER BY Sale_Price DESC` puts the highest price first.
- `RANK()` assigns the same rank to equal prices, so all products tied for first receive rank 1.
- Filter to `price_rank = 1` in an outer query or CTE.

### 4. Why PARTITION BY P.CategoryID, C.CategoryName is wrong for this requirement

Consider these rows after the LEFT JOIN:

| Product | P.CategoryID | C.CategoryID | C.CategoryName | Sale_Price |
|---|---:|---:|---|---:|
| Tea | 1 | 1 | Drinks | 10 |
| Coffee | 1 | 1 | Drinks | 10 |
| Mystery A | 99 | NULL | NULL | 30 |
| Mystery B | 100 | NULL | NULL | 20 |

With:

```sql
PARTITION BY P.CategoryID, C.CategoryName
```

the partitions are:

| Partition key | Products |
|---|---|
| (1, Drinks) | Tea, Coffee |
| (99, NULL) | Mystery A |
| (100, NULL) | Mystery B |

The two unmatched products are separated because their Products-side category IDs are 99 and 100. Both would receive rank 1, so both would survive the final filter. That does not implement the requirement that all unmatched category IDs are grouped under one `Unmapped` category.

### 5. Why PARTITION BY C.CategoryID is correct

Use:

```sql
PARTITION BY C.CategoryID
```

For matched products, `C.CategoryID` contains the real category ID. For every unmatched product, it is `NULL`. Therefore, all unmatched products share one NULL partition and compete against each other for the highest price.

| Product | Display category | C.CategoryID | Sale_Price | RANK |
|---|---|---:|---:|---:|
| Tea | Drinks | 1 | 10 | 1 |
| Coffee | Drinks | 1 | 10 | 1 |
| Mystery A | Unmapped | NULL | 30 | 1 |
| Mystery B | Unmapped | NULL | 20 | 2 |

After filtering `price_rank = 1`, Mystery A remains as the most expensive product in the single Unmapped group. Tea and Coffee both remain because they tie.

**Reusable rule:** When multiple unmatched foreign-key values must be collapsed into one fallback group, partition by the matched-side key (which is NULL for every unmatched row), not by the original foreign-key values.

### 6. SQL logical processing order and window filtering

The typical logical processing order for a SELECT query is:

1. `WITH` — defines CTEs used by the query.
2. `FROM` — identifies source tables.
3. `ON` — evaluates join matching conditions as part of join processing.
4. `JOIN` — combines rows according to the join type.
5. `WHERE` — filters rows before grouping and window calculations.
6. `GROUP BY` — forms groups.
7. `HAVING` — filters groups.
8. `SELECT` — calculates output expressions, aggregates and window-function results.
9. `DISTINCT` — removes duplicate result rows.
10. `ORDER BY` — sorts the result.
11. `LIMIT / OFFSET / FETCH` — restricts or skips final rows (syntax varies by SQL dialect).

This is logical processing order, not the order in which clauses are written. `ON` is part of join processing, not a separate later operation after all joins.

A window-function alias such as `price_rank` is not available to the `WHERE` clause at the same query level because WHERE is processed before the SELECT/window calculation. Calculate it in a CTE or subquery, then filter it in the outer query:

```sql
WITH ranked_products AS (
    SELECT
        P.ProductID,
        P.Product,
        COALESCE(C.CategoryName, 'Unmapped') AS CategoryName,
        P.Sale_Price,
        RANK() OVER (
            PARTITION BY C.CategoryID
            ORDER BY P.Sale_Price DESC
        ) AS price_rank
    FROM Products AS P
    LEFT JOIN Category AS C
        ON P.CategoryID = C.CategoryID
    WHERE P.Sale_Price IS NOT NULL
)
SELECT
    CategoryName,
    ProductID,
    Product,
    Sale_Price
FROM ranked_products
WHERE price_rank = 1
ORDER BY CategoryName, ProductID;
```

### 7. SELECT aliases: WHERE versus ORDER BY

An alias is a name assigned to a selected expression, for example:

```sql
SELECT Sale_Price * 2 AS Double_Price
FROM Products;
```

At the same query level:

- `WHERE Double_Price > 20` is not valid under the standard logical processing rule because WHERE runs before SELECT creates the alias. Repeat the expression in WHERE, or calculate it in a CTE/subquery and filter outside.
- `ORDER BY Double_Price DESC` is valid because ORDER BY is processed after SELECT has produced the alias.

Example:

```sql
-- Use the expression in WHERE
SELECT Product, Sale_Price * 2 AS Double_Price
FROM Products
WHERE Sale_Price * 2 > 20
ORDER BY Double_Price DESC;
```

**Memory rule:** WHERE filters before SELECT aliases exist; ORDER BY can use SELECT aliases. Some dialects have special rules in other clauses, but this is the standard rule to learn.

### 8. RANK(), DENSE_RANK() and ROW_NUMBER()

All three are window functions that number rows within each partition according to the window's ORDER BY. Their treatment of ties is different.

Example: three products in one category, ordered by price descending:

| Product | Sale_Price |
|---|---:|
| Tea | 100 |
| Coffee | 100 |
| Juice | 90 |

```sql
SELECT
    Product,
    Sale_Price,
    ROW_NUMBER() OVER (ORDER BY Sale_Price DESC) AS row_num,
    RANK() OVER (ORDER BY Sale_Price DESC) AS price_rank,
    DENSE_RANK() OVER (ORDER BY Sale_Price DESC) AS dense_rank
FROM Products;
```

| Product | Sale_Price | ROW_NUMBER() | RANK() | DENSE_RANK() |
|---|---:|---:|---:|---:|
| Tea | 100 | 1 | 1 | 1 |
| Coffee | 100 | 2 | 1 | 1 |
| Juice | 90 | 3 | 3 | 2 |

- **ROW_NUMBER():** gives every row a unique sequential number. Tied rows still receive different numbers; which tied row gets which number is not guaranteed unless the ORDER BY includes a deterministic tie-breaker.
- **RANK():** tied rows receive the same rank, and the next rank skips numbers (1, 1, 3).
- **DENSE_RANK():** tied rows receive the same rank, but the next rank does not skip numbers (1, 1, 2).

**Which one for which task?**
- Keep every product tied for the highest price: use `RANK() = 1` (as in P041). `DENSE_RANK() = 1` would also retain all top-price ties; the difference appears at later ranks.
- Choose exactly one row per category: use `ROW_NUMBER() = 1`, with a deterministic tie-breaker if the choice must be predictable.
- Assign competition-style positions with gaps after ties: use `RANK()`.
- Assign consecutive positions to distinct price levels: use `DENSE_RANK()`.

**Memory shortcut:** ROW_NUMBER = unique row numbers; RANK = ties share rank and leave gaps; DENSE_RANK = ties share rank without gaps.

## My solution — SQLite

**Final learner solution (submitted and preserved verbatim):**

```sql
WITH ranked_products AS (

    SELECT
        P.ProductID,
        P.Product,
        COALESCE(C.CategoryName, 'Unmapped') AS CategoryName,
        P.Sale_Price,

        DENSE_RANK() OVER (
            PARTITION BY C.CategoryID
            ORDER BY P.Sale_Price DESC
        ) AS price_rank

    FROM Products AS P

    LEFT JOIN Category AS C
        ON P.CategoryID = C.CategoryID

    WHERE P.Sale_Price IS NOT NULL

)

SELECT
    CategoryName,
    ProductID,
    Product,
    Sale_Price
FROM ranked_products
WHERE price_rank = 1
ORDER BY
    CategoryName ASC,
    ProductID ASC;
```
