# PNP Q043. Month-to-date order value for the latest three months

![NOT SOLVED YET](<../../_badges/not-solved-yet.svg>) ![MEDIUM](<../../_badges/medium.svg>)

## Question and image

**Source:** [100 SQL Interview Questions](<../Source Materials/Updated_100_SQL_Interview_Questions.pdf>), question 43, pp. 74–76. **Difficulty:** Medium.

**Business scenario.** The finance team tracks each month against its target with a month-to-date (MTD) line: on any day, how much order value has come in since the 1st. They want the last three months of data, one row per day that had orders, with that day's order value and the running MTD figure, so they can compare the shape of each month.

**Task.** Take the latest three calendar months in the data, counting the month of the latest order as the third. For each order date in that window, return the day's total order value and the month-to-date total, which restarts on the first day of each month. Sort by date.

**Expected output (as supplied):**

```text
order_date : the calendar date
daily_order_value : sum of Total_Order_Amount for orders placed that day
month_to_date_value : running total of daily_order_value from the start of that month up to and including this date
```

## My solution — SQLite

The learner chose the **scalar-subquery implementation** as the preferred version. The equivalent **CROSS JOIN implementation** is also retained below for comparison. Both derive the latest three-calendar-month window dynamically, aggregate orders to one row per calendar date, and calculate the month-to-date running total.

### Preferred implementation — scalar subqueries

The two scalar subqueries retrieve the single `start_date` and `end_date` values from `date_range` directly in the `WHERE` clause. No join is needed to expose those boundary values as columns.

```sql
WITH date_range AS (

    SELECT
        DATE(MAX(OrderDate), 'start of month', '-2 months') AS start_date,
        DATE(MAX(OrderDate), 'start of month', '+1 month') AS end_date

    FROM Orders

),

daily_orders AS (

    SELECT
        DATE(O.OrderDate) AS order_date,
        SUM(O.Total_Order_Amount) AS daily_order_value

    FROM Orders AS O

    WHERE DATE(O.OrderDate) >= (
        SELECT start_date
        FROM date_range
    )
      AND DATE(O.OrderDate) < (
        SELECT end_date
        FROM date_range
    )

    GROUP BY DATE(O.OrderDate)

),

monthly_running_total AS (

    SELECT
        order_date,
        daily_order_value,

        SUM(daily_order_value) OVER (
            PARTITION BY STRFTIME('%Y-%m', order_date)
            ORDER BY order_date
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS month_to_date_value

    FROM daily_orders

)

SELECT
    order_date,
    daily_order_value,
    month_to_date_value

FROM monthly_running_total

ORDER BY order_date;
```

### Equivalent alternative — CROSS JOIN

This version exposes the one-row `date_range` result as columns on each order row. Since `date_range` returns one row, the CROSS JOIN preserves the Orders row count before filtering.

```sql
WITH date_range AS (

    SELECT
        DATE(MAX(OrderDate), 'start of month', '-2 months') AS start_date,
        DATE(MAX(OrderDate), 'start of month', '+1 month') AS end_date

    FROM Orders

),

daily_orders AS (

    SELECT
        DATE(O.OrderDate) AS order_date,
        SUM(O.Total_Order_Amount) AS daily_order_value

    FROM Orders AS O

    CROSS JOIN date_range AS D

    WHERE DATE(O.OrderDate) >= D.start_date
      AND DATE(O.OrderDate) < D.end_date

    GROUP BY DATE(O.OrderDate)

),

monthly_running_total AS (

    SELECT
        order_date,
        daily_order_value,

        SUM(daily_order_value) OVER (
            PARTITION BY STRFTIME('%Y-%m', order_date)
            ORDER BY order_date
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS month_to_date_value

    FROM daily_orders

)

SELECT
    order_date,
    daily_order_value,
    month_to_date_value

FROM monthly_running_total

ORDER BY order_date;
```

### Key distinction

| Approach | How the date boundaries are accessed |
|---|---|
| Scalar subqueries | Retrieves `start_date` and `end_date` as individual scalar values inside `WHERE` |
| CROSS JOIN | Makes `start_date` and `end_date` available as columns through alias `D` |

Both approaches are logically equivalent for this one-row `date_range` CTE. Its aggregate query without a `GROUP BY` returns one row, including when `Orders` is empty (in that case the boundary values are NULL).

## Important learnings — Window frames: ROWS, RANGE, and GROUPS

A window frame defines **which rows around the current row are included in a window-function calculation**. The frame is evaluated within the current partition, after the window's ordering has been applied.

### 1. Understanding the frame used in P043

The P043 running-total expression is:

```sql
SUM(daily_order_value) OVER (
    PARTITION BY STRFTIME('%Y-%m', order_date)
    ORDER BY order_date
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

- `PARTITION BY STRFTIME('%Y-%m', order_date)`: creates a separate window for each calendar month, so the running total restarts for every month.
- `ORDER BY order_date`: processes the daily rows chronologically inside each month.
- `ROWS`: defines the frame by row positions in that ordered partition.
- `BETWEEN ... AND ...`: specifies the frame's start and end boundaries.
- `UNBOUNDED PRECEDING`: starts at the first row of the current partition.
- `CURRENT ROW`: ends at the current row.

**In plain English:** for each daily row, sum the daily values from the first available row in that month through the current date.

Because the `daily_orders` CTE has already grouped the source orders to one row per calendar date, the window calculation operates on daily totals rather than individual orders.

### 2. Frame boundary vocabulary

| Boundary | Meaning |
|---|---|
| `UNBOUNDED PRECEDING` | From the first row in the partition |
| `N PRECEDING` | N rows before the current row |
| `CURRENT ROW` | The current row |
| `N FOLLOWING` | N rows after the current row |
| `UNBOUNDED FOLLOWING` | Through the last row in the partition |

### 3. Common ROWS frame combinations

Assume the ordered partition contains five rows, and row 3 is the current row.

| Frame | Rows included for current row 3 | Typical use |
|---|---|---|
| `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | 1, 2, 3 | Running total |
| `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` | 1, 2, 3 | Trailing three-row calculation |
| `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` | 2, 3 | Current and previous row |
| `ROWS BETWEEN CURRENT ROW AND 2 FOLLOWING` | 3, 4, 5 | Current and next two rows |
| `ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING` | 2, 3, 4 | Centered three-row moving average |
| `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` | 1, 2, 3, 4, 5 | Whole-partition total |
| `ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING` | 3, 4, 5 | Current row through partition end |

The frame is clipped at partition boundaries. For example, `2 PRECEDING` on the first row cannot include rows before the partition; it includes only rows that actually exist.

### 4. Common analytical patterns

**Running total**

```sql
SUM(amount) OVER (
    ORDER BY order_date
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

**Trailing average over up to three rows**

```sql
AVG(amount) OVER (
    ORDER BY order_date
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)
```

**Centered moving average over up to three rows**

```sql
AVG(amount) OVER (
    ORDER BY order_date
    ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING
)
```

**Whole-partition total repeated on each row**

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
)
```

### 5. ROWS vs RANGE vs GROUPS

These frame types differ in how they identify rows around the current row.

| Frame type | How the frame is determined |
|---|---|
| `ROWS` | Physical row positions in the ordered partition |
| `RANGE` | Ordering values and peer rows; boundaries are based on ordering values rather than a count of physical rows |
| `GROUPS` | Peer groups: rows that have equal values for all window `ORDER BY` expressions |

A peer group consists of rows tied on the window's ordering expressions. Therefore, when multiple rows share an ordering value, `RANGE` or `GROUPS` can include peers together where a `ROWS` frame can stop at an individual row.

Frame syntax and supported options vary by SQL dialect. Check the target database before using a particular `RANGE` or `GROUPS` boundary.

### 6. How this connects to P043 and P044

- **P043:** uses a `ROWS` frame to calculate a cumulative month-to-date total. `PARTITION BY` restarts the calculation each month.
- **P044:** compares a month's value with the previous calendar month's value. A function such as `LAG()` is the natural window-function tool for retrieving a preceding row's value, but it does not by itself guarantee that the preceding row represents the immediately preceding calendar month when months are missing.

**Key takeaway:** `PARTITION BY` decides which group of rows is considered; `ORDER BY` decides their sequence; the frame decides which rows in that ordered partition contribute to the current row's calculation.
