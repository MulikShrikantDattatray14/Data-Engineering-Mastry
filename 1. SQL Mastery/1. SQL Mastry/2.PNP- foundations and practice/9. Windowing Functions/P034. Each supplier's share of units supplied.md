# PNP Q034. Each supplier's share of units supplied

![NOT SOLVED YET](<../../_badges/not-solved-yet.svg>) ![MEDIUM](<../../_badges/medium.svg>)

## Question and image

**Source:** [100 SQL Interview Questions](<../Source Materials/Updated_100_SQL_Interview_Questions.pdf>), question 34, pp. 58–59. **Difficulty:** Medium.

**Business scenario.** The supply chain team is reviewing dependence on each supplier before annual contracts are renewed. For every supplier on file they want the units it fulfilled and its share of all units. Two edge cases matter: a supplier with no lines must still appear with zero (it may be a contract to drop), and lines tagged with a SupplierID that is not on file must appear too, so the shares add up to 100.

**Task.** For every supplier, and for every unknown SupplierID found on order lines, return the units supplied and the share of all units. Suppliers with no lines show 0 units. Sort by units, highest first.

**Expected output (as supplied):**

```text
SupplierID : the supplier's ID, or the unrecognised ID from the lines
CompanyName : the supplier's name, or Unknown supplier
units_supplied : sum of Quantity (0 when none)
pct_of_units : share of all units (2 dp)
```

## Important learnings

### 1. Choose JOINs by checking unmatched rows on both sides

Do not choose a JOIN after noticing only the first edge case. Identify every kind of unmatched row the output must preserve:

- A supplier exists in `Suppliers`, but has no matching order line. Preserve this supplier with 0 units.
- An order line exists in `OrderDetails`, but its `SupplierID` does not exist in `Suppliers`. Preserve this order line so its units are included in the percentage denominator.

A `LEFT JOIN` from `Suppliers` preserves the first case but drops the second. A `FULL OUTER JOIN` preserves unmatched rows from both tables, satisfying both requirements.

**Reusable rule:** preserve unmatched rows from the left table → `LEFT JOIN`; preserve unmatched rows from the right table → `RIGHT JOIN`; preserve unmatched rows from both → `FULL OUTER JOIN`.

### 2. Choose GROUP BY columns based on what identifies one output row

Ask: **What does one output row represent, and which columns together identify that entity?**

Here, one output row represents one supplier identity. Grouping only by company name is unsafe because two different suppliers can have the same company name. Group by both the resolved supplier ID and resolved company name:

```sql
GROUP BY
    COALESCE(S.SupplierID, OD.SupplierID),
    COALESCE(S.CompanyName, 'Unknown supplier')
```

The supplier ID keeps different suppliers separate even when their names match. The company name supplies the displayed label. Aggregate values such as `SUM(OD.Quantity)` are calculated within each group; they are not grouping keys.

### 3. The order of GROUP BY expressions does not change the groups

These are equivalent for grouping and aggregate results:

```sql
GROUP BY
    COALESCE(S.SupplierID, OD.SupplierID),
    COALESCE(S.CompanyName, 'Unknown supplier')
```

```sql
GROUP BY
    COALESCE(S.CompanyName, 'Unknown supplier'),
    COALESCE(S.SupplierID, OD.SupplierID)
```

SQL groups by the combination of all listed expressions. Reordering those expressions does not change which rows belong to each group. Prefer a consistent, readable order—here, matching the SELECT list (SupplierID, then CompanyName) is a useful convention.
