# NULL Logic — Quick Revision Notes

**Main idea:** NULL means “no known value.” It is different from zero, an empty string, and FALSE. SQL comparisons involving NULL often produce UNKNOWN, and WHERE keeps only TRUE.

Sources: [Advanced SQL questions](<../Source Materials/Advanced_SQL_100_Query_Questions_Vol1 (2).pdf>) and [PrepNPlaced interview questions](<../Source Materials/Updated_100_SQL_Interview_Questions.pdf>). These are invented revision examples, not solutions to practice prompts.

## 1. Follow three simple rows

| order_id | amount |
|---:|---:|
| 1 | 10 |
| 2 | NULL |
| 3 | 0 |

Zero is known. NULL is unknown. Watch how that changes the calculations:

    SELECT COUNT(*) AS all_rows,
           COUNT(amount) AS known_amounts,
           SUM(amount) AS known_total,
           AVG(1.0 * amount) AS average_known,
           ROUND(AVG(1.0 * COALESCE(amount, 0)), 2) AS average_if_missing_is_zero
    FROM DemoOrders;

| all_rows | known_amounts | known_total | average_known | average_if_missing_is_zero |
|---:|---:|---:|---:|---:|
| 3 | 2 | 10 | 5 | 3.33 |

AVG(amount) uses 10 and 0, so 10 / 2 = 5. The second average intentionally substitutes zero for the missing value, so 10 / 3 = 3.33. Use COALESCE only if “missing means zero” is the required business rule.

## 2. WHERE uses TRUE, FALSE, and UNKNOWN

| Expression | Result |
|---|---|
| 10 <> 0 | TRUE |
| 0 <> 0 | FALSE |
| NULL <> 0 | UNKNOWN |
| NULL = NULL | UNKNOWN |
| NULL IS NULL | TRUE |

    SELECT order_id
    FROM DemoOrders
    WHERE amount <> 0;

Only order 1 appears. Order 2 is not “not zero”: its comparison is UNKNOWN. To ask whether a value is absent, use IS NULL or IS NOT NULL. Use parentheses with AND and OR so the intended logic is visible.

## 3. Missing match and missing value are different

Suppose customers A, B, and C exist. A has order 1 with amount 10; B has order 2 with a NULL amount; C has no order. A LEFT JOIN produces:

| customer | order_id | amount | interpretation |
|---|---:|---:|---|
| A | 1 | 10 | Matched, amount known |
| B | 2 | NULL | Matched, amount unknown |
| C | NULL | NULL | No matched order |

Checking amount IS NULL mixes B and C. Checking the non-null order key IS NULL finds only C. Likewise, COUNT(*) after this LEFT JOIN counts the C row, while COUNT(order_id) counts zero orders for C.

A right-table condition in WHERE may remove the NULL-extended row and undo the intended row preservation. Put a condition that restricts which right rows match in ON when every left row must stay.

## 4. NOT IN can be derailed by one NULL

For the test value 5:

    5 NOT IN (1, NULL)

The result is UNKNOWN: SQL cannot rule out the unknown list value being 5. In a WHERE clause the row disappears. When the inner set may contain NULL, either exclude NULL in that set or express the “no matching row” requirement with NOT EXISTS.

A positive IN test can still be TRUE when it finds a definite match, even if another value in the list is NULL.

## 5. COALESCE and NULLIF solve different problems

| Expression | Purpose | Example result |
|---|---|---|
| COALESCE(NULL, 'Unknown') | Choose the first known value | Unknown |
| NULLIF(0, 0) | Turn a specific value into NULL | NULL |
| 10.0 / NULLIF(0, 0) | Avoid a zero denominator | NULL |

A NULL result from safe division still needs interpretation; it does not mean 0%. A report may show “not defined” or exclude that group. Choose the denominator before writing a percentage.

## 6. Other places NULL changes the result

- GROUP BY puts NULL keys into one NULL group. It does not create one group per missing row.
- Most aggregates skip NULL inputs, but COUNT(*) counts rows.
- A standard equality join does not match NULL to NULL. If two missing keys should match, define that rule explicitly instead of assuming it.
- NULL sort position varies by SQL dialect and query. Specify the desired position when output ordering matters.
- A missing date may mean “not happened yet” or “data not recorded.” Those meanings need different reporting rules.
