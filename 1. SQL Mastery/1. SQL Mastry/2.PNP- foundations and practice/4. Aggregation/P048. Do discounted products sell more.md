# PNP Q048. Do discounted products sell more?

![NOT SOLVED YET](<../../_badges/not-solved-yet.svg>) ![MEDIUM](<../../_badges/medium.svg>)

## Question — Business Scenario & Task

**Source:** [100 SQL Interview Questions](<../Source Materials/Updated_100_SQL_Interview_Questions.pdf>), question 48, pp. 83–85. **Difficulty:** Medium.

**Business scenario.** The pricing team wants a bigger promotions budget. Their argument is that discounted products sell more, so deeper discounts will lift volume. Before approving it, the head of category wants a simple check: group products into discount bands and compare how many units an average product in each band has sold. "Sells more" means higher average units per product, with unsold products counted as zero.

**Task.** Band every product by its discount percentage, (Market_Price - Sale_Price) / Market_Price * 100 : Full price (0%), Up to 10% , 10% to 25% , Over 25% , and Unknown when Market_Price is missing or zero. For each band, return the number of products, how many of them ever sold, the average units sold per product (zero sellers included) and total units. List bands from full price to deepest discount, Unknown last.

**Required output columns**

| Column | Meaning |
|---|---|
| `discount_band` | The discount category assigned to every product; missing or zero Market_Price is Unknown. |
| `products` | Number of products in the band, including products that never sold. |
| `products_sold` | Number of distinct products in the band with at least one order-detail row. |
| `avg_units_per_product` | Total units in the band divided by all products in the band, including unsold products; display to 2 decimal places. |
| `total_units` | Sum of OrderDetails.Quantity for products in the band. |

**Input tables and row grain.** `Products` is the driving table: one starting row per product. `OrderDetails` supplies sales lines and can contain multiple rows per product. The final output grain is one row per discount band.

## My Solution — SQLite & SQL Server

### My final SQLite solution (preserved exactly as submitted)

```sql
SELECT
    CASE
        WHEN P.Market_Price IS NULL
             OR P.Market_Price = 0
             OR P.Sale_Price IS NULL
            THEN 'Unknown'

        WHEN P.Sale_Price >= P.Market_Price
            THEN 'Full price'

        WHEN (
            (P.Market_Price - P.Sale_Price) * 100.0
            / NULLIF(P.Market_Price, 0)
        ) <= 10
            THEN 'Up to 10%'

        WHEN (
            (P.Market_Price - P.Sale_Price) * 100.0
            / NULLIF(P.Market_Price, 0)
        ) <= 25
            THEN '10% to 25%'

        ELSE 'Over 25%'
    END AS discount_band,

    COUNT(DISTINCT P.ProductID) AS products,

    COUNT(DISTINCT OD.ProductID) AS products_sold,

    ROUND(
        COALESCE(SUM(OD.Quantity), 0) * 1.0
        / COUNT(DISTINCT P.ProductID),
        2
    ) AS avg_units_per_product,

    COALESCE(SUM(OD.Quantity), 0) AS total_units

FROM Products AS P

LEFT JOIN OrderDetails AS OD
    ON P.ProductID = OD.ProductID

GROUP BY discount_band

ORDER BY
    CASE
        WHEN discount_band = 'Unknown' THEN 1
        ELSE 0
    END ASC,

    MIN(
        (P.Market_Price - P.Sale_Price) * 100.0
        / NULLIF(P.Market_Price, 0)
    ) ASC;
```

**Validation notes**

- The learner's original query is preserved verbatim above.
- The classification handles missing or zero `Market_Price` and missing `Sale_Price` as `Unknown`.
- `Sale_Price >= Market_Price` is classified as `Full price`, matching the official solution's `discount_pct <= 0` rule.
- `COUNT(DISTINCT P.ProductID)` counts each product once despite multiple order-detail rows.
- `COUNT(DISTINCT OD.ProductID)` counts sold products once and ignores unmatched NULLs.
- `SUM(OD.Quantity)` includes all order-detail quantities; `COALESCE` returns zero for a band with no sales.
- The average divides by all distinct products in the band, so unsold products contribute zero.
- The custom sort puts Unknown last and orders the other bands by their minimum discount percentage.
- The actual source CSVs contain 22,088 products and 168,567 order-detail rows. The classification and grouped totals were independently checked against the supplied data and official band rules; the exact learner query has not been run in a SQLite engine in this workflow.

## Official Solution

**Source:** `Source Materials/PrepNPlaced_SQL_100_v2/sql/all_100_solutions.sql`, Q48. **Source dialect:** PostgreSQL 16, as stated in the answer-key header.

```sql
WITH product_units AS (
    SELECT od.ProductID,
           SUM(od.Quantity) AS units
    FROM OrderDetails AS od
    GROUP BY od.ProductID
),
priced AS (
    SELECT p.ProductID,
           100.0 * (p.Market_Price - p.Sale_Price) / NULLIF(p.Market_Price, 0) AS discount_pct,
           pu.units
    FROM Products AS p
    LEFT JOIN product_units AS pu ON pu.ProductID = p.ProductID
),
banded AS (
    SELECT pr.ProductID,
           CASE WHEN pr.discount_pct IS NULL THEN 'Unknown'
                WHEN pr.discount_pct <= 0    THEN 'Full price'
                WHEN pr.discount_pct <= 10   THEN 'Up to 10%'
                WHEN pr.discount_pct <= 25   THEN '10% to 25%'
                ELSE 'Over 25%'
           END AS discount_band,
           CASE WHEN pr.discount_pct IS NULL THEN 5
                WHEN pr.discount_pct <= 0    THEN 1
                WHEN pr.discount_pct <= 10   THEN 2
                WHEN pr.discount_pct <= 25   THEN 3
                ELSE 4
           END AS band_order,
           pr.units IS NOT NULL      AS has_sold,
           COALESCE(pr.units, 0)     AS units
    FROM priced AS pr
)
SELECT b.discount_band,
       COUNT(*)                         AS products,
       COUNT(*) FILTER (WHERE b.has_sold) AS products_sold,
       ROUND(AVG(b.units), 2)           AS avg_units_per_product,
       SUM(b.units)                     AS total_units
FROM banded AS b
GROUP BY b.discount_band, b.band_order
ORDER BY b.band_order;
```

**Official approach.** The answer key first aggregates order quantities to one row per product, then left-joins those totals to Products. It calculates a discount percentage, assigns the band and a numeric band order, counts sold products using the existence of aggregated units, and calculates average units across all products (coalescing unsold products to zero).

## My New Learnings

- Use `Products` as the driving table with a `LEFT JOIN` so products without order lines remain in the analysis.
- A product can have multiple order-detail rows. Use `COUNT(DISTINCT P.ProductID)` for product count and `COUNT(DISTINCT OD.ProductID)` for sold-product count.
- Sum every matching `OrderDetails.Quantity` row to calculate total units; do not deduplicate legitimate order lines.
- To include unsold products in the average, divide total units by the count of all distinct products in the band, not by the count of sold products.
- Use `COALESCE` to report zero units for a group with no sales.
- Use `CASE` to assign one discount band per product. Handle missing/zero market price and missing sale price before calculating the percentage.
- Treat `Sale_Price >= Market_Price` as Full price, equivalent to the official solution's non-positive discount percentage rule.
- Use an explicit sort key in `ORDER BY` when the requested category order is not alphabetical. A leading `CASE` key places Unknown last; the minimum percentage orders the non-Unknown bands.
- This problem needs classification and aggregation; a window function is not required.
