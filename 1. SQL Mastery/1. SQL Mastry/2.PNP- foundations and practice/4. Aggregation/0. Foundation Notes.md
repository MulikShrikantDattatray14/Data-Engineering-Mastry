# Aggregation and Pivoting — Quick Revision Notes

**Main idea:** choose the row grain, decide what each row contributes, then combine rows into one result per group. A pivot keeps one group row and turns categories into columns; an unpivot turns columns into labelled rows.

The orders below are invented revision data using the advanced deck's orders schema. They are not practice-question answers.

## 1. Read the starting rows

| order_id | cust_id | status | amount |
|---:|---:|---|---:|
| 101 | 1 | DELIVERED | 60 |
| 102 | 1 | CANCELLED | 20 |
| 103 | 2 | DELIVERED | 30 |
| 104 | 2 | PLACED | NULL |

One row is one order. NULL amount means the amount is unknown. It is not automatically zero.

## 2. Calculate one total for the whole table

    SELECT COUNT(*) AS order_rows,
           COUNT(amount) AS known_amounts,
           SUM(amount) AS total_amount,
           ROUND(AVG(1.0 * amount), 2) AS average_known
    FROM orders;

| order_rows | known_amounts | total_amount | average_known |
|---:|---:|---:|---:|
| 4 | 3 | 110 | 36.67 |

The calculation is 60 + 20 + 30 = 110. AVG divides 110 by **three known amounts**, not four rows. COUNT(*) includes the NULL-amount row; COUNT(amount) does not.

| Expression | What it counts or combines |
|---|---|
| COUNT(*) | Every input row |
| COUNT(column) | Non-NULL values in that column |
| COUNT(DISTINCT column) | Different non-NULL values |
| SUM(expression) | Non-NULL contributions |
| AVG(expression) | Mean of known contributions |
| MIN / MAX | Smallest / largest known contribution |

Avoid SUM(DISTINCT amount) to repair a duplicated join: two real orders may have the same amount.

## 3. GROUP BY changes the result grain

    SELECT cust_id,
           COUNT(*) AS order_count,
           SUM(amount) AS total_amount
    FROM orders
    GROUP BY cust_id
    ORDER BY cust_id;

| cust_id | order_count | total_amount |
|---:|---:|---:|
| 1 | 2 | 80 |
| 2 | 2 | 30 |

Both orders for customer 1 contribute: 60 + 20 = 80. Customer 2 has two rows but only one known amount, so SUM is 30. The result now has one row **per customer with at least one order**.

## 4. WHERE filters rows; HAVING filters groups

    SELECT cust_id, SUM(amount) AS delivered_amount
    FROM orders
    WHERE status = 'DELIVERED'
    GROUP BY cust_id
    HAVING SUM(amount) >= 40;

First WHERE keeps orders 101 and 103. Then GROUP BY produces customer totals 60 and 30. Finally HAVING keeps customer 1 because 60 >= 40. Use WHERE for a row condition and HAVING for a condition on the calculated group.

## 5. Include groups with no matching facts

Suppose customers contains Ada (1), Ben (2), and Cara (3). Cara has no order. Start from customers and LEFT JOIN orders:

    SELECT c.cust_id,
           COUNT(o.order_id) AS order_count,
           COALESCE(SUM(o.amount), 0) AS known_total
    FROM customers AS c
    LEFT JOIN orders AS o ON o.cust_id = c.cust_id
    GROUP BY c.cust_id
    ORDER BY c.cust_id;

| cust_id | order_count | known_total |
|---:|---:|---:|
| 1 | 2 | 80 |
| 2 | 2 | 30 |
| 3 | 0 | 0 |

For Cara the LEFT JOIN supplies one NULL-extended row. COUNT(*) would say 1; COUNT(o.order_id) correctly says 0. COALESCE turns the missing SUM into zero here because the report asks for a total for a customer with no orders. Decide that meaning explicitly.

## 6. Conditional aggregation pivots categories into columns

Use CASE to turn each row into 1 or 0, then sum those contributions within its group:

    SELECT cust_id,
           SUM(CASE WHEN status = 'DELIVERED' THEN 1 ELSE 0 END) AS delivered,
           SUM(CASE WHEN status = 'CANCELLED' THEN 1 ELSE 0 END) AS cancelled,
           SUM(CASE WHEN status = 'PLACED' THEN 1 ELSE 0 END) AS placed
    FROM orders
    GROUP BY cust_id
    ORDER BY cust_id;

| cust_id | delivered | cancelled | placed |
|---:|---:|---:|---:|
| 1 | 1 | 1 | 0 |
| 2 | 1 | 0 | 1 |

For customer 1, the DELIVERED test contributes 1 for order 101 and 0 for order 102, giving 1. Some dialects also support COUNT(*) FILTER (WHERE condition). CASE is widely portable and makes the 1/0 contribution visible.

A percentage needs a stated denominator. For example, customer 1 has 1 delivered order out of 2 orders: 100.0 × 1 / 2 = 50%. NULLIF(denominator, 0) prevents division by zero when a group can be empty.

## 7. Unpivot columns into labelled rows

Imagine a separate teaching table, Scores:

| learner_id | math | english |
|---:|---:|---:|
| 1 | 80 | 70 |
| 2 | 90 | NULL |

    SELECT learner_id, 'Math' AS subject, math AS score
    FROM Scores WHERE math IS NOT NULL
    UNION ALL
    SELECT learner_id, 'English', english
    FROM Scores WHERE english IS NOT NULL
    ORDER BY learner_id, subject;

| learner_id | subject | score |
|---:|---|---:|
| 1 | English | 70 |
| 1 | Math | 80 |
| 2 | Math | 90 |

Each SELECT gives the same three columns. UNION ALL stacks the rows and keeps duplicates that may be legitimate. Filters omit unknown scores only because this teaching report asks for recorded scores.

## 8. Do not aggregate after an accidental fan-out

Order 101 has two item rows. Suppose it also has two payment attempts. Joining orders, order_items, and payments produces four rows for this order: 2 items × 2 payments. SUM(o.amount) would count 60 four times.

| Stage | Rows representing order 101 |
|---|---:|
| orders | 1 |
| join two items | 2 |
| also join two payments | 4 |

Calculate items **per order** and payments **per order** separately before joining the summaries to orders. A grouped value must be calculated at the correct grain before it meets another one-to-many table.

For subtotals, GROUPING SETS or ROLLUP can add rows beyond ordinary GROUP BY in dialects that support them. Label those subtotal rows explicitly so NULL data values are not confused with subtotal markers.

## Quick check

1. What does one input row contribute: 1, an amount, or quantity × price?
2. What does one output row represent after GROUP BY?
3. Are missing rows or NULL values supposed to become zero?
4. Is a filter about source rows (WHERE) or finished groups (HAVING)?
5. Did a join multiply any amount before SUM or AVG?
