# PNP P038 — Products from inactive categories that still sold in the latest year

![NOT SOLVED YET](<../../_badges/not-solved-yet.svg>) ![MEDIUM](<../../_badges/medium.svg>)

## Question

**Source:** [100 SQL Interview Questions](<../Source Materials/Updated_100_SQL_Interview_Questions.pdf>), question 38, pp. 65–66. **Difficulty:** Medium.

**Business scenario.** The catalogue governance team switches categories off when the business exits them. A switched-off category should stop selling, but the storefront hides products by category only on some pages. The team wants every product in an inactive category that still appeared in orders during the latest calendar year in the data, with units sold and the last order date, so they can close each gap.

**Task.** Find the latest calendar year in Orders from the data itself. For every product whose category is not active and that had order lines in that year, return the units sold in that year and the most recent order date. Sort by units, highest first.

**Table-color key**

- 🟥 `Category` — category reference data.
- 🟩 `Products` — product catalogue data.
- 🟦 `Orders` and `OrderDetails` — transactional data.
- 🟪 Calculations or values combining sources.

### Required output columns

| Output column | Source / calculation | Meaning and eligibility rule | Example |
|---|---|---|---|
| `ProductID` | 🟩 `Products.ProductID` | One output row per qualifying product; only products in inactive categories with at least one order line in the latest year qualify. | `10` |
| `Product` | 🟩 `Products.Product` | Name of the qualifying product. | `Old mug` |
| `CategoryName` | 🟥 `Category.CategoryName` | Name of the inactive category to which the product belongs. | `Old stock` |
| `units_latest_year` | 🟦 `SUM(OrderDetails.Quantity)` after latest-year filtering | Total units from order lines placed in the latest calendar year. | `2` |
| `last_order_date` | 🟦 `MAX(Orders.OrderDate)` after latest-year filtering | Most recent order date for that product within the latest calendar year. | `2025-01-01` |

### How the sample produces this output

1. 🟥 Category 1 (`Old stock`) is inactive; category 2 (`Current stock`) is active.
2. 🟩 Product 10 belongs to category 1, so it qualifies for further checking. Product 20 belongs to category 2 and is removed.
3. 🟦 Product 10 has two order-detail rows: 2 units on order 100 and 3 units on order 101. Joining Orders supplies their dates.
4. The maximum order date in the sample is 2025-01-01, so the latest calendar year is 2025.
5. Only product 10's order 100 remains after the latest-year filter. Its quantity is 2 and its order date is 2025-01-01.
6. The final grouping returns one row for product 10. `SUM(Quantity)` is 2 and `MAX(OrderDate)` is 2025-01-01.

## Step 1 · Your approach before writing SQL

**Learner's agreed approach, developed incrementally:**

1. Start by filtering `Category` to inactive categories.
2. Join `Products` to those inactive categories on `CategoryID`, keeping only products from inactive categories.
3. Join those eligible products to `OrderDetails` on `ProductID`.
4. Join `OrderDetails` to `Orders` on `OrderID`, so each sale line has its order date.
5. In a separate CTE, use `MAX(OrderDate)` from `Orders` and extract its year to identify the latest calendar year dynamically.
6. Cross join the one-row latest-year result to the eligible product sales and keep only order rows whose year matches the latest year.
7. Group by the product identity and descriptive columns. Calculate total units with `SUM(Quantity)` and the most recent in-year order date with `MAX(OrderDate)`.
8. Sort by units sold descending.

**Join choices:** The learner chose `INNER JOIN` for Category → Products, Products → OrderDetails, and OrderDetails → Orders. This matches the requirement to report only products in an existing inactive category that have actual matching order lines and orders.

**Grouping decision:** The learner initially identified `ProductID` as the uniqueness key. The final query groups by `ProductID`, `Product`, `CategoryID`, and `CategoryName` so the product and category descriptors are explicit in the grouping.

**Approach review:** The learner independently identified the filtering sequence, join keys, latest-year derivation, aggregation and sorting. A formal /10 score was not recorded during the session.

## Final learner solution — SQLite

The following is the learner's selected five-CTE solution, retained as supplied:

```sql
WITH inactive_categories AS (
    SELECT
        CategoryID,
        CategoryName,
        Active
    FROM Category
    WHERE Active = 0
),

inactive_category_products AS (
    SELECT
        P.ProductID,
        P.Product,
        P.CategoryID,
        C.CategoryName
    FROM Products AS P
    INNER JOIN inactive_categories AS C
        ON P.CategoryID = C.CategoryID
),

inactive_product_sales AS (
    SELECT
        P.ProductID,
        P.Product,
        P.CategoryID,
        P.CategoryName,
        OD.OrderDetailID,
        OD.OrderID,
        OD.Quantity,
        O.OrderDate
    FROM inactive_category_products AS P
    INNER JOIN OrderDetails AS OD
        ON P.ProductID = OD.ProductID
    INNER JOIN Orders AS O
        ON OD.OrderID = O.OrderID
),

latest_year AS (
    SELECT
        MAX(OrderDate) AS latest_order_date,
        STRFTIME('%Y', MAX(OrderDate)) AS latest_year
    FROM Orders
),

latest_year_sales AS (
    SELECT
        IPS.*
    FROM inactive_product_sales AS IPS
    CROSS JOIN latest_year AS LY
    WHERE STRFTIME('%Y', IPS.OrderDate) = LY.latest_year
)

SELECT
    ProductID,
    Product,
    CategoryName,
    SUM(Quantity) AS units_latest_year,
    MAX(OrderDate) AS last_order_date
FROM latest_year_sales
GROUP BY
    ProductID,
    Product,
    CategoryID,
    CategoryName
ORDER BY
    units_latest_year DESC;
```

## Important learnings from P038

### 1. Filter the category population before looking for products

- `WHERE Active = 0` reduces Category to inactive categories.
- Joining Products to this reduced result means products in active categories cannot enter the later sales stages.
- This predicate assumes the source stores the flag consistently as numeric 0/1. If the source contains text flags such as `No`, `N`, `False`, or NULL, inspect and normalize the values rather than assuming `Active = 0` covers every inactive representation.

### 2. Follow the relationship keys in the correct order

- `Products.CategoryID = inactive_categories.CategoryID` determines whether a product belongs to an inactive category.
- `OrderDetails.ProductID = Products.ProductID` identifies the sale lines for an eligible product.
- `Orders.OrderID = OrderDetails.OrderID` supplies the order date for each sale line.
- These are three different relationships; do not join Orders directly to Products when the required path is through OrderDetails.

### 3. Why INNER JOIN is appropriate here

The output asks for products from inactive categories that still sold in the latest year. A qualifying output row therefore needs a matching category, product, order-detail line and order. The INNER JOINs remove rows without those matches. This is different from a report that must preserve unsold products or categories, where an outer join may be required.

### 4. Derive the latest year from the data

- `MAX(OrderDate)` finds the latest date in the Orders table.
- `STRFTIME('%Y', MAX(OrderDate))` extracts its year in SQLite.
- Do not hardcode the year: the query should adapt when new orders are added in a later year.
- The `latest_year` CTE is a scalar one-row result for a non-empty Orders table. The CROSS JOIN makes that value available to each eligible sales row.

### Learning — see the CROSS JOIN result before the year filter

This is the key intermediate result when combining `inactive_product_sales` with `latest_year`.

**Input 1 — `inactive_product_sales` (2 rows)**

| ProductID | Product | CategoryName | OrderDetailID | OrderID | Quantity | OrderDate |
|---:|---|---|---:|---:|---:|---|
| 10 | Old mug | Old stock | 1 | 100 | 2 | 2025-01-01 |
| 10 | Old mug | Old stock | 2 | 101 | 3 | 2024-01-01 |

**Input 2 — `latest_year` (1 row)**

| latest_order_date | latest_year |
|---|---:|
| 2025-01-01 | 2025 |

**After CROSS JOIN — before the WHERE condition (2 rows)**

A CROSS JOIN combines every row from the first input with every row from the second input. Since `inactive_product_sales` has 2 rows and `latest_year` has 1 row, the result has 2 × 1 = 2 rows. The latest-year value is attached to each sales row:

| ProductID | Product | OrderDetailID | OrderID | Quantity | OrderDate | latest_year |
|---:|---|---:|---:|---:|---|---:|
| 10 | Old mug | 1 | 100 | 2 | 2025-01-01 | 2025 |
| 10 | Old mug | 2 | 101 | 3 | 2024-01-01 | 2025 |

**After the WHERE condition — final `latest_year_sales` CTE output (1 row)**

The WHERE condition now compares the year from each `OrderDate` with `latest_year`. The 2025 row is retained; the 2024 row is excluded.

| ProductID | Product | OrderDetailID | OrderID | Quantity | OrderDate | latest_year |
|---:|---|---:|---:|---:|---|---:|
| 10 | Old mug | 1 | 100 | 2 | 2025-01-01 | 2025 |

**Important distinction:** CROSS JOIN does not filter the rows. It creates combinations. The WHERE clause performs the filtering. Because `latest_year` returns one row here, the row count stays at 2 immediately after the CROSS JOIN. If the second input returned 3 rows instead, 2 × 3 = 6 combinations would be produced before filtering.

### 5. Filter before aggregating

The latest-year filter must be applied before `SUM(Quantity)`. Otherwise, quantities from older years would be included in the total. The sample makes this visible: the 2024 quantity of 3 must not be added to the 2025 quantity of 2.

### 6. Understand the two aggregate calculations

- `SUM(Quantity)` adds every qualifying order-detail quantity for the product during the latest year.
- `MAX(OrderDate)` finds the latest date among that product's already-filtered latest-year order rows. It is not the maximum date across all years for that product.

### 7. Grouping and functional dependency

- `ProductID` is the product identifier and should identify one product when the key is valid.
- Under the stated key relationships, ProductID determines Product and CategoryID, and CategoryID determines CategoryName.
- SQLite permits selecting some non-grouped columns, but relying on that permissiveness can return arbitrary values if the grouped rows disagree.
- The saved query explicitly groups by ProductID, Product, CategoryID and CategoryName. This makes the selected descriptive attributes explicit and is suitable for stricter SQL dialects.

### 8. Date filtering and index use

The current query uses `STRFTIME('%Y', IPS.OrderDate) = LY.latest_year`, which is clear and works in SQLite for the expected date representation. Applying a function to the OrderDate column can make ordinary index use harder. A later optimization can calculate the start of the latest year and the start of the next year, then filter with a half-open range:

```sql
OrderDate >= year_start
AND OrderDate < next_year_start
```

This avoids including the first instant of the following year and is generally more index-friendly. Keep the current learner query unchanged unless an optimization is explicitly approved.

### 9. Sorting

`ORDER BY units_latest_year DESC` places products with the largest number of units sold first, as requested. No tie-breaker was specified in the task; if deterministic ordering among ties is desired, add ProductID as a secondary sort key and document that choice.

### 4. CTE 4 — derive the latest calendar year

```sql
SELECT
    MAX(OrderDate) AS latest_order_date,
    STRFTIME('%Y', MAX(OrderDate)) AS latest_year

```

The Orders table contains 2025-01-01 and 2024-01-01. MAX returns 2025-01-01; STRFTIME extracts 2025.

| 🟦 latest_order_date | 🟪 latest_year |
|---|---:|
| 2025-01-01 | 2025 |

**Rows: 1.** This one-row CTE provides the same dynamically derived reporting year to every sales row.

### 5. CTE 5 — keep only sales in the latest year

```sql
SELECT IPS.*
FROM inactive_product_sales AS IPS
CROSS JOIN latest_year AS LY
WHERE STRFTIME('%Y', IPS.OrderDate) = LY.latest_year
```

The CROSS JOIN pairs each of the two sales rows with the single latest-year row. The WHERE condition compares each order's year with 2025.

| 🟩 ProductID | 🟩 Product | 🟥 CategoryName | 🟦 OrderDetailID | 🟦 OrderID | 🟦 Quantity | 🟦 OrderDate | 🟪 latest_year | Decision |

| 10 | Old mug | Old stock | 2 | 101 | 3 | 2024-01-01 | 2025 | Exclude |

**Rows: 1.** At this point, all rows satisfy the inactive-category, actual-sale and latest-calendar-year requirements.

```sql
SELECT
    ProductID,
    Product,
    CategoryName,
    SUM(Quantity) AS units_latest_year,

    Product,
```

- `SUM(Quantity)` = 2, so `units_latest_year` = 2.
- `MAX(OrderDate)` = 2025-01-01, so `last_order_date` = 2025-01-01.
