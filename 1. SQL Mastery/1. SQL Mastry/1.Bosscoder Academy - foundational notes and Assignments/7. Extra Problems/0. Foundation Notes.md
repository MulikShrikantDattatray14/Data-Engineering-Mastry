# Extra Problems - Quick Revision Notes

**Main idea:** recognize the shape of the problem before choosing SQL syntax.

Read in this order: **identify the output population -> identify one fact -> preserve or exclude missing matches -> combine roles or pair events -> aggregate at the requested level**.

This section collects six reusable patterns from your extra problems. The examples are deliberately smaller than the full questions so the joins and counts are visible. Each pattern keeps its own example unchanged throughout. The queries use SQLite and portable SQL where possible; SQL Server notes appear beside relevant differences. Optional setup is at the end.

## 1. Choose a pattern from the requirement

Do not start by asking "Which kind of JOIN do I remember?" First say what must survive into the answer.

| Requirement | Driving rows | Pattern |
|---|---|---|
| Every user, including users with no rides | Users | LEFT JOIN, then zero-fill the summary |
| Count wins stored in several tournament columns | One winner per tournament event | UNION ALL the roles, then group |
| Visits without any transaction | Visits | NOT EXISTS or LEFT JOIN plus missing key |
| Duration from separate start/end records | One start-end pair per process | Self join on the full process key |
| Managers with enough direct reports | Manager-report links | Self join, GROUP BY manager ID, HAVING |
| Selling price weighted by sold units | Sales matched to effective prices | Date-range join, revenue / units |

The final aggregation is often easy. The hard part is creating the correct rows for it to aggregate. Check that intermediate table first.

## 2. Keep entities with zero activity

`Users` has four users; two different IDs share the name Ana.

| id | name |
|---|---|
| 1 | Ana |
| 2 | Ben |
| 3 | Cy |
| 4 | Ana |

`Rides`:

| id | user_id | distance |
|---|---|---|
| 1 | 1 | 10 |
| 2 | 1 | 20 |
| 3 | 2 | 30 |
| 4 | 4 | 5 |

Start from the complete list of users, because Cy must not disappear:

```sql
SELECT U.id, U.name, R.id AS ride_id, R.distance
FROM Users AS U
LEFT JOIN Rides AS R ON R.user_id = U.id
ORDER BY U.id, R.id;
```

| id | name | ride_id | distance |
|---|---|---|---|
| 1 | Ana | 1 | 10 |
| 1 | Ana | 2 | 20 |
| 2 | Ben | 3 | 30 |
| 3 | Cy | NULL | NULL |
| 4 | Ana | 4 | 5 |

The input has four rides; the LEFT JOIN has five rows because it also preserves Cy's missing match. That NULL row represents no ride, not a zero-distance recorded ride.

```sql
SELECT U.id, U.name,
       COUNT(R.id) AS ride_count,
       COALESCE(SUM(R.distance), 0) AS travelled_distance
FROM Users AS U
LEFT JOIN Rides AS R ON R.user_id = U.id
GROUP BY U.id, U.name
ORDER BY travelled_distance DESC, U.name ASC, U.id ASC;
```

| id | name | ride_count | travelled_distance |
|---|---|---|---|
| 1 | Ana | 2 | 30 |
| 2 | Ben | 1 | 30 |
| 4 | Ana | 1 | 5 |
| 3 | Cy | 0 | 0 |

Keep the user ID as a grouping key even if the final question only asks for name and distance. Otherwise the two Anas merge. The additional displayed ID and ride count here make the example checkable; omit them when they are not requested.

`COUNT(R.id)` counts actual rides. `COUNT(*)` would count Cy's placeholder as one. COALESCE turns Cy's missing total into the zero defined by the report.

**Filter placement matters:** if only long rides should contribute but every user must remain, put the ride condition in ON, or filter rides inside a CTE before the LEFT JOIN. A condition such as `WHERE R.distance > 10` removes Cy's NULL row. [SQLite join and WHERE processing](https://www.sqlite.org/lang_select.html#whereclause)

## 3. Combine several roles with UNION ALL

`Championships` stores four separate wins in each yearly row:

| year | Wimbledon | Fr_open | US_open | Au_open |
|---|---|---|---|---|
| 2020 | 1 | 1 | 2 | 2 |
| 2021 | 2 | 1 | 2 | 2 |

`Players` contains 1 Nadal, 2 Federer, and 3 Novak. Each tournament cell is one win; an entire yearly row is not one win.

Convert the four roles into one consistent column:

```sql
WITH wins AS (
    SELECT Wimbledon AS player_id FROM Championships
    UNION ALL
    SELECT Fr_open FROM Championships
    UNION ALL
    SELECT US_open FROM Championships
    UNION ALL
    SELECT Au_open FROM Championships
)
SELECT player_id, COUNT(*) AS win_count
FROM wins
GROUP BY player_id
ORDER BY player_id;
```

| player_id | win_count |
|---|---|
| 1 | 3 |
| 2 | 5 |

The intermediate winners are `1, 2` from Wimbledon, `1, 1` from Fr_open, `2, 2` from US_open, and `2, 2` from Au_open. That is eight events. The counts must sum to eight.

Use **UNION ALL**, because Federer winning two tournaments is two separate wins. Plain UNION on these single-column branches would reduce all eight events to just IDs 1 and 2. Each branch must return the same number of columns with compatible meanings/types. The first branch supplies the result column name. [SQL Server UNION](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/set-operators-union-transact-sql?view=sql-server-ver17)

Attach names after establishing the event rows:

```sql
WITH wins AS (
    SELECT Wimbledon AS player_id FROM Championships
    UNION ALL
    SELECT Fr_open FROM Championships
    UNION ALL
    SELECT US_open FROM Championships
    UNION ALL
    SELECT Au_open FROM Championships
)
SELECT P.player_id, P.player_name, COUNT(*) AS grand_slams_count
FROM wins AS W
JOIN Players AS P ON P.player_id = W.player_id
GROUP BY P.player_id, P.player_name
ORDER BY P.player_id;
```

| player_id | player_name | grand_slams_count |
|---|---|---|
| 1 | Nadal | 3 |
| 2 | Federer | 5 |

Novak has no winning event and is intentionally absent. Compare this with the travellers report, where zero-activity users were explicitly required.

The same pattern works for caller/callee participation, requester/accepter friendships, or home/away match contributions. Before stacking roles, decide whether each source row contributes once or once per participant. Preserve real repeated events; deduplicate only when the requirement asks for unique relationships.

## 4. Find facts with no matching child

`Visits`:

| visit_id | customer_id |
|---|---|
| 1 | 1 |
| 2 | 1 |
| 3 | 2 |
| 4 | 2 |
| 5 | 3 |
| 6 | 1 |

`Transactions`:

| transaction_id | visit_id | amount |
|---|---|---|
| 1 | 1 | 10 |
| 2 | 1 | 20 |
| 3 | 3 | 0 |

A visit with a zero-amount transaction still has a transaction. The test is whether a matching row exists, not whether its amount is positive.

```sql
SELECT V.visit_id, V.customer_id
FROM Visits AS V
LEFT JOIN Transactions AS T ON T.visit_id = V.visit_id
WHERE T.transaction_id IS NULL
ORDER BY V.visit_id;
```

| visit_id | customer_id |
|---|---|
| 2 | 1 |
| 4 | 2 |
| 5 | 3 |
| 6 | 1 |

Visit 1 has two transactions, but both matching rows are excluded by the missing-key test. Visit 3 is also excluded, even though its transaction amount is zero. The four remaining rows are four **visits**.

Now count those visits for each customer:

```sql
SELECT V.customer_id, COUNT(*) AS count_no_trans
FROM Visits AS V
WHERE NOT EXISTS (
    SELECT 1
    FROM Transactions AS T
    WHERE T.visit_id = V.visit_id
)
GROUP BY V.customer_id
ORDER BY V.customer_id;
```

| customer_id | count_no_trans |
|---|---|
| 1 | 2 |
| 2 | 1 |
| 3 | 1 |

NOT EXISTS directly asks whether the correlated lookup finds no row. The selected `1` is just a constant; the existence of rows is what matters. [SQL Server EXISTS](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/exists-transact-sql?view=sql-server-ver17)

Use a reliably non-NULL matching key for the LEFT JOIN version. Testing `T.amount IS NULL` could mistake a real transaction with an unknown amount for a missing transaction. Also avoid switching casually to NOT IN: a NULL in its result set can change the predicate to unknown for nonmatching values. [SQLite IN and NOT IN](https://www.sqlite.org/lang_expr.html#the_in_and_not_in_operators)

## 5. Pair related rows with a self join

`Activity` stores separate events. Here `[timestamp]` is a numeric number of seconds, not a SQL Server rowversion datatype:

| machine_id | process_id | activity_type | timestamp |
|---|---|---|---|
| 0 | 1 | start | 1 |
| 0 | 1 | end | 3 |
| 0 | 2 | start | 4 |
| 0 | 2 | end | 5 |
| 1 | 1 | start | 2 |
| 1 | 1 | end | 6 |

Read the same table twice under two roles: S supplies starts and E supplies ends.

```sql
SELECT S.machine_id, S.process_id,
       S.[timestamp] AS start_time,
       E.[timestamp] AS end_time,
       E.[timestamp] - S.[timestamp] AS duration
FROM Activity AS S
JOIN Activity AS E
  ON E.machine_id = S.machine_id
 AND E.process_id = S.process_id
 AND S.activity_type = 'start'
 AND E.activity_type = 'end'
ORDER BY S.machine_id, S.process_id;
```

| machine_id | process_id | start_time | end_time | duration |
|---|---|---|---|---|
| 0 | 1 | 1 | 3 | 2 |
| 0 | 2 | 4 | 5 | 1 |
| 1 | 1 | 2 | 6 | 4 |

Six event rows become three process pairs. Joining only on process_id would also pair machine 0's process 1 with machine 1's process 1. The complete key is **machine_id plus process_id**, while the type conditions distinguish the roles.

```sql
SELECT S.machine_id,
       ROUND(AVG(1.0 * (E.[timestamp] - S.[timestamp])), 3)
           AS processing_time
FROM Activity AS S
JOIN Activity AS E
  ON E.machine_id = S.machine_id
 AND E.process_id = S.process_id
 AND S.activity_type = 'start'
 AND E.activity_type = 'end'
GROUP BY S.machine_id
ORDER BY S.machine_id;
```

| machine_id | processing_time |
|---|---|
| 0 | 1.5 |
| 1 | 4 |

Machine 0 averages `(2 + 1) / 2 = 1.5`; machine 1 has one duration of 4. The denominator counts completed process pairs, not the six start/end events. Values may display as 1.5 instead of 1.500.

This relies on the exercise guarantee of exactly one start and one end per process. Repeated starts or ends would multiply matches. In a different dataset, decide how such events should be paired before calculating AVG. Zero duration is valid when end equals start.

## 6. Count direct reports

Use this `Employee` table. John 101 and John 108 are different managers:

| id | name | department | managerId |
|---|---|---|---|
| 101 | John | A | NULL |
| 102 | Dan | A | 101 |
| 103 | Ana | A | 101 |
| 104 | Ben | A | 101 |
| 105 | Cy | A | 101 |
| 106 | Dee | B | 101 |
| 107 | Eve | A | 102 |
| 108 | John | B | NULL |
| 109 | Fay | B | 108 |

Each non-NULL managerId is a direct report relationship. Department is not part of this relationship.

```sql
SELECT M.id, M.name, COUNT(R.id) AS direct_reports
FROM Employee AS M
JOIN Employee AS R ON R.managerId = M.id
GROUP BY M.id, M.name
ORDER BY M.id;
```

| id | name | direct_reports |
|---|---|---|
| 101 | John | 5 |
| 102 | Dan | 1 |
| 108 | John | 1 |

John 101 directly manages IDs 102 through 106. Eve reports to Dan 102, so she is not John's direct report. Dee counts even though she works in department B.

```sql
SELECT M.name
FROM Employee AS M
JOIN Employee AS R ON R.managerId = M.id
GROUP BY M.id, M.name
HAVING COUNT(R.id) >= 5
ORDER BY M.id;
```

| name |
|---|
| John |

HAVING filters the completed manager groups. Grouping by name alone would merge the two Johns. Grouping by both ID and selected name also meets SQL Server's grouping rules. [SQL Server GROUP BY](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-group-by-transact-sql?view=sql-server-ver17)

Direct reports require one relationship step. Counting all descendants in a management hierarchy is a different problem and usually needs recursive traversal; do not silently turn one into the other.

## 7. Match date ranges before a weighted average

`Prices` gives nonoverlapping, inclusive date intervals for each product:

| product_id | start_date | end_date | price |
|---|---|---|---|
| 1 | 2020-01-01 | 2020-01-10 | 5 |
| 1 | 2020-01-11 | 2020-01-31 | 20 |
| 2 | 2020-01-01 | 2020-01-31 | 10 |
| 3 | 2020-01-01 | 2020-01-31 | 7 |

`UnitsSold`:

| product_id | purchase_date | units |
|---|---|---|
| 1 | 2020-01-10 | 2 |
| 1 | 2020-01-11 | 1 |
| 1 | 2020-01-11 | 1 |
| 3 | 2020-01-20 | 3 |

The two identical product 1 sales are separate supplied rows and both count. Product 2 has a price but no sales.

```sql
SELECT P.product_id, P.price, U.purchase_date, U.units,
       P.price * U.units AS revenue
FROM Prices AS P
LEFT JOIN UnitsSold AS U
  ON U.product_id = P.product_id
 AND U.purchase_date >= P.start_date
 AND U.purchase_date <= P.end_date
ORDER BY P.product_id, P.start_date, U.purchase_date;
```

| product_id | price | purchase_date | units | revenue |
|---|---|---|---|---|
| 1 | 5 | 2020-01-10 | 2 | 10 |
| 1 | 20 | 2020-01-11 | 1 | 20 |
| 1 | 20 | 2020-01-11 | 1 | 20 |
| 2 | 10 | NULL | NULL | NULL |
| 3 | 7 | 2020-01-20 | 3 | 21 |

Three conditions are needed: the same product, purchase on/after the interval start, and purchase on/before the interval end. The January 10 sale uses 5; January 11 uses 20. Because intervals do not overlap, a sale cannot match two price rows for that product.

Keep these conditions in ON. Moving the date comparisons to WHERE would discard the NULL row for unsold product 2. Starting from Prices preserves the products whose average must be reported as zero.

```sql
SELECT P.product_id,
       COALESCE(
           ROUND(
               SUM(1.0 * P.price * U.units)
               / NULLIF(SUM(U.units), 0),
               2
           ),
           0
       ) AS average_price
FROM Prices AS P
LEFT JOIN UnitsSold AS U
  ON U.product_id = P.product_id
 AND U.purchase_date >= P.start_date
 AND U.purchase_date <= P.end_date
GROUP BY P.product_id
ORDER BY P.product_id;
```

| product_id | average_price |
|---|---|
| 1 | 12.5 |
| 2 | 0 |
| 3 | 7 |

Product 1 revenue is `10 + 20 + 20 = 50` across `2 + 1 + 1 = 4` units, so its average is 12.5. Product 3 gives `21 / 3 = 7`. Product 2 has no sales and receives the zero required by the question.

AVG(price) would weight matched rows equally instead of weighting units. COUNT(*) would count sale rows, including a placeholder, instead of sold units. SUM(DISTINCT ...) could erase genuine repeated purchases. Always name the denominator before writing it.

The example uses date-only values and inclusive endpoints because that is the schema's rule. Timestamp intervals often use a half-open boundary instead; do not copy `<= end_date` without checking what end_date means. A sale outside all price intervals has no known effective price: inspect that data issue rather than assuming an arbitrary price.

## 8. Quick reference and debugging checklist

### Choose the query shape

| Pattern | Key construction | Result grain |
|---|---|---|
| Zero activity included | Master list LEFT JOIN facts | One row per master entity |
| Several event roles | SELECT role1 UNION ALL SELECT role2 | One row per contribution, then entity summary |
| No matching event | NOT EXISTS / LEFT JOIN with missing key | One surviving source fact |
| Start and end pairing | Self join on all entity/process keys | One completed pair |
| Direct reports | Manager ID = report.managerId | One row per manager after grouping |
| Effective-dated price | Product match AND valid date interval | One sale at its applicable price |

### Five questions to ask before aggregating

1. **Who must remain?** All users/products, only winners, or only unmatched visits?
2. **What does one intermediate row mean?** A ride, win, visit, completed process, direct report, or sale?
3. **Can the join multiply it?** Missing process keys, overlapping price intervals, and multiple child records are common causes.
4. **What is actually counted or summed?** COUNT of a real child key, number of event rows, sum of durations, or sum of units?
5. **Which missing-value policy applies?** Zero where the question specifies it; absence where it asks only for participants; NULL when a measure is unknown.

### Small dialect reminders

| Need | SQLite | SQL Server |
|---|---|---|
| Patterns in this guide | Same JOIN, CASE, COALESCE, UNION ALL, EXISTS shapes | Same shapes |
| Fractional average of integer expression | AVG(1.0 * expression) | AVG(1.0 * expression) |
| Keep selected labels in grouped results | GROUP BY ID, name | GROUP BY ID, name |
| Limit ordered rows | LIMIT n | TOP (n) or OFFSET/FETCH |
| Date-only interval predicates | Quoted ISO text stored consistently | Typed DATE values |

SQL Server's integer AVG return type is why the decimal multiplier is a useful portable habit. [SQL Server AVG](https://learn.microsoft.com/en-us/sql/t-sql/functions/avg-transact-sql?view=sql-server-ver17)
