# Aggregation - Quick Revision Notes

**Main idea:** choose the right input rows, then reduce them to meaningful counts, totals, averages, or extremes.

Read in this order: **identify one input row -> choose a group -> calculate contributions -> combine them -> divide safely -> round the final result**.

These examples use small, consistent teaching tables. SQLite is the main dialect. SQL Server changes are marked, and an optional setup appears at the end. The notes complement your saved solutions rather than replacing their logic.

## 1. Choose the aggregate and its input

Use this `Transactions` table for the core examples:

| id | customer_id | country | state | amount | trans_date |
|---|---|---|---|---|---|
| 1 | 1 | US | approved | 100 | 2020-01-05 |
| 2 | 1 | US | declined | 50 | 2020-01-06 |
| 3 | 2 | US | approved | 100 | 2020-01-07 |
| 4 | 2 | DE | approved | 200 | 2020-02-01 |
| 5 | 3 | DE | declined | NULL | 2020-02-02 |
| 6 | 3 | NULL | approved | 50 | 2020-02-03 |

One row is a transaction. The two 100 amounts belong to different transactions and both matter. The NULL amount is unknown; the NULL country means its country is not recorded.

```sql
SELECT COUNT(*) AS transaction_count,
       SUM(amount) AS total_amount,
       AVG(1.0 * amount) AS average_amount,
       MIN(amount) AS smallest_amount,
       MAX(amount) AS largest_amount
FROM Transactions;
```

| transaction_count | total_amount | average_amount | smallest_amount | largest_amount |
|---|---|---|---|---|
| 6 | 500 | 100 | 50 | 200 |

The known amounts are `100, 50, 100, 200, 50`: total 500 across five known values, so the average is 100. The unknown amount does not turn into a sixth zero.

| Function | Question it answers |
|---|---|
| COUNT(*) | How many rows reached this calculation? |
| COUNT(column) | How many non-NULL values? |
| COUNT(DISTINCT column) | How many different non-NULL values? |
| SUM(expression) | What is the total contribution? |
| AVG(expression) | What is the mean of the known contributions? |
| MIN / MAX | What is the smallest / largest known value? |

The expression matters as much as the function. `SUM(price)` totals listed prices; `SUM(price * units)` totals revenue; `SUM(out_time - in_time)` totals visit durations. Write the contribution of **one row** before summing it.

## 2. COUNT, DISTINCT, NULL and empty inputs

### Count rows separately from known values

```sql
SELECT COUNT(*) AS all_rows,
       COUNT(amount) AS known_amounts,
       COUNT(DISTINCT amount) AS distinct_amounts,
       COUNT(*) - COUNT(amount) AS missing_amounts
FROM Transactions;
```

| all_rows | known_amounts | distinct_amounts | missing_amounts |
|---|---|---|---|
| 6 | 5 | 3 | 1 |

There are three different known amounts: 50, 100, and 200. `SUM(DISTINCT amount)` would produce 350, incorrectly removing real repeated transaction amounts if the requirement is total transaction value.

`SUM`, `AVG`, `MIN`, and `MAX` ignore NULL input values. COUNT of a column also ignores NULL, while COUNT(*) counts rows. [SQLite aggregates](https://www.sqlite.org/lang_aggfunc.html)

### Replacing NULL changes the question

```sql
SELECT AVG(1.0 * amount) AS average_known,
       ROUND(AVG(1.0 * COALESCE(amount, 0)), 2) AS average_zero_filled
FROM Transactions;
```

| average_known | average_zero_filled |
|---|---|
| 100 | 83.33 |

The first average is `500 / 5`. The second is `500 / 6`. Choose zero only when the problem defines missing amounts as zero. `COALESCE` is a business decision, not an automatic repair for every NULL.

### No matching rows versus no groups

```sql
SELECT COUNT(*) AS row_count,
       SUM(amount) AS total_amount,
       AVG(1.0 * amount) AS average_amount
FROM Transactions
WHERE id < 0;
```

| row_count | total_amount | average_amount |
|---|---|---|
| 0 | NULL | NULL |

An aggregate without GROUP BY still produces one summary row on this empty input. A query grouped by country on the same empty input produces no groups and therefore no result rows. `COALESCE(SUM(amount), 0)` can replace a NULL aggregate, but cannot create a missing grouped row; that requires a driving list of entities and a LEFT JOIN.

## 3. One summary per group

```sql
SELECT country,
       COUNT(*) AS transaction_count,
       COUNT(amount) AS known_amount_count,
       SUM(amount) AS total_amount,
       ROUND(AVG(1.0 * amount), 2) AS average_amount
FROM Transactions
GROUP BY country
ORDER BY CASE WHEN country IS NULL THEN 1 ELSE 0 END, country;
```

| country | transaction_count | known_amount_count | total_amount | average_amount |
|---|---|---|---|---|
| DE | 2 | 1 | 200 | 200 |
| US | 3 | 3 | 250 | 83.33 |
| NULL | 1 | 1 | 50 | 50 |

For DE, there are two transactions but only one known amount. For US, all three amounts contribute. NULL country rows form a group, rather than disappearing from GROUP BY.

Do not average the displayed group averages to get the overall transaction average: `(200 + 83.33 + 50) / 3` weights the countries equally. The overall average uses the original five known transaction amounts. When combining summaries, carry **sum and non-NULL count**, then divide total sum by total count.

If the requirement changes to month **and** country, both belong in GROUP BY. The unit represented by one output row determines the keys.

## 4. Conditional aggregation

Compute several measures from the same input population with CASE:

```sql
SELECT country,
       COUNT(*) AS transaction_count,
       SUM(CASE WHEN state = 'approved' THEN 1 ELSE 0 END)
           AS approved_count,
       SUM(amount) AS total_amount,
       SUM(CASE WHEN state = 'approved' THEN amount ELSE 0 END)
           AS approved_amount
FROM Transactions
GROUP BY country
ORDER BY CASE WHEN country IS NULL THEN 1 ELSE 0 END, country;
```

| country | transaction_count | approved_count | total_amount | approved_amount |
|---|---|---|---|---|
| DE | 2 | 1 | 200 | 200 |
| US | 3 | 2 | 250 | 200 |
| NULL | 1 | 1 | 50 | 50 |

The count CASE contributes 1 for an approved row and 0 otherwise. The amount CASE contributes that approved amount. The NULL-country group remains present because all measures are calculated in that same group.

Compare these expressions carefully:

| Expression | Meaning |
|---|---|
| `SUM(CASE WHEN condition THEN 1 ELSE 0 END)` | Count matching rows |
| `COUNT(CASE WHEN condition THEN 1 END)` | Count matching rows; omitted ELSE produces NULL |
| `COUNT(CASE WHEN condition THEN 1 ELSE 0 END)` | Counts every row because both 1 and 0 are non-NULL |
| `SUM(CASE WHEN condition THEN amount ELSE 0 END)` | Add amounts only for matching rows |

Putting `WHERE state = 'approved'` before grouping would also remove declined rows from the **total** count and amount. Use WHERE when the whole calculation should exclude them; use CASE when only a particular measure should exclude them.

Separately aggregated branches can also work, as in your saved monthly-transactions solution. When joining such summaries, remember that ordinary equality does not match NULL country to NULL country. A single conditional aggregation avoids that particular join issue.

## 5. Ratios, percentages and safe division

Write the numerator and denominator in words first:

> Approved transaction percentage = approved transaction rows / all transaction rows * 100.

```sql
SELECT SUM(CASE WHEN state = 'approved' THEN 1 ELSE 0 END)
           AS approved_count,
       COUNT(*) AS total_count,
       ROUND(
           100.0 * SUM(CASE WHEN state = 'approved' THEN 1 ELSE 0 END)
           / NULLIF(COUNT(*), 0),
           2
       ) AS approved_percentage
FROM Transactions;
```

| approved_count | total_count | approved_percentage |
|---|---|---|
| 4 | 6 | 66.67 |

Four of six rows are approved. A fraction would be about 0.67; a percentage is 66.67. Do not divide by `COUNT(amount)` here: a missing monetary value does not mean the transaction is absent.

### Force decimal division before information is lost

```sql
SELECT 1 / 2 AS integer_division,
       1.0 / 2 AS decimal_division,
       ROUND(1 / 2, 2) AS rounded_too_late;
```

| integer_division | decimal_division | rounded_too_late |
|---|---|---|
| 0 | 0.5 | 0 |

Rounding cannot restore a fraction discarded by integer division. Multiply by `1.0` or cast to a suitable decimal type **before** dividing. SQLite's integer arithmetic rules explain the first result. [SQLite expressions](https://www.sqlite.org/lang_expr.html)

SQL Server also needs care with `AVG(integer_column)`, which returns an integer type. `AVG(1.0 * integer_column)` preserves fractions. For exact decimal business calculations, choose an appropriate `DECIMAL(p,s)`; SQLite's numeric affinity does not provide SQL Server-style fixed-decimal arithmetic. [SQL Server AVG return types](https://learn.microsoft.com/en-us/sql/t-sql/functions/avg-transact-sql?view=sql-server-ver17), [SQLite type affinity](https://www.sqlite.org/datatype3.html#type_affinity)

### Zero denominator: decide what the result should mean

```sql
SELECT 1.0 / NULLIF(0, 0) AS undefined_ratio,
       COALESCE(1.0 / NULLIF(0, 0), 0) AS zero_by_policy;
```

| undefined_ratio | zero_by_policy |
|---|---|
| NULL | 0 |

`NULLIF(denominator, 0)` converts a zero denominator to NULL. Add COALESCE only if the problem defines the undefined ratio as zero. This also avoids relying on SQLite and SQL Server having identical divide-by-zero behavior.

Round the final aggregate to the requested precision. Rounding each contribution first can change the sum. Numeric rounding does not guarantee display text such as `50.00`; a client may show `50`.

For large SQL Server integer totals, cast the **input** to a wider type before SUM if needed. Multiplying an already-overflowed integer SUM by 1.0 is too late. [SQL Server SUM return types](https://learn.microsoft.com/en-us/sql/t-sql/functions/sum-transact-sql?view=sql-server-ver17)

## 6. Weighted averages

A separate `PriceSales` example makes the weights visible:

| product_id | price | units |
|---|---|---|
| 1 | 10 | 1 |
| 1 | 20 | 3 |
| 2 | 5 | 2 |
| 2 | 5 | 2 |

```sql
SELECT product_id,
       SUM(price * units) AS revenue,
       SUM(units) AS total_units,
       AVG(1.0 * price) AS average_row_price,
       ROUND(SUM(price * units) * 1.0 / NULLIF(SUM(units), 0), 2)
           AS weighted_price
FROM PriceSales
GROUP BY product_id
ORDER BY product_id;
```

| product_id | revenue | total_units | average_row_price | weighted_price |
|---|---|---|---|---|
| 1 | 70 | 4 | 15 | 17.5 |
| 2 | 20 | 4 | 5 | 5 |

Product 1 sold one unit at 10 and three at 20. The revenue is `10 + 60 = 70`; dividing by four units gives 17.5. A simple average of the two row prices gives 15 because it weights the rows equally.

Use **SUM(value * weight) / SUM(weight)** whenever a row represents several units. The same principle combines group averages: multiply each average by its contributing count, add those weighted totals, and divide by the combined count. Preserve exact sums/counts when available instead of rebuilding them from rounded averages.

## 7. Joins, missing rows and duplicated contributions

`Customers` contains IDs 1 Ana, 2 Ben, 3 Cy, and 4 Dee. Dee has no transaction.

```sql
SELECT C.customer_id, C.name,
       COUNT(*) AS joined_rows,
       COUNT(T.id) AS transaction_count,
       COALESCE(SUM(T.amount), 0) AS total_amount
FROM Customers AS C
LEFT JOIN Transactions AS T ON T.customer_id = C.customer_id
GROUP BY C.customer_id, C.name
ORDER BY C.customer_id;
```

| customer_id | name | joined_rows | transaction_count | total_amount |
|---|---|---|---|---|
| 1 | Ana | 2 | 2 | 150 |
| 2 | Ben | 2 | 2 | 300 |
| 3 | Cy | 2 | 2 | 50 |
| 4 | Dee | 1 | 0 | 0 |

The LEFT JOIN creates one placeholder for Dee. COUNT(*) counts it; COUNT(T.id) does not. Zero-filling the amount is appropriate here only because the report defines no transactions as a zero total.

### Inspect the joined rows before trusting SUM

Suppose `Tags` contains two labels for transaction 1:

```sql
SELECT T.id, T.amount, G.tag
FROM Transactions AS T
JOIN Tags AS G ON G.transaction_id = T.id
ORDER BY T.id, G.tag;
```

| id | amount | tag |
|---|---|---|
| 1 | 100 | online |
| 1 | 100 | priority |

Summing these joined amounts gives 200, even though there is one 100 transaction. `SUM(DISTINCT amount)` is not a general fix: it would wrongly merge different transactions that happen to share the same amount.

If labels only determine whether a transaction qualifies, use an existence test:

```sql
SELECT SUM(T.amount) AS tagged_transaction_total
FROM Transactions AS T
WHERE EXISTS (
    SELECT 1
    FROM Tags AS G
    WHERE G.transaction_id = T.id
);
```

| tagged_transaction_total |
|---|
| 100 |

If the report needs independent child summaries, aggregate each child table to one row per parent before joining the summaries. Check that each join key has the multiplicity you expect. A correct SUM applied to duplicated input still gives a wrong business result.

## 8. Dates, durations and earliest events

### Filter the requested time period before aggregating

```sql
SELECT COUNT(*) AS january_count, SUM(amount) AS january_total
FROM Transactions
WHERE trans_date >= '2020-01-01'
  AND trans_date < '2020-02-01';
```

| january_count | january_total |
|---|---|
| 3 | 250 |

The half-open interval includes January and excludes February. It also works for timestamps at any time during January when stored in a consistent comparable format. Quote dates: unquoted `2020-01-01` is arithmetic, not a date literal in SQLite.

For a monthly summary, include the year:

```sql
SELECT STRFTIME('%Y-%m', trans_date) AS month,
       COUNT(*) AS transaction_count,
       SUM(amount) AS total_amount
FROM Transactions
GROUP BY STRFTIME('%Y-%m', trans_date)
ORDER BY month;
```

| month | transaction_count | total_amount |
|---|---|---|
| 2020-01 | 3 | 250 |
| 2020-02 | 3 | 250 |

SQL Server can group by `YEAR(trans_date), MONTH(trans_date)` or by a month-start date. SQLite uses date functions such as STRFTIME; it does not have SQL Server's YEAR/MONTH functions by default. [SQLite date functions](https://www.sqlite.org/lang_datefunc.html)

### Calculate each duration before combining visits

`WorkVisits` contains two visits for employee 1 on January 1, another visit on January 2, and one visit for employee 2:

```sql
SELECT emp_id, event_day,
       SUM(out_time - in_time) AS total_minutes
FROM WorkVisits
GROUP BY emp_id, event_day
ORDER BY emp_id, event_day;
```

| emp_id | event_day | total_minutes |
|---|---|---|
| 1 | 2020-01-01 | 70 |
| 1 | 2020-01-02 | 20 |
| 2 | 2020-01-01 | 30 |

For employee 1's first day: `(40 - 10) + (90 - 50) = 70`. These values are numeric minutes, so subtraction is enough. Date/time strings require date arithmetic instead:

```sql
SELECT ROUND(
    (JULIANDAY('2020-01-01 13:30:00')
     - JULIANDAY('2020-01-01 12:00:00')) * 1440,
    2
) AS elapsed_minutes;
```

| elapsed_minutes |
|---|
| 90 |

In SQL Server, `DATEDIFF(minute, start_time, end_time)` counts minute boundaries. It matches this whole-minute example, but is not exact fractional elapsed minutes for arbitrary timestamps. [SQL Server DATEDIFF](https://learn.microsoft.com/en-us/sql/t-sql/functions/datediff-transact-sql?view=sql-server-ver17)

### "First" changes the population before the ratio

For immediate **first** deliveries, find MIN(order_date) per customer, join back on customer and date, then test whether that first order was immediate. For next-day retention, find each player's first login, then match activity on exactly the following date. A later immediate order or any later login is insufficient. Identify eligible events first; only then count them for the numerator.

## 9. Grouped aggregates versus windows

```sql
SELECT id, customer_id, amount,
       SUM(amount) OVER (PARTITION BY customer_id) AS customer_total
FROM Transactions
ORDER BY id;
```

| id | customer_id | amount | customer_total |
|---|---|---|---|
| 1 | 1 | 100 | 150 |
| 2 | 1 | 50 | 150 |
| 3 | 2 | 100 | 300 |
| 4 | 2 | 200 | 300 |
| 5 | 3 | NULL | 50 |
| 6 | 3 | 50 | 50 |

GROUP BY customer_id would produce three customer rows. The window keeps all six transaction rows and attaches the customer summary to each one. Choose using the required output grain. Running totals and rankings belong in the dedicated window-functions notes.

## 10. Quick reference and final checks

| Need | Expression or approach | Common trap |
|---|---|---|
| Count facts | COUNT(*) | Counting a multiplied join |
| Count real child rows after LEFT JOIN | COUNT(child_primary_key) | Counting the placeholder |
| Count distinct entities | COUNT(DISTINCT id) | Counting repeated events instead |
| Total line contribution | SUM(price * units) | SUM(price) |
| Mean of known values | AVG(1.0 * value) | Dividing by all rows when values are NULL |
| Conditional count | SUM(CASE WHEN ... THEN 1 ELSE 0 END) | COUNT with ELSE 0 |
| Percentage | numerator * 100.0 / denominator | Integer division or wrong population |
| Weighted mean | SUM(value * weight) / SUM(weight) | Averaging row prices |
| Empty denominator | NULLIF(denominator, 0) | Assigning zero without a rule |
| Keep zero-activity entities | Entity list LEFT JOIN facts | Starting from facts only |
| One summary per entity | GROUP BY entity key | Grouping by an event ID |
| Detail plus total | Aggregate OVER (PARTITION BY ...) | Collapsing rows that must remain |

Five checks:

1. **Grain:** what does one input row represent after every join?
2. **Contribution:** what amount, count flag, or duration does that row contribute?
3. **Population:** which rows belong in the numerator and denominator?
4. **Arithmetic:** NULLs, zero denominator, decimal division, overflow, and final rounding?
5. **Output:** correct group keys, aliases, row count, and required order?

The section's exercises combine these ideas in delivery percentages, latest logins, daily employee time, retention, monthly transactions, first logins, warehouse volumes, largest customer order counts, and project experience averages.
