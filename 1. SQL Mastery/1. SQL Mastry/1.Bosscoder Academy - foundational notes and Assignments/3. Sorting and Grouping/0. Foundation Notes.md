# Sorting and Grouping - Quick Revision Notes

**Main idea:** decide which rows belong together, calculate one summary per group, and put the final rows in the requested order.

Read in this order: **define a result row -> filter input -> choose group keys -> calculate -> filter groups -> sort -> limit**.

The examples reuse a small shop dataset. They are teaching data, not replacements for any saved practice solution. The queries use SQLite; SQL Server differences are marked. Run the optional setup at the end in a scratch database.

## 1. Start with the output row

`Customers` contains two different people named Ana. Their IDs distinguish them.

| customer_id | name | region |
|---|---|---|
| 1 | Ana | East |
| 2 | Ben | West |
| 3 | Ana | East |
| 4 | Dee | NULL |

`Orders` contains one row per order. A NULL amount means the amount is unknown, not zero.

| order_id | customer_id | product_id | order_date | status | amount |
|---|---|---|---|---|---|
| 1 | 1 | 10 | 2020-06-01 | paid | 100 |
| 2 | 1 | 20 | 2020-06-05 | paid | 50 |
| 3 | 1 | 10 | 2020-07-01 | returned | 20 |
| 4 | 2 | 10 | 2020-06-01 | paid | 100 |
| 5 | 2 | 10 | 2020-06-07 | pending | NULL |
| 6 | 3 | 20 | 2020-06-03 | paid | 100 |
| 7 | 3 | 10 | 2020-07-01 | paid | 100 |
| 8 | 4 | 20 | 2020-07-02 | pending | NULL |

The product catalog contains product IDs **10 and 20**.

Before choosing a clause, complete: **"One result row represents ___."**

| Required result | One row represents | Main operation |
|---|---|---|
| Orders from largest to smallest | An order | ORDER BY |
| Total order amount per customer | A customer | GROUP BY customer_id |
| Counts per customer and product | A customer-product pair | GROUP BY both IDs |
| Unique ordered products | A product ID | DISTINCT |
| Customers with at least two orders | A qualifying customer | GROUP BY, then HAVING |

Sorting changes the sequence. Grouping changes how many detail rows are represented by each result row. A grouped query is not automatically sorted; put the required order in the final `ORDER BY`. [SQLite SELECT processing](https://www.sqlite.org/lang_select.html)

## 2. ORDER BY, ties and row limits

### Read sort keys from left to right

```sql
SELECT order_id, customer_id, amount
FROM Orders
WHERE amount IS NOT NULL
ORDER BY amount DESC, order_id ASC;
```

| order_id | customer_id | amount |
|---|---|---|
| 1 | 1 | 100 |
| 4 | 2 | 100 |
| 6 | 3 | 100 |
| 7 | 3 | 100 |
| 2 | 1 | 50 |
| 3 | 1 | 20 |

`amount DESC` puts the largest amounts first. `order_id ASC` decides the order among the four 100s. A later sort key only breaks ties in earlier keys; it does not replace them.

`ASC` is the default, but writing it makes a revision answer easier to read. If a question says "highest total, then smallest name," use total descending followed by name ascending. Add a unique ID when otherwise equal rows need a reproducible sequence.

### Top rows come after sorting

```sql
SELECT order_id, amount
FROM Orders
WHERE amount IS NOT NULL
ORDER BY amount DESC, order_id ASC
LIMIT 2;
```

| order_id | amount |
|---|---|
| 1 | 100 |
| 4 | 100 |

This means **exactly two rows**, not every order tied for the largest amount. If the question wants all ties, filtering by the maximum value or using a ranking function is a different requirement.

SQL Server uses `TOP` in the select list:

```sqlserver
SELECT TOP (2) order_id, amount
FROM Orders
WHERE amount IS NOT NULL
ORDER BY amount DESC, order_id ASC;
```

Do not rely on insertion order, a primary-key index, or an earlier CTE's apparent order. The outermost query controls the displayed sequence. [SQL Server ORDER BY](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-order-by-clause-transact-sql?view=sql-server-ver17)

## 3. NULLs, custom order and text comparisons

### State where unknown values should appear

Both SQLite and SQL Server normally place NULL before non-NULL values in ascending order. A portable way to put NULL last, regardless of the numeric direction, is an explicit flag:

```sql
SELECT order_id, amount
FROM Orders
ORDER BY CASE WHEN amount IS NULL THEN 1 ELSE 0 END,
         amount ASC,
         order_id ASC;
```

| order_id | amount |
|---|---|
| 3 | 20 |
| 2 | 50 |
| 1 | 100 |
| 4 | 100 |
| 6 | 100 |
| 7 | 100 |
| 5 | NULL |
| 8 | NULL |

Known amounts receive sort flag 0, unknown amounts receive 1, and the remaining keys sort within those groups. This sorts the rows without changing NULL into a misleading monetary value. [SQLite ordering rules](https://www.sqlite.org/lang_select.html#the_order_by_clause), [SQL Server ordering rules](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-order-by-clause-transact-sql?view=sql-server-ver17)

### Custom business priority uses CASE too

Suppose pending orders should appear first, then paid, then returned:

```sql
SELECT order_id, status
FROM Orders
ORDER BY CASE status
             WHEN 'pending' THEN 0
             WHEN 'paid' THEN 1
             WHEN 'returned' THEN 2
             ELSE 3
         END,
         order_id;
```

| order_id | status |
|---|---|
| 5 | pending |
| 8 | pending |
| 1 | paid |
| 2 | paid |
| 4 | paid |
| 6 | paid |
| 7 | paid |
| 3 | returned |

The CASE result is a temporary sort value. It need not appear in the output.

For names, "alphabetical" depends on the database collation, including case and accents. Do not assume SQLite's default text comparisons and a SQL Server database collation treat `Ana`, `ana`, and accented names identically. An explicit collation is a dialect-specific decision; choose it only when the question requires one. [SQL Server COLLATE in ordering](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-order-by-clause-transact-sql?view=sql-server-ver17)

## 4. GROUP BY and composite keys

### One key: one summary per customer

```sql
SELECT customer_id,
       COUNT(*) AS order_count,
       SUM(amount) AS total_amount,
       ROUND(AVG(1.0 * amount), 2) AS avg_amount
FROM Orders
GROUP BY customer_id
ORDER BY customer_id;
```

| customer_id | order_count | total_amount | avg_amount |
|---|---:|---:|---:|
| 1 | 3 | 170 | 56.67 |
| 2 | 2 | 100 | 100 |
| 3 | 2 | 200 | 100 |
| 4 | 1 | NULL | NULL |

Eight orders become four customer summaries. `AVG` divides the sum by the count of **non-NULL** amounts: customer 1 has `(100 + 50 + 20) / 3 = 56.67`, while customer 2 has `100 / 1 = 100.00` because its other amount is NULL. Customer 2 still has two order rows under `COUNT(*)`. Customer 4's sum and average are NULL because their only amount is unknown. The `1.0 * amount` keeps a fractional average in both SQLite and SQL Server.

### Two keys: one summary per exact pair

```sql
SELECT customer_id, product_id, COUNT(*) AS order_count
FROM Orders
GROUP BY customer_id, product_id
ORDER BY customer_id, product_id;
```

| customer_id | product_id | order_count |
|---|---|---|
| 1 | 10 | 2 |
| 1 | 20 | 1 |
| 2 | 10 | 2 |
| 3 | 10 | 1 |
| 3 | 20 | 1 |
| 4 | 20 | 1 |

Grouping by only `customer_id` merges that customer's different products. Grouping by `order_id` as well would split the groups back into individual orders. Add a key because it defines the requested result, not just because the column exists.

The same idea handles day-and-brand, actor-and-director, employee-and-day, and latitude-and-longitude groups. Each combination defines its own group.

## 5. DISTINCT and counting unique values

These operations answer different questions:

```sql
SELECT customer_id,
       COUNT(*) AS order_rows,
       COUNT(product_id) AS known_product_rows,
       COUNT(DISTINCT product_id) AS unique_products
FROM Orders
GROUP BY customer_id
ORDER BY customer_id;
```

| customer_id | order_rows | known_product_rows | unique_products |
|---|---|---|---|
| 1 | 3 | 3 | 2 |
| 2 | 2 | 2 | 1 |
| 3 | 2 | 2 | 2 |
| 4 | 1 | 1 | 1 |

Customer 1 has three order rows but two different products. Repeated orders count as events; they do not become new unique products.

`SELECT DISTINCT customer_id, product_id` returns the unique **pairs**, not independent lists of customers and products. To count unique pairs portably, make the pairs first:

```sql
SELECT COUNT(*) AS unique_pairs
FROM (
    SELECT DISTINCT customer_id, product_id
    FROM Orders
) AS pairs;
```

| unique_pairs |
|---|
| 6 |

Do not concatenate IDs to simulate a pair: `(1, 23)` and `(12, 3)` could both become `123`. A derived table preserves the real columns. `COUNT(DISTINCT column)` ignores NULL, just as `COUNT(column)` does. [SQLite aggregate functions](https://www.sqlite.org/lang_aggfunc.html)

## 6. WHERE versus HAVING

Think **row condition first; group condition second**.

Find customers whose paid orders total at least 150:

```sql
SELECT customer_id, SUM(amount) AS paid_total
FROM Orders
WHERE status = 'paid'
GROUP BY customer_id
HAVING SUM(amount) >= 150
ORDER BY customer_id;
```

| customer_id | paid_total |
|---|---|
| 1 | 150 |
| 3 | 200 |

Trace customer 1: keep orders 1 and 2 because they are paid; add `100 + 50`; then keep the resulting 150 group. The returned order is excluded before calculating the sum.

`WHERE amount >= 150` would ask for individual large orders and remove every order in this dataset. `HAVING SUM(amount) >= 150` asks about the accumulated group. Do not use an aggregate directly in the same query's WHERE.

A useful logical reading order is:

```text
FROM / JOIN
-> WHERE keeps input rows
-> GROUP BY forms groups
-> aggregate calculations and HAVING test groups
-> SELECT returns requested columns
-> DISTINCT removes repeated result rows if requested
-> ORDER BY sorts
-> LIMIT / TOP chooses a requested subset
```

This is a reasoning order, not a promise about the engine's physical execution plan. For portable SQL, repeat the aggregate expression in HAVING instead of relying on its SELECT alias. `ORDER BY paid_total` is fine.

## 7. Identity, names and strict grouping

Group customers by their identity even when the output only needs their name:

```sql
SELECT C.customer_id, C.name, SUM(O.amount) AS paid_total
FROM Customers AS C
JOIN Orders AS O ON O.customer_id = C.customer_id
WHERE O.status = 'paid'
GROUP BY C.customer_id, C.name
ORDER BY C.customer_id;
```

| customer_id | name | paid_total |
|---|---|---|
| 1 | Ana | 150 |
| 2 | Ben | 100 |
| 3 | Ana | 200 |

Grouping by `C.name` alone would merge the two Anas into 350. Including name alongside the unique ID keeps the selection explicit and works in SQL Server.

For each selected column, check: **is it a group key, or inside an aggregate?** SQL Server generally requires the former for selected nonaggregated columns. SQLite permits "bare" columns, but accepting a query does not make an arbitrary detail value meaningful. [SQL Server GROUP BY requirements](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-group-by-transact-sql?view=sql-server-ver17), [SQLite bare columns](https://www.sqlite.org/lang_select.html#bare_columns_in_an_aggregate_query)

Avoid this shape when you need an order ID associated with a date:

```text
SELECT customer_id, order_id, MAX(order_date)
FROM Orders
GROUP BY customer_id;
```

A single built-in MIN/MAX has special bare-column behavior in SQLite, but ties still leave a choice of row and the query is not portable. Make the relationship explicit instead.

## 8. First or latest values versus whole rows

Finding the earliest **date** is one grouped calculation. Finding **all orders on that date** needs those dates matched back to the detail rows.

```sql
WITH first_dates AS (
    SELECT product_id, MIN(order_date) AS first_date
    FROM Orders
    GROUP BY product_id
)
SELECT O.product_id, O.order_id, O.order_date, O.amount
FROM Orders AS O
JOIN first_dates AS F
  ON O.product_id = F.product_id
 AND O.order_date = F.first_date
ORDER BY O.product_id, O.order_id;
```

| product_id | order_id | order_date | amount |
|---|---|---|---|
| 10 | 1 | 2020-06-01 | 100 |
| 10 | 4 | 2020-06-01 | 100 |
| 20 | 6 | 2020-06-03 | 100 |

Product 10 has two orders on its first day, so both survive. Joining only on the date could attach an order belonging to another product. Joining only on product would bring back every order for that product.

For latest rows, replace MIN with MAX. If the requirement is exactly one row despite tied dates, specify a tie rule and use `ROW_NUMBER()` in a CTE. A random detail column beside MAX does not express that rule.

Also decide **when to filter**. "Latest paid order" filters paid rows before MAX. "Was the latest order paid?" first finds the latest among all orders, then inspects its status. Those are different questions.

## 9. All required items and multiple conditions

### Bought every catalog product

The required product set is IDs 10 and 20. Restrict to paid orders and count distinct catalog IDs:

```sql
SELECT O.customer_id
FROM Orders AS O
JOIN Product AS P ON P.product_id = O.product_id
WHERE O.status = 'paid'
GROUP BY O.customer_id
HAVING COUNT(DISTINCT P.product_id) = (
    SELECT COUNT(*) FROM Product
)
ORDER BY O.customer_id;
```

| customer_id |
|---|
| 1 |
| 3 |

Both customers cover the two required IDs. Customer 2 ordered product 10 repeatedly, but repeated purchases cannot substitute for missing product 20.

This pattern compares **coverage of a required set**, not event count. The join limits counted IDs to the catalog. If the required catalog can be empty and every customer should then qualify, start from the full customer population and use a missing-item/`NOT EXISTS` formulation; this grouped paid-order version only sees customers with qualifying orders.

### Has A and B, but no forbidden event

For this same dataset: paid orders for products 10 and 20, and no returned order:

```sql
SELECT customer_id
FROM Orders
GROUP BY customer_id
HAVING SUM(CASE WHEN status = 'paid' AND product_id = 10
                THEN 1 ELSE 0 END) > 0
   AND SUM(CASE WHEN status = 'paid' AND product_id = 20
                THEN 1 ELSE 0 END) > 0
   AND SUM(CASE WHEN status = 'returned'
                THEN 1 ELSE 0 END) = 0
ORDER BY customer_id;
```

| customer_id |
|---|
| 3 |

Customer 1 has the two paid products but also a returned order. Do not filter returns out with WHERE first: that would erase the evidence needed to reject customer 1. Keep the rows and test their aggregate flags.

## 10. Quick reference and submission checks

| Wording in the question | Starting point | Check |
|---|---|---|
| Largest first, alphabetical tie | ORDER BY metric DESC, name ASC | Add ID for a complete order if needed |
| One row per entity | GROUP BY entity ID | Names may repeat |
| One row per pair | GROUP BY both keys | Do not add a unique event ID |
| How many events | COUNT(*) | Repeated events may be valid |
| How many different entities | COUNT(DISTINCT id) | NULL IDs are excluded |
| Keep individual rows | WHERE | No same-level aggregate condition |
| Keep qualifying totals/counts | HAVING | Evaluate after group formation |
| First/latest value | MIN/MAX | Filter the right population first |
| Details at first/latest value | Aggregate then join back | Include entity key and value |
| All required items | Distinct coverage equals required count | Count required IDs, not purchases |
| A and B, but not C | Conditional counts in HAVING | Preserve evidence for C |
| Top N rows | Sort, then LIMIT/TOP | Clarify ties versus exact row count |

Before submitting:

1. State the result grain and match it to the group keys.
2. Verify duplicate events versus distinct entities.
3. Trace one group manually through WHERE and HAVING.
4. Check missing values, repeated names, and tied dates or scores.
5. Check exact aliases, final ordering, and row-limit semantics.
