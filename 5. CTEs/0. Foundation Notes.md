# CTEs - Quick Revision Notes

**A Common Table Expression (CTE) gives a name to a query result so the next part of the same statement can use it.** Use it when naming intermediate steps makes the logic easier to build and check.

Read in this order: **define each row -> build one named step -> connect steps -> check the population -> learn recursion**. Examples use SQLite first. SQL Server differences appear where they matter. Optional setup is at the end.

## 1. One ordinary CTE

Use this small employee table throughout the first examples. Each row represents one employee; `manager_id` refers to another employee's ID.

| employee_id | first_name | last_name | department | salary | manager_id |
|---|---|---|---|---:|---:|
| 1 | Michael | Anderson | Management | 120000 | NULL |
| 2 | Emily | Johnson | Engineering | 90000 | 1 |
| 3 | Daniel | Williams | Sales | 80000 | 1 |
| 4 | Sophia | Miller | Engineering | 70000 | 2 |
| 5 | Ethan | Brown | Engineering | 60000 | 2 |

Task: calculate one average per department.

```sql
WITH department_stats AS (
    SELECT department, AVG(1.0 * salary) AS average_salary
    FROM employees
    GROUP BY department
)
SELECT department, ROUND(average_salary, 2) AS average_salary
FROM department_stats
ORDER BY department;
```

| department | average_salary |
|---|---:|
| Engineering | 73333.33 |
| Management | 120000.00 |
| Sales | 80000.00 |

Read the query as two steps:

1. Inside the parentheses, group five employees into three department rows.
2. Outside, read that named result, round for display, and sort it.

`WITH` starts the definition; `department_stats` is your chosen name; `AS (...)` holds the query. The final `SELECT` consumes it. A CTE definition by itself is incomplete. The final output may display `120000.0` rather than `120000.00`; rounding and fixed-width formatting are different.

The multiplication by `1.0` preserves a fractional average in SQL Server too: `AVG` of an integer expression otherwise returns an integer there. [SQL Server AVG](https://learn.microsoft.com/en-us/sql/t-sql/functions/avg-transact-sql)

**Scope:** the name exists only for the one statement attached to `WITH`. Running another `SELECT * FROM department_stats;` afterward does not reuse it. Use one `WITH`, separate definitions with commas, and end the complete statement with a semicolon. In SQL Server, `;WITH` safely terminates a preceding statement. [SQLite WITH](https://www.sqlite.org/lang_with.html), [SQL Server CTE syntax](https://learn.microsoft.com/en-us/sql/t-sql/queries/with-common-table-expression-transact-sql)

A CTE can also feed an `INSERT`, `UPDATE` or `DELETE`; it is not limited to a final `SELECT`. The definition still belongs to that one attached statement.

An optional column list renames outputs by position:

```sql
WITH department_stats(dept, avg_pay) AS (
    SELECT department, AVG(1.0 * salary)
    FROM employees
    GROUP BY department
)
SELECT dept, ROUND(avg_pay, 2) AS avg_pay
FROM department_stats
ORDER BY dept;
```

The rows are unchanged. Two output columns require two names. CTE names and column aliases label results; they do not create stored tables or change the source data.

## 2. Dependent and independent steps

### A dependent step uses an earlier result

Task: find employees paid more than their own department's average. The summary has one row per department; the comparison needs individual employees again.

```sql
WITH department_stats AS (
    SELECT department, AVG(1.0 * salary) AS average_salary
    FROM employees
    GROUP BY department
), above_average AS (
    SELECT e.employee_id, e.first_name, e.salary, d.average_salary
    FROM employees AS e
    JOIN department_stats AS d ON d.department = e.department
    WHERE e.salary > d.average_salary
)
SELECT employee_id, first_name, salary,
       ROUND(average_salary, 2) AS department_average
FROM above_average
ORDER BY employee_id;
```

| employee_id | first_name | salary | department_average |
|---|---|---:|---:|
| 2 | Emily | 90000 | 73333.33 |

Before filtering, the join produces five employee rows: each employee matches exactly one department summary. Emily exceeds 73333.33; Sophia and Ethan do not. Michael and Daniel each equal their single-person department average, so strict `>` excludes them.

`above_average` depends on `department_stats`, so define the summary first. Compare the unrounded average and round only the displayed value. Early rounding can change whether a near-boundary salary qualifies.

A CTE may also be referenced more than once within its statement. For example, one reference can list department averages while another supplies the greatest average. Repeated references do **not** promise that the database caches one stored result. CTEs primarily organize SQL; inspect the execution plan before making performance claims. [Microsoft CTE usage guidelines](https://learn.microsoft.com/en-us/sql/t-sql/queries/with-common-table-expression-transact-sql#usage-guidelines)

### Independent steps calculate separate facts

Our small attendance fixture has users `1, 2, 3`, with registrations `(10,1), (10,2), (20,2)`. One registration row means one user joined one contest; assume the pair is unique.

```sql
WITH total_users AS (
    SELECT COUNT(*) AS user_count FROM users
), contest_counts AS (
    SELECT contest_id, COUNT(*) AS attendee_count
    FROM registrations
    GROUP BY contest_id
)
SELECT c.contest_id, c.attendee_count, t.user_count,
       ROUND(100.0 * c.attendee_count / NULLIF(t.user_count, 0), 2)
           AS percentage
FROM contest_counts AS c
CROSS JOIN total_users AS t
ORDER BY c.contest_id;
```

| contest_id | attendee_count | user_count | percentage |
|---|---:|---:|---:|
| 10 | 2 | 3 | 66.67 |
| 20 | 1 | 3 | 33.33 |

Neither CTE uses the other. `total_users` produces exactly one row, so the cross join attaches that one denominator to each contest. Two contest rows multiplied by one total row still gives two rows. If both sides had several rows, a cross join would multiply them.

`100.0` prevents integer division. `NULLIF(x, 0)` returns NULL when `x` is zero, avoiding a zero divisor. Whether an undefined percentage should remain NULL or become zero depends on the question.

## 3. Row meaning, populations and denominators

Before coding a CTE, complete this sentence: **“One row of this result represents ...”**

| Intermediate result | One row represents | Typical key |
|---|---|---|
| employees | An employee | employee_id |
| department_stats | A department | department |
| first_orders | A customer's first order | customer_id, assuming a unique first order |
| contest_counts | A contest | contest_id |
| normalized_calls | One call with a consistent pair of people | A call identifier if supplied |

A group changes row meaning; a join can multiply rows. A clear name helps, but the SQL must actually produce the intended key.

**Choose the population before calculating a rate.** Suppose a teaching table records query observations:

| query_name | position | result |
|---|---:|---|
| dog | 1 | good |
| dog | 2 | bad |
| cat | 1 | good |
| cat | 1 | bad |

Task: among position-1 observations, what percentage are good?

```sql
WITH first_position AS (
    SELECT query_name, result
    FROM query_observations
    WHERE position = 1
)
SELECT query_name,
       ROUND(100.0 * SUM(CASE WHEN result = 'good' THEN 1 ELSE 0 END)
             / COUNT(*), 2) AS good_percentage
FROM first_position
GROUP BY query_name
ORDER BY query_name;
```

| query_name | good_percentage |
|---|---:|
| cat | 50.00 |
| dog | 100.00 |

The denominator is the number of position-1 observations for each query. Dog's position-2 row is outside that population. Do not filter `result = 'good'` before counting the denominator: doing so would remove failures and make every remaining group's rate 100%.

The same habit applies to first-order delivery rates: identify **each customer's first order**, then evaluate whether those orders were immediate. If two of four first orders qualify, use `2/4`, even when the full delivery table has seven rows. Decide how tied earliest orders should behave from the problem's guarantees; joining only on an earliest date can return several orders if ties are possible.

A CTE can also normalize repeated roles before aggregation. For a call between people 9 and 2, produce `(person1, person2) = (2,9)`; the reverse call becomes the same pair. For country-level call participation, one call has two participants, so preserve both contributions. State the unit being counted before choosing `UNION` or `UNION ALL`.

## 4. Preserve required rows and repeated events

**Missing events do not always mean missing output rows.** Start from the complete required population and attach events using `LEFT JOIN`.

Small fixture: users `1,2,3`; confirmation events `(1,'confirmed'), (1,'timeout'), (2,'timeout')`.

```sql
WITH confirmation_stats AS (
    SELECT user_id,
           COUNT(*) AS attempts,
           SUM(CASE WHEN action = 'confirmed' THEN 1 ELSE 0 END)
               AS confirmed
    FROM confirmations
    GROUP BY user_id
)
SELECT u.user_id,
       COALESCE(ROUND(1.0 * c.confirmed / c.attempts, 2), 0) AS rate
FROM users AS u
LEFT JOIN confirmation_stats AS c ON c.user_id = u.user_id
ORDER BY u.user_id;
```

| user_id | rate |
|---|---:|
| 1 | 0.50 |
| 2 | 0.00 |
| 3 | 0.00 |

User 3 has no statistics row. The left join keeps the user; the problem's zero-rate rule justifies `COALESCE`. Existing event groups have at least one row, so their attempt counts are positive.

Two related patterns:

- **All required combinations:** cross join students and subjects to build one row per required pair, then left join examinations. Two students and three subjects require six pairs even if some have no exam. Count a non-NULL matched exam column, not `COUNT(*)`, which counts the placeholder row too.
- **Aggregate both sides before joining:** joining several orders directly to several payments per customer can multiply both totals. Summarize orders to one row per customer and payments to one row per customer first when those separate totals are the requirement.

Keep legitimate repeated events. `DISTINCT` is not a general repair for a wrong join: it can erase real repeated calls, attempts, or examinations.

## 5. Recursive CTEs

Ordinary CTEs refer to tables or earlier steps. A recursive CTE also refers to its **own previous results**, making it useful for a manager hierarchy.

Four pieces explain the process:

1. **Anchor:** start with root employees whose manager is NULL.
2. **Recursive member:** find employees managed by the current rows.
3. **UNION ALL:** keep the anchor and newly discovered rows together.
4. **Termination:** stop when an iteration produces no new rows.

```sql
-- SQLite; use the employee fixture above
WITH RECURSIVE reports(employee_id, manager_id, level) AS (
    SELECT employee_id, manager_id, 1
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT e.employee_id, e.manager_id, r.level + 1
    FROM employees AS e
    JOIN reports AS r ON e.manager_id = r.employee_id
)
SELECT r.level, e.first_name AS employee, m.first_name AS manager
FROM reports AS r
JOIN employees AS e ON e.employee_id = r.employee_id
LEFT JOIN employees AS m ON m.employee_id = r.manager_id
ORDER BY r.level, r.employee_id;
```

| level | employee | manager |
|---:|---|---|
| 1 | Michael | NULL |
| 2 | Emily | Michael |
| 2 | Daniel | Michael |
| 3 | Sophia | Emily |
| 3 | Ethan | Emily |

The anchor contributes Michael. He leads to Emily and Daniel; Emily leads to Sophia and Ethan. Neither Sophia nor Ethan has a report, so the next iteration is empty. The final joins add names after traversal; the left join preserves the root with no manager.

**SQL Server adaptation:** use the same query with `WITH reports...` instead of `WITH RECURSIVE reports...`, and replace the final semicolon with:

```sqlserver
OPTION (MAXRECURSION 100);
```

Anchor and recursive columns must have matching counts and compatible corresponding types; SQL Server requires matching types. This example keeps IDs unchanged and uses integer levels. When constructing text paths, explicitly size/cast text consistently. SQL Server's default recursion limit is 100; `0` removes the limit and does not fix a cycle. A limit error is not a successful complete traversal. [Microsoft recursive CTE rules](https://learn.microsoft.com/en-us/sql/t-sql/queries/with-common-table-expression-transact-sql#guidelines-for-recursive-common-table-expressions), [MAXRECURSION](https://learn.microsoft.com/en-us/sql/t-sql/queries/hints-transact-sql-query#maxrecursion-integer_value)

This example assumes a finite, acyclic hierarchy. Starting from roots returns only root-reachable employees; orphaned rows or a disconnected cycle without a root are not discovered. A more general graph may need explicit cycle detection.

Adding `WHERE r.level < 2` to the recursive member deliberately returns only Michael, Emily and Daniel. That is a depth-limited answer, not the whole hierarchy. Replacing `UNION ALL` with `UNION` is not universal cycle prevention: rows with changing levels or paths remain different. SQLite also prohibits aggregates and window functions in the recursive member; summarize after traversal. [SQLite recursion rules](https://www.sqlite.org/lang_with.html#recursive_common_table_expressions)

## 6. CTEs, derived tables, views and temporary tables

| Choice | Main purpose | Lifetime/storage idea |
|---|---|---|
| Derived table: `FROM (SELECT ...) AS d` | One embedded intermediate result | Within its statement |
| CTE: `WITH d AS (...)` | Name and organize steps; support recursion | Within its statement; no automatic storage promise |
| View | Reuse a named query definition | Stored database object; ordinary views do not store their result rows |
| Temporary table | Store intermediate rows for later statements | Actual table; lifetime depends on engine/session rules |

Choose the simplest form that makes the task clear. Splitting a query into CTEs does not automatically make it faster. Temporary tables can be appropriate for repeated work across statements, but introduce creation, population and cleanup decisions.

## 7. Debugging and revision sheet

To inspect a CTE, temporarily replace the final consumer with `SELECT * FROM its_name`. Run the entire `WITH ... SELECT ...` statement. Check the intermediate key, number of rows, and denominator before adding another stage.

| If you see this | Check this first |
|---|---|
| CTE name not found | Did you start a separate statement? |
| Syntax error between CTEs | Use commas, not another WITH or a semicolon |
| Missing zero-count entities | Start with the complete population and left join |
| Inflated totals | Did the join create multiple matches per intended row? |
| Every percentage is 100 | Were failures removed before building the denominator? |
| Percentage is zero unexpectedly | Use decimal arithmetic before division |
| Recursive output never finishes | Check cycles, join direction and stopping conditions |
| Results appear sorted by accident | Put required ORDER BY in the final query |

Five questions before submitting: **What is one row? What is its key? Which population is counted? Can a join multiply it? What happens for missing matches or empty input?**
