# Joins - Quick Revision Notes

**Main idea:** choose a join by which rows must survive, then check how many matching rows each source row can create.

Follow the same Customers and Orders example through the core joins. Small related examples cover employee roles, whole keys, date ranges, and total multiplication. Run the optional setup at the end to try the queries in SQLite.

## 1. Start with the relationship and the row you need

A join puts related information from different table rows beside each other. Before choosing a join, state what one result row should represent: one customer, one order, or one order line.

Our main example has four customers and four orders. An order belongs to at most one customer here; a customer may have many orders. Order 104 is unassigned, so its customer_id is NULL.

```sql
SELECT customer_id, customer_name
FROM Customers
ORDER BY customer_id;
```

**Result:**

| customer_id | customer_name |
| --- | --- |
| 1 | Ada |
| 2 | Ben |
| 3 | Cara |
| 4 | Dev |


```sql
SELECT order_id, customer_id, amount, status, order_date
FROM Orders
ORDER BY order_id;
```

**Result:**

| order_id | customer_id | amount | status | order_date |
| --- | --- | --- | --- | --- |
| 101 | 1 | 30 | paid | 2026-01-05 |
| 102 | 1 | 20 | pending | 2026-01-20 |
| 103 | 2 | 40 | paid | 2026-01-12 |
| 104 | NULL | 10 | paid | 2026-02-01 |


Read `C.customer_id = O.customer_id` as: **match this customer to orders containing this customer's ID**. It does not compare row positions. Ada matches two orders, so she appears twice in an order-level joined result.

| Relationship | Matches for one left row | Effect |
| --- | --- | --- |
| One-to-one | At most one right row | No multiplication from the right |
| One-to-many | Several right rows possible | Left values repeat for each match |
| Many-to-many | Several matches on both sides | Potentially many combinations |

A unique right-side join key prevents more than one match per left row. A foreign key alone does not make the referencing column unique. NULL does not equal NULL under an ordinary `=` join condition.

Use aliases for roles and qualify shared column names. Prefer an explicit `ON` condition over `NATURAL JOIN`: adding a same-named column can otherwise change the match. SQLite supports `USING`, but explicit `ON` also works in SQL Server.

## 2. INNER JOIN: return matching pairs

Use `INNER JOIN`, or simply `JOIN`, when rows must have a match on both sides.

```sql
SELECT C.customer_name, O.order_id, O.amount
FROM Customers AS C
JOIN Orders AS O
    ON C.customer_id = O.customer_id
ORDER BY C.customer_id, O.order_id;
```

**Result:**

| customer_name | order_id | amount |
| --- | --- | --- |
| Ada | 101 | 30 |
| Ada | 102 | 20 |
| Ben | 103 | 40 |


Ada appears once for order 101 and again for order 102. Cara and Dev have no orders. Order 104 has no matching customer. Those unmatched rows are absent.

The join has not calculated a total. The result grain is one matched order. If you want one row per customer, decide whether you need aggregation or only an existence check.

**Common mistake:** joining on `C.customer_id <> O.customer_id` creates pairs with different IDs; it does not find customers without an order.

## 3. LEFT JOIN: keep every row from the left

The left table is the one before `LEFT JOIN`. Keep Customers on the left when every customer must appear.

```sql
SELECT C.customer_name, O.order_id, O.amount
FROM Customers AS C
LEFT JOIN Orders AS O
    ON C.customer_id = O.customer_id
ORDER BY C.customer_id, O.order_id;
```

**Result:**

| customer_name | order_id | amount |
| --- | --- | --- |
| Ada | 101 | 30 |
| Ada | 102 | 20 |
| Ben | 103 | 40 |
| Cara | NULL | NULL |
| Dev | NULL | NULL |


For Cara and Dev, SQL supplies NULL in the right-side columns because no order matched. Ada still has two rows: keeping every customer does not mean producing exactly one row per customer.

Counting after this join shows why `COUNT(*)` and `COUNT(column)` differ:

```sql
SELECT C.customer_name,
       COUNT(*) AS joined_rows,
       COUNT(O.order_id) AS order_count
FROM Customers AS C
LEFT JOIN Orders AS O
    ON C.customer_id = O.customer_id
GROUP BY C.customer_id, C.customer_name
ORDER BY C.customer_id;
```

**Result:**

| customer_name | joined_rows | order_count |
| --- | --- | --- |
| Ada | 2 | 2 |
| Ben | 1 | 1 |
| Cara | 1 | 0 |
| Dev | 1 | 0 |


`COUNT(*)` counts the supplied unmatched row. `COUNT(O.order_id)` ignores its NULL, giving zero orders. Choose a right-side column guaranteed non-NULL in real rows, such as its primary key.

For totals, `SUM(O.amount)` returns NULL when the group has no non-NULL amounts. Use `COALESCE(SUM(O.amount), 0)` when the required business meaning is zero.

## 4. RIGHT and FULL JOIN: preserve the other side or both

A `RIGHT JOIN` preserves Orders here:

```sql
SELECT C.customer_name, O.order_id
FROM Customers AS C
RIGHT JOIN Orders AS O
    ON C.customer_id = O.customer_id
ORDER BY O.order_id;
```

**Result:**

| customer_name | order_id |
| --- | --- |
| Ada | 101 |
| Ada | 102 |
| Ben | 103 |
| NULL | 104 |


Order 104 survives with a NULL customer name. The same preservation can be written as `Orders AS O LEFT JOIN Customers AS C ON O.customer_id = C.customer_id`, which also works on older SQLite platforms.

A `FULL OUTER JOIN` keeps matched pairs and unmatched rows from either side:

```sql
SELECT C.customer_name, O.order_id
FROM Customers AS C
FULL OUTER JOIN Orders AS O
    ON C.customer_id = O.customer_id
ORDER BY CASE WHEN C.customer_id IS NULL THEN 1 ELSE 0 END,
         C.customer_id, O.order_id;
```

**Result:**

| customer_name | order_id |
| --- | --- |
| Ada | 101 |
| Ada | 102 |
| Ben | 103 |
| Cara | NULL |
| Dev | NULL |
| NULL | 104 |


SQLite added RIGHT and FULL OUTER JOIN in **3.39.0**. Older interview environments can reject them even when the logic is correct. SQL Server supports both. Check the platform version before using them. [SQLite 3.39 release notes](https://www.sqlite.org/releaselog/3_39_0.html), [SQL Server joins](https://learn.microsoft.com/en-us/sql/relational-databases/performance/joins?view=sql-server-ver17).

For older SQLite, combine a left join with **only the unmatched rows from the other direction**:

```sql
SELECT customer_id, customer_name, order_id
FROM (
    SELECT C.customer_id, C.customer_name, O.order_id
    FROM Customers AS C
    LEFT JOIN Orders AS O ON C.customer_id = O.customer_id

    UNION ALL

    SELECT C.customer_id, C.customer_name, O.order_id
    FROM Orders AS O
    LEFT JOIN Customers AS C ON C.customer_id = O.customer_id
    WHERE C.customer_id IS NULL
) AS combined_rows
ORDER BY CASE WHEN customer_id IS NULL THEN 1 ELSE 0 END,
         customer_id, order_id;
```

**Result:**

| customer_id | customer_name | order_id |
| --- | --- | --- |
| 1 | Ada | 101 |
| 1 | Ada | 102 |
| 2 | Ben | 103 |
| 3 | Cara | NULL |
| 4 | Dev | NULL |
| NULL | NULL | 104 |


The first part already includes all matched pairs. The second part contributes order 104 only. `UNION ALL` preserves legitimate repeated rows; plain `UNION` can remove equal projected rows that represent different matches. The outer SELECT makes the final ordering explicit.

## 5. ON versus WHERE: match first, then filter

Suppose the request is **every customer, with their paid orders if any**. Put the right-table restriction inside `ON`:

```sql
SELECT C.customer_name, O.order_id
FROM Customers AS C
LEFT JOIN Orders AS O
    ON C.customer_id = O.customer_id
   AND O.status = 'paid'
ORDER BY C.customer_id, O.order_id;
```

**Result:**

| customer_name | order_id |
| --- | --- |
| Ada | 101 |
| Ben | 103 |
| Cara | NULL |
| Dev | NULL |


Only paid orders qualify as matches, but Cara and Dev are still preserved.

Move that condition into `WHERE`, and the requirement changes to **rows whose joined order is paid**:

```sql
SELECT C.customer_name, O.order_id
FROM Customers AS C
LEFT JOIN Orders AS O
    ON C.customer_id = O.customer_id
WHERE O.status = 'paid'
ORDER BY C.customer_id, O.order_id;
```

**Result:**

| customer_name | order_id |
| --- | --- |
| Ada | 101 |
| Ben | 103 |


For Cara and Dev, `O.status = 'paid'` evaluates to unknown because status is NULL. WHERE keeps only true conditions, so their rows disappear.

| Clause | Question it answers |
| --- | --- |
| ON | Which right rows match this left row? |
| WHERE | Which resulting rows should remain? |

For an inner join, moving an ordinary condition between ON and WHERE often gives the same rows. For an outer join, the location can change which unmatched rows survive. [SQLite SELECT processing](https://www.sqlite.org/lang_select.html).

A left-table restriction in ON also does not remove preserved left rows: `AND C.customer_id <= 2` there merely prevents other customers from matching. Put that restriction in WHERE if those customers should be excluded entirely.

## 6. EXISTS and NOT EXISTS: ask whether a match exists

If you need **customers who have any order**, you do not need the order columns or one row per order. EXISTS keeps each qualifying customer row once:

```sql
SELECT C.customer_id, C.customer_name
FROM Customers AS C
WHERE EXISTS (
    SELECT 1
    FROM Orders AS O
    WHERE O.customer_id = C.customer_id
)
ORDER BY C.customer_id;
```

**Result:**

| customer_id | customer_name |
| --- | --- |
| 1 | Ada |
| 2 | Ben |


This is often called a **semi join**. The `SELECT 1` value is not returned; EXISTS tests whether the subquery produces a row. Ada having two orders does not duplicate her outer row.

For **customers with no order**, use NOT EXISTS:

```sql
SELECT C.customer_id, C.customer_name
FROM Customers AS C
WHERE NOT EXISTS (
    SELECT 1
    FROM Orders AS O
    WHERE O.customer_id = C.customer_id
)
ORDER BY C.customer_id;
```

**Result:**

| customer_id | customer_name |
| --- | --- |
| 3 | Cara |
| 4 | Dev |


This is an **anti join**. The familiar LEFT JOIN pattern gives the same result here:

```sql
SELECT C.customer_id, C.customer_name
FROM Customers AS C
LEFT JOIN Orders AS O ON C.customer_id = O.customer_id
WHERE O.order_id IS NULL
ORDER BY C.customer_id;
```

**Result:**

| customer_id | customer_name |
| --- | --- |
| 3 | Cara |
| 4 | Dev |


Test the matched table's non-NULL key. Testing a nullable descriptive field can mistake a real match with missing data for no match.

Avoid `customer_id NOT IN (SELECT customer_id FROM Orders)` in this example: the subquery contains NULL from order 104, so missing-customer comparisons become unknown. NOT EXISTS directly expresses the intended absence test.

## 7. CROSS JOIN and self joins

**CROSS JOIN** deliberately creates every combination. For two customers and two channels, there are 2 × 2 = 4 rows:

```sql
SELECT C.customer_name, H.channel
FROM Customers AS C
CROSS JOIN Channels AS H
WHERE C.customer_id <= 2
ORDER BY C.customer_id, H.channel;
```

**Result:**

| customer_name | channel |
| --- | --- |
| Ada | Online |
| Ada | Store |
| Ben | Online |
| Ben | Store |


Use this for combinations such as each product with every reporting date. An accidentally missing join condition can create this same multiplication when it was not intended.

A **self join** reads one table under two aliases. The aliases express different roles; it is not a separate join keyword. Our employee rows are:

| employee_id | employee_name | manager_id |
| --- | --- | --- |
| 1 | Asha | NULL |
| 2 | Ben | 1 |
| 3 | Cara | 1 |
| 4 | Dara | 2 |

```sql
SELECT E.employee_name, M.employee_name AS manager_name
FROM Employees AS E
LEFT JOIN Employees AS M
    ON E.manager_id = M.employee_id
ORDER BY E.employee_id;
```

**Result:**

| employee_name | manager_name |
| --- | --- |
| Asha | NULL |
| Ben | Asha |
| Cara | Asha |
| Dara | Ben |


`E` is the employee; `M` is the manager. Match the employee's manager_id to the manager row's employee_id. LEFT JOIN keeps Asha, who has no manager. An inner join would omit her. A self join is useful for one relationship level; repeated hierarchy traversal is a separate recursive-CTE topic.

## 8. Match the whole key, or the correct range

**Multiple-column key:** an order line is identified by both order_id and line_number. Line 1 can exist in many orders.

| order_id | line_number | item_name | line_amount | matching note |
| --- | --- | --- | --- | --- |
| 101 | 1 | Pen | 10 | Gift |
| 101 | 2 | Mug | 20 | Fragile |
| 103 | 1 | Book | 40 | Express |

```sql
SELECT L.order_id, L.line_number, L.item_name, N.note
FROM OrderLines AS L
JOIN LineNotes AS N
    ON L.order_id = N.order_id
   AND L.line_number = N.line_number
ORDER BY L.order_id, L.line_number;
```

**Result:**

| order_id | line_number | item_name | note |
| --- | --- | --- | --- |
| 101 | 1 | Pen | Gift |
| 101 | 2 | Mug | Fragile |
| 103 | 1 | Book | Express |


Joining only on order_id would pair each of order 101's two lines with both of its notes, producing four rows for that order. Adding both conditions gives exactly one correct note per line.

**Range join:** a customer's tier can change over time. Match the customer and the period containing the order date.

| customer_id | start_date | end_date | tier |
| --- | --- | --- | --- |
| 1 | 2026-01-01 | 2026-01-14 | Bronze |
| 1 | 2026-01-15 | 2026-01-31 | Silver |
| 2 | 2026-01-01 | 2026-01-31 | Gold |

```sql
SELECT O.order_id, O.order_date, T.tier
FROM Orders AS O
LEFT JOIN CustomerTiers AS T
    ON O.customer_id = T.customer_id
   AND O.order_date >= T.start_date
   AND O.order_date <= T.end_date
ORDER BY O.order_id;
```

**Result:**

| order_id | order_date | tier |
| --- | --- | --- |
| 101 | 2026-01-05 | Bronze |
| 102 | 2026-01-20 | Silver |
| 103 | 2026-01-12 | Gold |
| 104 | 2026-02-01 | NULL |


Ada's January 5 order uses Bronze; her January 20 order uses Silver. Order 104 has no matching tier and remains because this is a left join.

These are date-only ISO strings, so chronological comparison works in SQLite. SQL Server applications can store them as DATE. Both endpoints are inclusive here, matching the supplied periods. For timestamp periods, a half-open interval `event_time >= start_time AND event_time < next_start_time` often avoids end-of-day ambiguity.

The sample tier periods do not overlap for a customer. If they overlap, an order can match multiple tiers. A join cannot decide which overlapping record is correct unless the requirement supplies a rule.

## 9. Avoid multiplying totals when joining two child tables

Order 101 has two lines worth 10 and 20, and two payments worth 10 and 20. Joining both child tables directly on order_id creates 2 × 2 rows:

```sql
SELECT L.line_number, L.line_amount, P.payment_id, P.paid_amount
FROM OrderLines AS L
JOIN Payments AS P ON L.order_id = P.order_id
WHERE L.order_id = 101
ORDER BY L.line_number, P.payment_id;
```

**Result:**

| line_number | line_amount | payment_id | paid_amount |
| --- | --- | --- | --- |
| 1 | 10 | 1 | 10 |
| 1 | 10 | 2 | 20 |
| 2 | 20 | 1 | 10 |
| 2 | 20 | 2 | 20 |


The true line total is 30 and the true payment total is 30. Summing either amount over these four joined rows gives 60, because each original amount appears twice.

When the required output is **one row per order**, first reduce each child table to that grain:

```sql
WITH line_totals AS (
    SELECT order_id, SUM(line_amount) AS line_total
    FROM OrderLines
    GROUP BY order_id
),
payment_totals AS (
    SELECT order_id, SUM(paid_amount) AS paid_total
    FROM Payments
    GROUP BY order_id
)
SELECT O.order_id,
       COALESCE(L.line_total, 0) AS line_total,
       COALESCE(P.paid_total, 0) AS paid_total
FROM Orders AS O
LEFT JOIN line_totals AS L ON O.order_id = L.order_id
LEFT JOIN payment_totals AS P ON O.order_id = P.order_id
ORDER BY O.order_id;
```

**Result:**

| order_id | line_total | paid_total |
| --- | --- | --- |
| 101 | 30 | 30 |
| 102 | 0 | 0 |
| 103 | 40 | 40 |
| 104 | 0 | 0 |


Each CTE now has at most one row per order_id. The outer joins cannot multiply an order by several lines or payments. COALESCE displays zero for absent child totals. This example uses the child records to calculate totals; the Orders.amount column is a separate stored order value.

Do not repair multiplication with `SUM(DISTINCT amount)`: two legitimate lines or payments can have the same amount and must both count. DISTINCT works on values, not on the business identity of a line or payment.

Before aggregating, inspect a few raw joined rows. Count how many times one known source row appears. That makes an incorrect join visible before totals hide it.

## 10. Quick revision and choosing the join

| Need | Typical pattern | Check carefully |
| --- | --- | --- |
| Matching rows and columns from both tables | INNER JOIN | Are all required keys included? |
| Every left row, optional right details | LEFT JOIN | Does WHERE remove the unmatched rows? |
| Every right row | RIGHT JOIN, or reverse to LEFT JOIN | Platform support and table direction |
| Unmatched rows from both sides too | FULL OUTER JOIN | Older SQLite fallback |
| Every combination | CROSS JOIN | Is the row count intentionally left × right? |
| Employee and manager | Self join using aliases | Correct role for each ID |
| Left rows that have a match | EXISTS | No need to multiply by all matches |
| Left rows without a match | NOT EXISTS / LEFT JOIN + key IS NULL | Nullable-key traps |
| Date-dependent match | Key + range conditions | Boundaries and overlapping ranges |
| Totals from several child tables | Aggregate each child before joining | One row per required key |

**Before running:** identify each table's grain, choose which side must survive, write the complete match, and predict the number of matches for one sample row.

**Before accepting:** check no matches, multiple matches, NULL keys, duplicate values, and different entities sharing a name. Group by identity when names are not guaranteed unique. Add ORDER BY only as required, using deterministic tie-breakers when needed.

JOIN builds columns from related rows; UNION ALL stacks compatible rows vertically. They solve different shapes of problem. See [Advanced SELECT](../1.%20Intro%20to%20SQL%20and%20Advanced%20Select/0.%20Foundation%20Notes.md) for set operators, [Aggregation](../4.%20Aggregation/0.%20Foundation%20Notes.md) for totals, and [CTEs](../5.%20CTEs/0.%20Foundation%20Notes.md) for named intermediate results.

The examples use explicit ON conditions and grouping columns compatible with SQLite and SQL Server. RIGHT/FULL require SQLite 3.39.0 or later; the shown UNION ALL fallback works on older SQLite. No SQL Server execution is claimed.

    status VARCHAR(10) NOT NULL,
