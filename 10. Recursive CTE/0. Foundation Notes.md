# Recursive CTE — Quick Revision Notes

**Main idea:** start with known rows, repeatedly build the next rows, and stop when a round produces none.

Read a recursive CTE as **start → repeat → stop → select**. The examples below use SQLite first; SQL Server syntax is shown where it differs.

## 1. The three parts

| Part | Plain meaning | In the example below |
|---|---|---|
| Anchor | Starting row or rows | Begin with `1` |
| Recursive member | Make the next row from a previous row | Add `1` to `n` |
| Stop condition | Prevent the member from producing more rows | Generate a next row only while `n < 5` |

`UNION ALL` combines the starting rows with all rows generated by the recursive member. The final `SELECT` reads the completed CTE.

## 2. Count from 1 to 5

### SQLite query

```sql
WITH RECURSIVE numbers(n) AS (
    SELECT 1

    UNION ALL

    SELECT n + 1
    FROM numbers
    WHERE n < 5
)
SELECT n
FROM numbers
ORDER BY n;
```

| Round | Row read by the recursive member | New row produced | Why |
|---:|---:|---:|---|
| Anchor | — | 1 | `SELECT 1` starts the CTE |
| 1 | 1 | 2 | `1 < 5` |
| 2 | 2 | 3 | `2 < 5` |
| 3 | 3 | 4 | `3 < 5` |
| 4 | 4 | 5 | `4 < 5` |
| 5 | 5 | None | `5 < 5` is false |

Final result:

| n |
|---:|
| 1 |
| 2 |
| 3 |
| 4 |
| 5 |

**Read the condition carefully:** `WHERE n < 5` tests the current row before creating `n + 1`. The final `ORDER BY n` controls display order; do not rely on the order in which recursive rows are produced.

### SQL Server version

SQL Server uses `WITH` without the `RECURSIVE` keyword. The anchor, recursive member, and stop condition have the same roles.

```sql
WITH numbers(n) AS (
    SELECT 1

    UNION ALL

    SELECT n + 1
    FROM numbers
    WHERE n < 5
)
SELECT n
FROM numbers
ORDER BY n;
```

## 3. Follow an employee hierarchy

Suppose `Employees` contains these rows:

| employee_id | employee_name | manager_id |
|---:|---|---:|
| 1 | Ada | NULL |
| 2 | Ben | 1 |
| 3 | Cia | 1 |
| 4 | Dev | 2 |
| 5 | Ema | 2 |
| 6 | Fay | 3 |

The goal is to list the people under Ada, including Ada, and show how far each person is from the top.

```sql
WITH RECURSIVE team(employee_id, employee_name, manager_id, depth) AS (
    SELECT employee_id, employee_name, manager_id, 0
    FROM Employees
    WHERE employee_id = 1

    UNION ALL

    SELECT e.employee_id, e.employee_name, e.manager_id, t.depth + 1
    FROM Employees AS e
    JOIN team AS t
        ON e.manager_id = t.employee_id
)
SELECT employee_id, employee_name, manager_id, depth
FROM team
ORDER BY depth, employee_id;
```

| employee_id | employee_name | manager_id | depth |
|---:|---|---:|---:|
| 1 | Ada | NULL | 0 |
| 2 | Ben | 1 | 1 |
| 3 | Cia | 1 | 1 |
| 4 | Dev | 2 | 2 |
| 5 | Ema | 2 | 2 |
| 6 | Fay | 3 | 2 |

Follow the same rows through the rounds:

| Round | Current manager rows | Matching direct reports produced |
|---:|---|---|
| Anchor | — | Ada (depth 0) |
| 1 | Ada | Ben, Cia (depth 1) |
| 2 | Ben, Cia | Dev, Ema, Fay (depth 2) |
| 3 | Dev, Ema, Fay | None, so recursion stops |

The anchor chooses the starting employee. The join `e.manager_id = t.employee_id` finds employees reporting to rows already in `team`. The hierarchy ends when no current team member has another direct report.

For SQL Server, use the same query with `WITH team(...)` instead of `WITH RECURSIVE team(...)`.

## 4. SQLite and SQL Server syntax

| Need | SQLite | SQL Server |
|---|---|---|
| Start a recursive CTE | `WITH RECURSIVE name(...) AS (...)` | `WITH name(...) AS (...)` |
| Combine anchor and recursive rows | `UNION ALL` | `UNION ALL` |
| Read the generated rows | Final `SELECT` from the CTE | Final `SELECT` from the CTE |
| Sort the final answer | Outer `ORDER BY` | Outer `ORDER BY` |

The recursive member must eventually stop producing rows. A numeric boundary, a hierarchy with no further children, or an explicit visited-row rule can provide that stopping behavior. Check for cycles when following relationships that may point back to earlier rows.

## 5. Quick revision checklist

1. State what one generated row represents.
2. Choose the anchor rows.
3. Write how one round finds the next rows.
4. Identify exactly why the rounds stop.
5. Check duplicate rows and possible cycles.
6. Trace two or three rounds with a small example.
7. Apply final filtering and `ORDER BY` in the outer query.

**Remember:** `ORDER BY` in the final query arranges the answer. The recursive join decides which rows are generated.
