## My solution — SQLite

```sql
SELECT user_id, name, mail
FROM Users
WHERE mail REGEXP '^[a-zA-Z][a-zA-Z0-9_.-]*@bosscoderacademy[.]com$';
```

**Execution requirement:** SQLite recognizes the `REGEXP` operator but does not define a `regexp()` function by default. This saved solution requires the runner or an extension to supply it. Use case-sensitive matching; the behavior of anchors also depends on that implementation. The walkthrough assumes beginning/end anchors apply to the whole email, without multiline matching. [SQLite documentation](https://www.sqlite.org/lang_expr.html#the_like_glob_regexp_match_and_extract_operators)

### Step-by-step explanation with one example

**1. Define the result and inspect the supplied Users table**

Return `user_id`, `name`, and `mail` for each user whose email follows the stated rules. Each input row is checked separately, so no grouping or aggregation is required. The result may be in any order.

Use these same input rows throughout:

| user_id | name | mail |
|---|---|---|
| 1 | Winston | winston@bosscoderacademy.com |
| 2 | Jonathan | jonathanisgreat |
| 3 | Annabelle | bella-@bosscoderacademy.com |
| 4 | Sally | sally.come@bosscoderacademy.com |
| 5 | Marwan | quarz#2020@bosscoderacademy.com |
| 6 | David | david69@bosscoderacademy.com |
| 7 | Shapiro | .shapo@bosscoderacademy.com |

For this practice, follow the written domain rule, `@bosscoderacademy.com`. The original prompt and class reference contain a domain mismatch; they remain preserved in their own sections.

**2. Require the first character to be a letter**

The pattern begins with:

```regex
^[a-zA-Z]
```

`^` anchors the match at the beginning. `[a-zA-Z]` consumes exactly one uppercase or lowercase ASCII letter. There are no comma separators inside the brackets: a comma placed there would itself become an allowed character.

Inspect only this first condition:

```sql
SELECT user_id, name
FROM Users
WHERE mail REGEXP '^[a-zA-Z]'
ORDER BY user_id;
```

| user_id | name |
|---|---|
| 1 | Winston |
| 2 | Jonathan |
| 3 | Annabelle |
| 4 | Sally |
| 5 | Marwan |
| 6 | David |

Shapiro is excluded because his email starts with a period. Jonathan and Marwan still pass this partial check because their first characters are letters; later parts of the pattern must check the remaining requirements.

**3. Permit the allowed remaining prefix characters, then require @**

The prefix portion becomes:

```regex
^[a-zA-Z][a-zA-Z0-9_.-]*@
```

The first character class still requires one letter. The second class permits letters, digits, underscore, period, or dash. The dash is last so it is treated as a literal dash; a period inside this class is literal as well.

The `*` applies only to the second character class. It means zero or more allowed characters after the required first letter.

| Prefix from the same example | Required first letter | Remaining characters |
|---|---|---|
| winston | w | inston |
| bella- | b | ella- |
| sally.come | s | ally.come |
| david69 | d | avid69 |

For example, `bella-` needs five characters after its first letter, and `david69` needs six. Without `*`, the second class would match only one character, making the two classes together require exactly two prefix characters. Zero repetitions also permits a one-letter prefix; it does not permit an empty prefix because the first letter is mandatory.

Require `@` immediately after the allowed prefix:

```sql
SELECT user_id, name
FROM Users
WHERE mail REGEXP '^[a-zA-Z][a-zA-Z0-9_.-]*@'
ORDER BY user_id;
```

| user_id | name |
|---|---|
| 1 | Winston |
| 3 | Annabelle |
| 4 | Sally |
| 6 | David |

Jonathan is now excluded because there is no `@`. Marwan is excluded because `#` is not an allowed prefix character: the repeating class cannot consume it, and `@` does not occur at that position. Shapiro still fails the first-letter requirement.

All four remaining sample emails have acceptable prefixes. This partial pattern still needs the exact domain and an end anchor.

**4. Require the literal domain and the end of the email**

The final domain portion is:

```regex
@bosscoderacademy[.]com$
```

`[.]` matches an actual period. A plain `.` outside brackets is a wildcard, so it would also allow a different character in that position. The end anchor `$` makes the domain the final part of the email under the stated whole-string matching behavior.

The complete pattern can be read as:

| Pattern part | Meaning |
|---|---|
| `^` | Start at the beginning |
| `[a-zA-Z]` | Require one initial letter |
| `[a-zA-Z0-9_.-]*` | Allow zero or more permitted prefix characters |
| `@bosscoderacademy` | Require this exact domain name after @ |
| `[.]` | Require a literal period |
| `com` | Require the literal suffix com |
| `$` | End the match at the end of the email |

Case-sensitive matching still allows uppercase letters in the prefix because both letter ranges are explicitly present. It keeps the fixed domain literal case-sensitive.

All four rows from the previous step remain: each has the required domain.

**5. Assemble the final query**

`WHERE` applies the complete pattern to each `mail`, and `SELECT` returns the three requested columns for matching users:

```sql
SELECT user_id, name, mail
FROM Users
WHERE mail REGEXP '^[a-zA-Z][a-zA-Z0-9_.-]*@bosscoderacademy[.]com$';
```

| user_id | name | mail |
|---|---|---|
| 1 | Winston | winston@bosscoderacademy.com |
| 3 | Annabelle | bella-@bosscoderacademy.com |
| 4 | Sally | sally.come@bosscoderacademy.com |
| 6 | David | david69@bosscoderacademy.com |

The table is displayed in ID order for readability; the final query does not promise an order, and the prompt does not require one.

## My solution — SQL Server

**SQL Server 2025 (17.x) or newer; database compatibility level 170 or higher**

```sql
SELECT user_id, name, mail
FROM Users
WHERE REGEXP_LIKE(
    mail,
    '^[a-zA-Z][a-zA-Z0-9_.-]*@bosscoderacademy[.]com$',
    'c'
);
```

This retains the user's exact regular expression and filtering logic. SQL Server uses `REGEXP_LIKE(mail, pattern, 'c')` directly as the `WHERE` predicate. The `'c'` flag explicitly requests case-sensitive matching, and no multiline flag is enabled.

Native `REGEXP_LIKE` requires compatibility level 170 or higher and is unavailable in SQL Server 2022 and earlier. This version-labelled adaptation therefore targets SQL Server 2025 or newer rather than assuming all SQL Server installations provide regex support. [Microsoft REGEXP_LIKE documentation](https://learn.microsoft.com/en-us/sql/t-sql/functions/regexp-like-transact-sql?view=sql-server-ver17)
