# 9. SQL Patients With Condition

## Question and image

**3. Sql Patients With Condition**

Table: Patients

| Column Name | Type |
|---|---|
| patient_id | int |
| patient_name | varchar |
| conditions | varchar |

patient_id is the primary key (column with unique values) for this table.

'conditions' contains 0 or more code separated by spaces.

This table contains information of the patients in the hospital.

Write a solution to find the patient_id, patient_name, and conditions of the patients who have Type I Diabetes. Type I Diabetes always starts with DIAB1 prefix.

Return the result table ordered by patient_id in ascending order.

**Output:**

**Explanation:**

Bob and George both have a condition that starts with DIAB1.

## My solution — SQLite

### Solution 1 — GLOB

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions GLOB 'DIAB1*'
   OR conditions GLOB '* DIAB1*'
ORDER BY patient_id ASC;
```

This version uses SQLite's case-sensitive `GLOB` matching for the uppercase prefix `DIAB1`. Its `*` wildcard matches zero or more characters. The two patterns cover a code at the beginning of the string and a code immediately after a space. [SQLite pattern-matching documentation](https://www.sqlite.org/lang_expr.html#the_like_glob_regexp_match_and_extract_operators)

### Step-by-step explanation with one example

**1. Define the output and read the input rows**

Return `patient_id`, `patient_name`, and `conditions` for each qualifying patient, ordered by `patient_id` ascending. One result row represents one patient; no grouping or counting is needed.

Use the supplied `Patients` data throughout:

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
ORDER BY patient_id ASC;
```

| patient_id | patient_name | conditions |
|---|---|---|
| 1 | Daniel | YFEV COUGH |
| 2 | Alice | |
| 3 | Bob | DIAB100 MYOP |
| 4 | George | ACNE DIAB100 |
| 5 | Alain | DIAB201 |

Alice's empty cell represents an empty string. Bob's matching code appears first; George's matching code appears after another code and a space.

**2. Match a condition code at the beginning**

`GLOB 'DIAB1*'` requires the string to begin with the exact uppercase characters `DIAB1`. The final `*` allows the rest of that code and any later text.

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions GLOB 'DIAB1*'
ORDER BY patient_id ASC;
```

| patient_id | patient_name | conditions |
|---|---|---|
| 3 | Bob | DIAB100 MYOP |

Bob matches because `DIAB100 MYOP` begins with `DIAB1`. George does not match this pattern because his complete string begins with `ACNE`.

**3. Match a condition code after a space**

`GLOB '* DIAB1*'` allows earlier text, then requires a literal space immediately followed by `DIAB1`, and finally allows the remaining text.

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions GLOB '* DIAB1*'
ORDER BY patient_id ASC;
```

| patient_id | patient_name | conditions |
|---|---|---|
| 4 | George | ACNE DIAB100 |

George's `ACNE DIAB100` contains a space followed by `DIAB1`, so he matches. The space matters because the question describes separate condition codes. A match inside an unrelated code such as `XDIAB100` would not identify a code beginning with `DIAB1`.

**4. Combine the two allowed positions with OR**

A patient's matching code may occur at either position. `OR` keeps the patient when at least one complete condition is true.

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions GLOB 'DIAB1*'
   OR conditions GLOB '* DIAB1*';
```

| patient_id | patient_name | conditions |
|---|---|---|
| 3 | Bob | DIAB100 MYOP |
| 4 | George | ACNE DIAB100 |

The two qualifying rows are Bob and George. The order shown here illustrates the rows returned; this intermediate query does not specify their order.

Even if a patient has matching codes in both positions, that patient appears once. `WHERE` filters each original row; it does not produce a separate output row for every matching code.

**5. Add the required ordering and assemble the final query**

The assignment requires ascending `patient_id`. Add `ORDER BY patient_id ASC` after the complete filter:

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions GLOB 'DIAB1*'
   OR conditions GLOB '* DIAB1*'
ORDER BY patient_id ASC;
```

| patient_id | patient_name | conditions |
|---|---|---|
| 3 | Bob | DIAB100 MYOP |
| 4 | George | ACNE DIAB100 |

ID 3 comes before ID 4. Sorting determines the order of qualifying rows; it does not change which patients match.

**6. Check the same example manually**

| patient_id | patient_name | Reason | Include? |
|---|---|---|---|
| 1 | Daniel | Neither code begins with DIAB1. | No |
| 2 | Alice | There are no condition codes. | No |
| 3 | Bob | DIAB100 begins with DIAB1 and is the first code. | Yes |
| 4 | George | DIAB100 begins with DIAB1 and follows a space. | Yes |
| 5 | Alain | DIAB201 begins with DIAB2. | No |

The final output contains exactly Bob and George in ascending ID order. The returned `conditions` values stay unchanged.

Case handling is part of this version's behavior: `GLOB` distinguishes `DIAB1` from `diab1`. SQLite's default `LIKE` does not distinguish ASCII letter case. Empty strings and NULL conditions do not pass either pattern. The delimiter being tested is the literal space specified by the question.

### Solution 2 — LIKE

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions LIKE 'DIAB1%'
   OR conditions LIKE '% DIAB1%'
ORDER BY patient_id ASC;
```

This is the original `LIKE` approach. It keeps the same two code-start positions and ascending patient-ID order. SQLite's default `LIKE` ignores ASCII letter case, so both `DIAB100` and `diab100` match this version. The `GLOB` version above requires the exact uppercase prefix. [SQLite pattern-matching documentation](https://www.sqlite.org/lang_expr.html#the_like_glob_regexp_match_and_extract_operators)

#### Walkthrough using the same example

Use the same five `Patients` rows shown in step 1 above.

**1. Find a matching code at the beginning.**

`LIKE 'DIAB1%'` matches a value beginning with `DIAB1`. The final `%` accepts zero or more remaining characters.

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions LIKE 'DIAB1%'
ORDER BY patient_id ASC;
```

| patient_id | patient_name | conditions |
|---|---|---|
| 3 | Bob | DIAB100 MYOP |

Bob matches because his first code begins with `DIAB1`. George's complete value starts with `ACNE`, so this first condition does not select him.

**2. Find a matching code after a space.**

`LIKE '% DIAB1%'` allows earlier text, requires a literal space before `DIAB1`, and then allows the remaining text.

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions LIKE '% DIAB1%'
ORDER BY patient_id ASC;
```

| patient_id | patient_name | conditions |
|---|---|---|
| 4 | George | ACNE DIAB100 |

George matches because `DIAB100` follows a space. Keeping that space prevents a match inside an unrelated code such as `XDIAB100`.

**3. Combine both conditions and sort the qualifying patients.**

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions LIKE 'DIAB1%'
   OR conditions LIKE '% DIAB1%'
ORDER BY patient_id ASC;
```

| patient_id | patient_name | conditions |
|---|---|---|
| 3 | Bob | DIAB100 MYOP |
| 4 | George | ACNE DIAB100 |

`OR` keeps a patient when either position matches. A patient matching both conditions still appears once. `ORDER BY patient_id ASC` puts Bob's ID 3 before George's ID 4.

The sample's manual check is unchanged: Daniel has no matching code, Alice has no codes, and Alain's code begins with `DIAB2`. Both saved approaches return Bob and George for these sample rows; the approaches differ when prefix letters have lowercase or mixed-case spelling.

## My solution — SQL Server

### Equivalent of Solution 1 — GLOB

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions COLLATE Latin1_General_100_BIN2 LIKE 'DIAB1%'
   OR conditions COLLATE Latin1_General_100_BIN2 LIKE '% DIAB1%'
ORDER BY patient_id ASC;
```

SQL Server uses `LIKE` here, with `%` replacing SQLite's `GLOB` wildcard `*`. The two code-start positions and ascending ID order are preserved.

`COLLATE Latin1_General_100_BIN2` applies binary comparison rules to each condition check, preserving the case-sensitive uppercase-prefix behavior of the SQLite version regardless of a case-insensitive database default. It applies to these expressions; it does not change the column or database definition. [Microsoft COLLATE documentation](https://learn.microsoft.com/en-us/sql/t-sql/statements/collations?view=sql-server-ver17), [Microsoft binary collation documentation](https://learn.microsoft.com/en-us/sql/relational-databases/collations/collation-and-unicode-support?view=sql-server-ver17)

### Equivalent of Solution 2 — LIKE

```sql
SELECT patient_id, patient_name, conditions
FROM Patients
WHERE conditions COLLATE Latin1_General_100_CI_AS LIKE 'DIAB1%'
   OR conditions COLLATE Latin1_General_100_CI_AS LIKE '% DIAB1%'
ORDER BY patient_id ASC;
```

For the ASCII condition codes used here, `Latin1_General_100_CI_AS` preserves SQLite's usual case-insensitive `LIKE` behavior. For example, `DIAB100` and `diab100` both match. Applying the collation to each expression makes that behavior independent of a case-sensitive database default. The patterns and result ordering are unchanged. [Microsoft collation documentation](https://learn.microsoft.com/en-us/sql/relational-databases/collations/collation-and-unicode-support?view=sql-server-ver17)
