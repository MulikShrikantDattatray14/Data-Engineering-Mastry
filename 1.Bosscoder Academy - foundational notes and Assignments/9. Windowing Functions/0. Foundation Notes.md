# Windowing Functions - Quick Revision Notes

**Main idea:** calculate something across related rows while keeping each row visible.

Read in this order: **keep rows -> choose a partition -> choose an order -> choose a frame -> calculate -> filter**.

The examples reuse the sales and scores from your slides. They use SQLite and also work in SQL Server unless labelled otherwise. Run the optional setup at the end if you want to try them.

## 1. Window functions versus GROUP BY

Use this small `Sales` table throughout the sales examples. For these examples, `id` gives the sale sequence.

| id | customer | amount |
|---|---|---|
| 1 | A | 100 |
| 2 | B | 200 |
| 3 | A | 300 |
| 4 | B | 400 |
| 5 | A | 500 |

### GROUP BY: one result row per customer

```sql
SELECT customer, SUM(amount) AS customer_total
FROM Sales
GROUP BY customer
ORDER BY customer;
```

| customer | customer_total |
|---|---|
| A | 900 |
| B | 600 |

The five sales become two customer summaries.

### Window function: keep each sale and attach the customer total

```sql
SELECT id, customer, amount,
       SUM(amount) OVER (PARTITION BY customer) AS customer_total
FROM Sales
ORDER BY customer, id;
```

| id | customer | amount | customer_total |
|---|---|---|---|
| 1 | A | 100 | 900 |
| 3 | A | 300 | 900 |
| 5 | A | 500 | 900 |
| 2 | B | 200 | 600 |
| 4 | B | 400 | 600 |

For every A row, SQL calculates `100 + 300 + 500 = 900`. For every B row, it calculates `200 + 400 = 600`.

**Choose by the output:** one summary per customer -> `GROUP BY`; each sale plus a summary -> window function.

## 2. Read OVER in three parts

General shape; the bracketed parts are placeholders, not literal SQL:

```text
function(...) OVER (
    [PARTITION BY group_columns]
    [ORDER BY sequence_columns]
    [frame]
)
```

| Part | Question it answers | Sales example |
|---|---|---|
| Function | What do I calculate? | SUM(amount) |
| PARTITION BY | Which rows belong together? | One partition per customer |
| ORDER BY inside OVER | In what sequence? | Earlier sale id first |
| Frame | Which rows around this row contribute? | First sale through this sale |

A **partition** is the full group. A **frame** is the portion used for a particular row's calculation. They are not additional stored tables.

| Expression | Meaning |
|---|---|
| `SUM(amount) OVER ()` | Total of all five sales: 1500 on every row |
| `SUM(amount) OVER (PARTITION BY customer)` | Whole customer total: A = 900, B = 600 |
| `SUM(amount) OVER (ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` | Running total across all customers, in id order: 100, 300, 600, 1000, 1500 |
| `SUM(amount) OVER (PARTITION BY customer ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` | Customer's total so far |

### Calculate all four expressions using the same sales

All four expressions **keep the same five sales rows**. What changes is **which amounts contribute to the sum for each row**.

We will use this same `Sales` table throughout:

| id | customer | amount |
|---:|:---:|---:|
| 1 | A | 100 |
| 2 | B | 200 |
| 3 | A | 300 |
| 4 | B | 400 |
| 5 | A | 500 |

#### 1. SUM(amount) OVER () - total of all rows

The empty `OVER ()` means all five rows belong to one window. There is no customer grouping or running sequence.

The overall total is:

```text
100 + 200 + 300 + 400 + 500 = 1500
```

Every sale gets that same overall total:

| id | amount | Overall total |
|---:|---:|---:|
| 1 | 100 | 1500 |
| 2 | 200 | 1500 |
| 3 | 300 | 1500 |
| 4 | 400 | 1500 |
| 5 | 500 | 1500 |

Even the first row shows **1500**, because this expression includes **all five sales**, including later ones.

#### 2. SUM(amount) OVER (PARTITION BY customer) - total for each customer

`PARTITION BY customer` separates the rows into two groups. Each row receives the total of its **entire customer group**.

| Customer | Included sale IDs | Calculation | Customer total |
|:---:|:---:|---|---:|
| A | 1, 3, 5 | `100 + 300 + 500` | 900 |
| B | 2, 4 | `200 + 400` | 600 |

Attach those totals to the original rows:

| id | customer | amount | Customer total |
|---:|:---:|---:|---:|
| 1 | A | 100 | 900 |
| 2 | B | 200 | 600 |
| 3 | A | 300 | 900 |
| 4 | B | 400 | 600 |
| 5 | A | 500 | 900 |

At **id 1**, A already shows **900**, because the calculation includes A's sales at IDs **1, 3 and 5**.

#### 3. Overall running total - add amounts in id order

```sql
SUM(amount) OVER (
    ORDER BY id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

This is the window expression to use in a SELECT list. Read its parts:

| Part | Meaning |
|---|---|
| No `PARTITION BY` | All customers participate together |
| `ORDER BY id` | Use the sequence 1, 2, 3, 4, 5 |
| `UNBOUNDED PRECEDING` | Start from the first row |
| `CURRENT ROW` | Stop at the row being calculated |

The included rows grow as we move forward:

| Current id | customer | Included sale IDs | Calculation | Overall running total |
|---:|:---:|---|---|---:|
| 1 | A | 1 | `100` | 100 |
| 2 | B | 1, 2 | `100 + 200` | 300 |
| 3 | A | 1, 2, 3 | `100 + 200 + 300` | 600 |
| 4 | B | 1, 2, 3, 4 | `100 + 200 + 300 + 400` | 1000 |
| 5 | A | 1, 2, 3, 4, 5 | `100 + 200 + 300 + 400 + 500` | 1500 |

At **id 3**, the total is **600**. It includes both A's and B's earlier sales.

Future rows are excluded: amounts **400 and 500** have not entered that row's calculation.

#### 4. Customer running total - add amounts separately for each customer

```sql
SUM(amount) OVER (
    PARTITION BY customer
    ORDER BY id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

This expression combines both ideas:

- **Partition:** include only the current customer's rows.
- **Order and frame:** include that customer's first sale through their current sale.

| Current id | customer | Included sale IDs | Calculation | Customer running total |
|---:|:---:|---|---|---:|
| 1 | A | 1 | `100` | 100 |
| 2 | B | 2 | `200` | 200 |
| 3 | A | 1, 3 | `100 + 300` | 400 |
| 4 | B | 2, 4 | `200 + 400` | 600 |
| 5 | A | 1, 3, 5 | `100 + 300 + 500` | 900 |

Think of **two separate running totals**:

```text
Customer A: 100 -> 400 -> 900
Customer B: 200 -> 600
```

When A appears again at **id 3**, A's total continues from **100**. It does not reset because a B row appeared between A's sales. Rows for the same partition need not sit next to each other in the original input.

#### All four results together

The four calculated columns below follow the same order as the four expressions in the comparison above:

| id | customer | amount | Overall total | Customer total | Overall running total | Customer running total |
|---:|:---:|---:|---:|---:|---:|---:|
| 1 | A | 100 | 1500 | 900 | 100 | 100 |
| 2 | B | 200 | 1500 | 600 | 300 | 200 |
| 3 | A | 300 | 1500 | 900 | 600 | 400 |
| 4 | B | 400 | 1500 | 600 | 1000 | 600 |
| 5 | A | 500 | 1500 | 900 | 1500 | 900 |

**Two ORDER BY clauses have different jobs:** the one inside `OVER` controls the calculation; the final `ORDER BY` controls the displayed result. Keep the final one when the question requires a sorted answer. [OVER documentation](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-over-clause-transact-sql?view=sql-server-ver17)

## 3. Aggregate window functions

**Each function calculates a different summary for the same customer group, while keeping every individual sale visible.** We will understand the shared `OVER` clause first, then calculate each result separately.

### Start with the same Sales data

| id | customer | amount |
|---:|:---:|---:|
| 1 | A | 100 |
| 2 | B | 200 |
| 3 | A | 300 |
| 4 | B | 400 |
| 5 | A | 500 |

There are five input rows. This query also returns five rows, adding summary columns beside each sale.

### First understand OVER (PARTITION BY customer)

Every function below uses the same clause: `OVER (PARTITION BY customer)`.

| Part | What it tells SQL |
|---|---|
| Function, such as SUM or AVG | Which calculation to perform |
| OVER (...) | Calculate across related rows while keeping the detail rows |
| PARTITION BY customer | Calculate separately for each customer |

SQL logically separates the rows into these two partitions:

| Customer | Included sale IDs | Amounts available to each function |
|:---:|:---:|---|
| A | 1, 3, 5 | 100, 300, 500 |
| B | 2, 4 | 200, 400 |

For an A row, each function uses A's three sales. For a B row, each function uses B's two sales. A's and B's amounts never mix in these calculations.

There is **no ORDER BY inside OVER**, so these aggregate expressions use the **whole customer partition**. They are not running calculations. Even A's first row includes A's later sales when calculating its summaries.

All rows belonging to one customer receive the same set of summary values. The rows need not be adjacent in the original input for SQL to recognize their partition.

### 1. SUM - calculate the total amount

Expression: `SUM(amount) OVER (PARTITION BY customer) AS total_amount`

SUM adds all the amounts belonging to the current customer.

| Customer | Calculation | total_amount | Rows receiving this value |
|:---:|---|---:|---|
| A | `100 + 300 + 500 = 900` | 900 | IDs 1, 3, 5 |
| B | `200 + 400 = 600` | 600 | IDs 2, 4 |

For example, sale 1 has an individual amount of 100, but its `total_amount` is 900 because that column describes all of A's sales.

### 2. AVG - calculate the average sale amount

Expression: `AVG(1.0 * amount) OVER (PARTITION BY customer) AS avg_amount`

AVG adds the known amounts and divides by how many known amounts there are. All amounts in our example are non-NULL, so the calculation is:

| Customer | Total amount | Number of amounts | Calculation | avg_amount |
|:---:|---:|---:|---|---:|
| A | 900 | 3 | `(100 + 300 + 500) / 3 = 900 / 3 = 300` | 300 |
| B | 600 | 2 | `(200 + 400) / 2 = 600 / 2 = 300` | 300 |

A and B happen to have the same average, even though their totals and numbers of sales differ. Each A row and each B row therefore shows 300 in `avg_amount`.

**Why multiply by 1.0?** It makes the input a decimal expression so fractional averages are preserved in SQL Server. AVG of an integer expression returns an integer there; SQLite already returns a floating-point average. This example's exact average is 300, so a client may display 300 or 300.0. [SQL Server AVG](https://learn.microsoft.com/en-us/sql/t-sql/functions/avg-transact-sql?view=sql-server-ver17)

### 3. COUNT(*) - count the sales rows

Expression: `COUNT(*) OVER (PARTITION BY customer) AS sale_count`

Each row in Sales represents one sale. COUNT(*) counts those rows; it does not add the amounts or the sale IDs.

| Customer | Included sale IDs | Calculation: one count per row | sale_count |
|:---:|:---:|---|---:|
| A | 1, 3, 5 | `1 + 1 + 1 = 3` | 3 |
| B | 2, 4 | `1 + 1 = 2` | 2 |

Every A row receives 3; every B row receives 2.

### 4. MIN - find the smallest sale amount

Expression: `MIN(amount) OVER (PARTITION BY customer) AS smallest`

MIN compares the amounts within the customer's partition and returns the lowest value.

| Customer | Amounts compared | Smallest value | Rows receiving this value |
|:---:|---|---:|---|
| A | 100, 300, 500 | 100 | IDs 1, 3, 5 |
| B | 200, 400 | 200 | IDs 2, 4 |

For A's sale of 500, `smallest` is still 100. It describes the smallest sale in A's whole partition, not the current row's amount.

### 5. MAX - find the largest sale amount

Expression: `MAX(amount) OVER (PARTITION BY customer) AS largest`

MAX compares the same amounts and returns the highest value.

| Customer | Amounts compared | Largest value | Rows receiving this value |
|:---:|---|---:|---|
| A | 100, 300, 500 | 500 | IDs 1, 3, 5 |
| B | 200, 400 | 400 | IDs 2, 4 |

For A's first sale of 100, `largest` is already 500 because the whole partition includes A's later sale of 500.

### Put the five summaries beside each sale

The calculation changes with the function; the set of participating rows stays the same:

| Function | Question it answers |
|---|---|
| SUM | What is this customer's total amount? |
| AVG | What is this customer's average sale amount? |
| COUNT(*) | How many sales rows does this customer have? |
| MIN | What is this customer's smallest sale amount? |
| MAX | What is this customer's largest sale amount? |

For example, **id 3** is A's sale of 300. Its summary columns describe A's full set of amounts, 100, 300 and 500: total 900, average 300, count 3, smallest 100 and largest 500.

**NULL reminder:** COUNT(*) includes every row, even if its amount is NULL. COUNT(amount) counts only non-NULL amounts. SUM, AVG, MIN and MAX ignore NULL inputs; AVG's denominator counts known amounts rather than all rows. If every amount in a partition is NULL, these four aggregates return NULL, while COUNT(amount) returns 0.

### Complete query and final combined result

`AS` names each output column. The final `ORDER BY customer, id` displays A's rows first, then B's, with IDs ascending within each customer. It does not turn these whole-partition summaries into running calculations.

```sql
SELECT id, customer, amount,
       SUM(amount) OVER (PARTITION BY customer) AS total_amount,
       AVG(1.0 * amount) OVER (PARTITION BY customer) AS avg_amount,
       COUNT(*) OVER (PARTITION BY customer) AS sale_count,
       MIN(amount) OVER (PARTITION BY customer) AS smallest,
       MAX(amount) OVER (PARTITION BY customer) AS largest
FROM Sales
ORDER BY customer, id;
```

| id | customer | amount | total_amount | avg_amount | sale_count | smallest | largest |
|---:|:---:|---:|---:|---:|---:|---:|---:|
| 1 | A | 100 | 900 | 300 | 3 | 100 | 500 |
| 3 | A | 300 | 900 | 300 | 3 | 100 | 500 |
| 5 | A | 500 | 900 | 300 | 3 | 100 | 500 |
| 2 | B | 200 | 600 | 300 | 2 | 200 | 400 |
| 4 | B | 400 | 600 | 300 | 2 | 200 | 400 |

## 4. Running totals and moving averages

### What ORDER BY id does inside OVER

In these examples, `id` gives the sale sequence. `PARTITION BY customer` first makes a separate set of rows for A and B. Then `ORDER BY id` puts the sales **within each customer's partition** in this order:

| Customer | Sales in id order |
|:---:|---|
| A | id 1: 100 -> id 3: 300 -> id 5: 500 |
| B | id 2: 200 -> id 4: 400 |

That order gives meaning to **previous row**, **current row** and **total so far**. For A's id 3 sale, the preceding row is A's id 1 sale. B's id 2 sale is not part of A's partition. When A appears again at id 5, its calculation continues from A's earlier sales.

`ORDER BY id` inside `OVER (...)` controls the **calculation**. The `ORDER BY customer, id` at the end of each query controls only the **display order** of the finished rows. The examples use `id` as a sale sequence; if the question asks for chronological order, order by the relevant date or time and add a tie-breaker when needed.

### Running total: keep adding as you move forward

```sql
SELECT id, customer, amount,
       SUM(amount) OVER (
           PARTITION BY customer
           ORDER BY id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM Sales
ORDER BY customer, id;
```

`UNBOUNDED PRECEDING` starts at the first sale in this customer's `id` order. `CURRENT ROW` stops at the sale being calculated. The frame grows by one customer sale at each step.

| Current sale | Included sale IDs | Calculation | running_total |
|---|---|---|---:|
| A, id 1 | 1 | `100` | 100 |
| A, id 3 | 1, 3 | `100 + 300` | 400 |
| A, id 5 | 1, 3, 5 | `100 + 300 + 500` | 900 |
| B, id 2 | 2 | `200` | 200 |
| B, id 4 | 2, 4 | `200 + 400` | 600 |

The sum restarts for B: at B's id 2 sale it is 200, because A's id 1 sale is in a different partition. Without `PARTITION BY customer`, the running total would continue across all five sales, as shown in the [four-expression comparison](#2-read-over-in-three-parts).

### Moving average: current sale and one previous sale

```sql
SELECT id, customer, amount,
       AVG(1.0 * amount) OVER (
           PARTITION BY customer
           ORDER BY id
           ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
       ) AS moving_avg
FROM Sales
ORDER BY customer, id;
```

`1 PRECEDING` means one **previous row in the same customer's id order**. This frame keeps at most two sales: the current one and that previous one. At a customer's first sale, only the current row exists.

| Current sale | Included sale IDs | Calculation | moving_avg |
|---|---|---|---:|
| A, id 1 | 1 | `100 / 1` | 100 |
| A, id 3 | 1, 3 | `(100 + 300) / 2` | 200 |
| A, id 5 | 3, 5 | `(300 + 500) / 2` | 400 |
| B, id 2 | 2 | `200 / 1` | 200 |
| B, id 4 | 2, 4 | `(200 + 400) / 2` | 300 |

At A's id 5 sale, id 3 is the preceding **A** row; id 1 has moved outside the two-row frame. B's id 4 sale is never included in A's average.

### Both calculations together

The queries above each select one result. Putting their two expressions in the same SELECT gives these values for the same five rows:

| id | customer | amount | running_total | moving_avg |
|---:|:---:|---:|---:|---:|
| 1 | A | 100 | 100 | 100 |
| 3 | A | 300 | 400 | 200 |
| 5 | A | 500 | 900 | 400 |
| 2 | B | 200 | 200 | 200 |
| 4 | B | 400 | 600 | 300 |

### Frame words to remember

| Frame | Meaning |
|---|---|
| `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | First row through current row |
| `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` | Current row plus up to two earlier rows |
| `ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING` | Previous, current and next rows, where available |
| `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` | Whole partition, even with window ordering |

**ROWS counts rows, not days.** Seven daily totals represent seven days only when there is one row per day and no dates are missing. If several purchases occur on the same date, aggregate by date first. Decide whether an incomplete initial window should be included.

### ROWS versus the default RANGE: ties matter

**Remember this difference:** `ROWS` adds **one person at a time**. The default `RANGE` adds **everyone tied at the current score together**.

Our `Scores` data is:

| score_id | name | score |
|---:|---|---:|
| 1 | Bob | 95 |
| 2 | Charlie | 95 |
| 3 | Alice | 90 |
| 4 | David | 85 |
| 5 | Emma | 80 |

`ORDER BY score DESC` starts with the highest score: **95, 95, 90, 85, 80**. Bob and Charlie both have 95. They are a **tie** on `score`.

#### Watch what happens at the tie

| Current person | ROWS: add people one at a time | Default RANGE: add tied scores together |
|---|---|---|
| Bob (95) | Bob's `95` = **95** | Bob's `95` + Charlie's `95` = **190** |
| Charlie (95) | Bob's `95` + Charlie's `95` = **190** | Same tied group: `95 + 95` = **190** |
| Alice (90) | `95 + 95 + 90` = **280** | Both 95s, then 90: `95 + 95 + 90` = **280** |

Bob is the clearest difference. `ROWS` can stop after Bob's single row, giving **95**. The default `RANGE` stops after the whole **95-score group**, so Bob already sees Charlie's 95 and gets **190**. At Charlie the ROWS calculation catches up, and both give 190. David and Emma have no ties, so both calculations continue to 365 and then 445.

Why is RANGE the **default** here? For an aggregate such as `SUM(score)` with `ORDER BY` inside `OVER` and no written frame, SQLite and SQL Server use `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. In this example, it includes all higher-score groups plus **all rows tied at the current score**. RANGE here is about tied ordering values; it does not mean scores within a numeric distance such as five points. [SQLite frames](https://www.sqlite.org/windowfunctions.html#frame_specifications), [SQL Server frames](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-over-clause-transact-sql?view=sql-server-ver17)

To get the one-person-at-a-time result, write an explicit ROWS frame. Add `score_id` after `score DESC` to decide which 95 comes first: Bob (`score_id = 1`), then Charlie (`score_id = 2`). Without this second ordering column, either tied person could receive 95 first. Keep only `score` in the RANGE expression: adding the unique `score_id` there would make Bob and Charlie different ordering values, so they would no longer tie for that calculation.

```sql
SELECT name, score,
       SUM(score) OVER (ORDER BY score DESC) AS default_total,
       SUM(score) OVER (
           ORDER BY score DESC, score_id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS row_total
FROM Scores
ORDER BY score DESC, score_id;
```

The `ORDER BY` **inside each OVER** controls that calculation. The final `ORDER BY score DESC, score_id` only displays the finished rows in a predictable order.

| name | score | default_total: RANGE | row_total: ROWS |
|---|---:|---:|---:|
| Bob | 95 | 190 | 95 |
| Charlie | 95 | 190 | 190 |
| Alice | 90 | 280 | 280 |
| David | 85 | 365 | 365 |
| Emma | 80 | 445 | 445 |

## 5. ROW_NUMBER, RANK and DENSE_RANK

Using the same five scores:

```sql
SELECT name, score,
       ROW_NUMBER() OVER (ORDER BY score DESC, score_id) AS row_num,
       RANK() OVER (ORDER BY score DESC) AS score_rank,
       DENSE_RANK() OVER (ORDER BY score DESC) AS dense_rank
FROM Scores
ORDER BY score DESC, score_id;
```

| name | score | row_num | score_rank | dense_rank |
|---|---|---|---|---|
| Bob | 95 | 1 | 1 | 1 |
| Charlie | 95 | 2 | 1 | 1 |
| Alice | 90 | 3 | 3 | 2 |
| David | 85 | 4 | 4 | 3 |
| Emma | 80 | 5 | 5 | 4 |

| Function | Rule | Typical need |
|---|---|---|
| ROW_NUMBER() | A different number for each row | Choose exactly one row using a tie-breaker |
| RANK() | Ties share rank; later ranks have gaps | Competition positions |
| DENSE_RANK() | Ties share rank; no gaps | Second distinct value, top N distinct values |

**Why does only ROW_NUMBER include score_id?** It makes Bob/Charlie numbering predictable. Adding it to `RANK` or `DENSE_RANK` would make their ordering values different and remove the intended score tie.

To restart rankings for each customer, use a partition, for example:

```sql
SELECT customer, id, amount,
       DENSE_RANK() OVER (
           PARTITION BY customer ORDER BY amount DESC
       ) AS amount_rank
FROM Sales
ORDER BY customer, amount DESC, id;
```

A's amounts `500, 300, 100` receive ranks `1, 2, 3`. B's `400, 200` restart at `1, 2`.

## 6. Filter a window result using a CTE

In SQLite and SQL Server, calculate the window value first, then filter it in an outer query.

Example: keep everyone in the top **two distinct score levels**.

```sql
WITH ranked_scores AS (
    SELECT name, score,
           DENSE_RANK() OVER (ORDER BY score DESC) AS score_rank
    FROM Scores
)
SELECT name, score
FROM ranked_scores
WHERE score_rank <= 2
ORDER BY score DESC, name;
```

| name | score |
|---|---|
| Bob | 95 |
| Charlie | 95 |
| Alice | 90 |

The CTE produces all five ranked rows. The outer query keeps ranks 1 and 2, giving three people because the highest score is tied.

**Logical flow:** `FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> window calculations -> final ORDER BY`.

A window sees the rows remaining at its query level after earlier filtering/grouping. Do not place its expression or alias in that same query's `WHERE` or `HAVING`. If another calculation needs a window result, an additional CTE/query level also makes that dependency clear.

## 7. LAG and LEAD

- `LAG`: fetch a value from an earlier row in the partition's order.
- `LEAD`: fetch a value from a later row in that order.

```sql
SELECT id, customer, amount,
       LAG(amount) OVER (
           PARTITION BY customer ORDER BY id
       ) AS previous_amount,
       LEAD(amount) OVER (
           PARTITION BY customer ORDER BY id
       ) AS next_amount
FROM Sales
ORDER BY customer, id;
```

| id | customer | amount | previous_amount | next_amount |
|---|---|---|---|---|
| 1 | A | 100 | NULL | 300 |
| 3 | A | 300 | 100 | 500 |
| 5 | A | 500 | 300 | NULL |
| 2 | B | 200 | NULL | 400 |
| 4 | B | 400 | 200 | NULL |

For A's middle sale, the previous amount is 100 and the next is 500. Neither function crosses from A into B.

### Offset and default

```text
LAG(value, offset, default) OVER (...)
LEAD(value, offset, default) OVER (...)
```

| Expression, ordered by id within A | Results for amounts 100, 300, 500 |
|---|---|
| `LAG(amount)` | NULL, 100, 300 |
| `LAG(amount, 1, 0)` | 0, 100, 300 |
| `LAG(amount, 2, -1)` | -1, -1, 100 |
| `LEAD(amount, 2, -1)` | 500, -1, -1 |

The default offset is 1; the default missing-row result is NULL. The third argument applies when the requested row does not exist, not when an existing row contains NULL. [LAG arguments](https://learn.microsoft.com/en-us/sql/t-sql/functions/lag-transact-sql?view=sql-server-ver17)

A change from the previous sale is `amount - previous_amount`: for A, `NULL, 200, 200`.

**Previous row is not automatically previous day/month.** Order by a real date for chronological comparisons and check date gaps if required. Likewise, adjacent rows do not guarantee consecutive numeric IDs. For `LAG`/`LEAD`, choose the partition, order and offset; the aggregate frame recipes above do not define their offset.

## 8. NTILE and PERCENT_RANK

### NTILE: split ordered rows into buckets

Using the same five scores:

```sql
SELECT name, score,
       NTILE(2) OVER (ORDER BY score DESC, score_id) AS bucket
FROM Scores
ORDER BY score DESC, score_id;
```

| name | score | bucket |
|---|---|---|
| Bob | 95 | 1 |
| Charlie | 95 | 1 |
| Alice | 90 | 1 |
| David | 85 | 2 |
| Emma | 80 | 2 |

Five rows cannot split equally into two buckets, so sizes are **3 and 2**. Earlier buckets receive extra rows. With eight rows and `NTILE(4)`, sizes are `2, 2, 2, 2`; with nine rows, they are `3, 2, 2, 2`.

Buckets balance **row counts**, not value ranges. Equal scores can fall in different buckets. `ORDER BY score DESC` puts higher scores in earlier buckets. [NTILE rules](https://learn.microsoft.com/en-us/sql/t-sql/functions/ntile-transact-sql?view=sql-server-ver17)

### PERCENT_RANK: relative rank from 0 to 1

```sql
SELECT name, score,
       PERCENT_RANK() OVER (ORDER BY score DESC) AS relative_rank
FROM Scores
ORDER BY score DESC, score_id;
```

| name | score | RANK used | relative_rank |
|---|---|---|---|
| Bob | 95 | 1 | 0 |
| Charlie | 95 | 1 | 0 |
| Alice | 90 | 3 | 0.50 |
| David | 85 | 4 | 0.75 |
| Emma | 80 | 5 | 1.00 |

"RANK used" explains the formula; it is not an extra selected column.

For more than one row: `(RANK - 1) / (partition row count - 1)`.
For Alice: `(3 - 1) / (5 - 1) = 0.50`.

A one-row partition returns 0. Multiply by 100 if a percentage is required. With descending score order, the highest scores have relative rank 0; this is not a percentage of marks. [PERCENT_RANK definition](https://www.sqlite.org/windowfunctions.html#built_in_window_functions)

## 9. Quick revision and common mistakes

### Choose the operation

| Requirement | Starting point |
|---|---|
| Collapse rows into one summary per group | GROUP BY |
| Keep rows and show the group total/average | Aggregate OVER (PARTITION BY ...) |
| Total so far | SUM + ORDER BY + explicit running ROWS frame |
| Average of the current and preceding rows | AVG + bounded ROWS frame |
| Exactly one selected row per group | ROW_NUMBER with a complete tie-breaker |
| Top N distinct values, including ties | DENSE_RANK |
| Competition ranks with gaps | RANK |
| Previous/next row's value | LAG / LEAD |
| Roughly equal-sized buckets | NTILE |
| Relative rank | PERCENT_RANK |
| Filter by a calculated window value | CTE/subquery, then outer WHERE |

Before writing SQL, fill in: **"For each ___, ordered by ___, calculate ___ using ___ rows."**

Example: "For each customer, ordered by sale id, calculate the total amount using the first row through the current row."

### Five checks before submitting

1. **Rows:** am I keeping the correct detail level? A join that duplicates rows also changes window calculations.
2. **Partition:** does the calculation restart for the correct entity? Prefer its unique ID when names can repeat.
3. **Order and ties:** is the order complete where needed, and are intended ties preserved?
4. **Frame and boundaries:** whole group or running/moving subset? Rows or dates? Missing neighbour or incomplete window?
5. **Final output:** filter in the right query level and apply the required final ordering.

Do not attach a frame to every function: the aggregate examples use frames; ranking functions such as `RANK` do not need them, and SQL Server disallows frames on ranking functions.

### Small dialect reminders

| Need | SQLite | SQL Server |
|---|---|---|
| Core examples in this guide | Same window syntax | Same window syntax |
| Preserve fractional average of integers | AVG(1.0 * amount) | AVG(1.0 * amount) |
| Add six calendar days | DATE('2020-01-01', '+6 days') | DATEADD(day, 6, CAST('2020-01-01' AS date)) |
| Days between date-only values | JULIANDAY('2020-01-07') - JULIANDAY('2020-01-01') | DATEDIFF(day, '2020-01-01', '2020-01-07') |
| COUNT(DISTINCT value) OVER (...) | Not supported | Not supported |

The date examples return January 7 and 6 days respectively. In SQLite, adding `6` directly to a date string is not calendar arithmetic. Two-argument `DATEDIFF(later, earlier)` in the class handout is MySQL syntax. SQL Server `DATEDIFF(day,...)` counts day boundaries, so do not treat it as elapsed 24-hour periods for timestamps. [SQLite dates](https://www.sqlite.org/lang_datefunc.html), [SQL Server DATEDIFF](https://learn.microsoft.com/en-us/sql/t-sql/functions/datediff-transact-sql?view=sql-server-ver17)
