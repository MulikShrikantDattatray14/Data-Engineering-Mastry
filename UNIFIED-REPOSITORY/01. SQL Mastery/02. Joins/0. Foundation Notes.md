# SQL Joins — Foundation Notes

## Why learn joins?

An e-commerce database stores customers and orders separately to avoid repeating all customer details inside every order. A **join** combines related rows using their shared key.

## 1. Example input

**Customers**

| CustomerID | Name |
|---:|---|
| 1 | Asha |
| 2 | Ravi |
| 3 | Neha |

**Orders**

| OrderID | CustomerID |
|---:|---:|
| 201 | 1 |
| 202 | 1 |
| 203 | 3 |

## 2. INNER JOIN — matching rows only

```sql
SELECT c.CustomerID, c.Name, o.OrderID
FROM Customers c
INNER JOIN Orders o ON c.CustomerID = o.CustomerID
ORDER BY c.CustomerID, o.OrderID;
```

**Output**

| CustomerID | Name | OrderID |
|---:|---|---:|
| 1 | Asha | 201 |
| 1 | Asha | 202 |
| 3 | Neha | 203 |

Asha has **two orders**, so the join creates **two rows**. Joins can multiply rows; they aren't always one customer → one result.

## 3. LEFT JOIN — keep unmatched customers

Change `INNER JOIN` to `LEFT JOIN`.

| CustomerID | Name | OrderID |
|---:|---|---:|
| 1 | Asha | 201 |
| 1 | Asha | 202 |
| 2 | Ravi | NULL |
| 3 | Neha | 203 |

Ravi remains even though no order matches.

## 4. Anti-join — customers with no orders

```sql
SELECT c.CustomerID, c.Name
FROM Customers c
LEFT JOIN Orders o ON c.CustomerID = o.CustomerID
WHERE o.OrderID IS NULL;
```

**Output:** `(2, Ravi)`. Test a **non-null right-side key** for missing matches, not an arbitrary nullable attribute.

## 5. ON vs WHERE is crucial

To attach **only paid orders** while keeping every customer, put the qualifying `status='paid'` condition in the `LEFT JOIN ... ON` clause. Putting `WHERE o.status='paid'` afterwards filters out unmatched customers.

**Step-by-step mental model:** choose left rows → find qualifying right matches → fill missing right columns with NULL → apply final WHERE.

## 6. Types and cautions

- `INNER JOIN`: only matches; `LEFT JOIN`: all left rows plus matches.
- `RIGHT JOIN` and `FULL OUTER JOIN` are also available in supported SQL dialects; SQLite version support varies, so test the actual engine.
- SQL is a multiset language: duplicates and join fan-out affect counts and sums.
- Always identify table **grain** before joining; aggregating after a one-to-many join can double-count.
- Sort explicitly; joins do not guarantee output ordering.

**JS developer connection:** A join resembles building a lookup `Map` keyed by customer ID and attaching matching orders, but SQL can produce multiple rows per key and has NULL semantics.
