# SQL Basics - Quick Revision Notes

**Main idea:** a query turns stored rows into the exact rows and columns you need.

Read in this order: **understand a row -> read columns -> filter -> calculate -> understand query order -> change data carefully**.

Use the optional setup at the end in a fresh scratch database. The examples build on one small product catalogue. SQLite is the practice dialect; shared SQL also works in SQL Server unless a difference is labelled. These are foundation examples, not solutions to the numbered interview questions.

## 1. Tables, rows, columns and keys

A database holds related tables. A table describes one kind of thing; each row is one occurrence, and each column records one attribute. Here **one Products row represents one product**, not one purchase or one supplier.

```sql
SELECT * FROM Products ORDER BY product_id;
```

**Result:**

| product_id | product_name | category | price_cents | stock | supplier_id |
| --- | --- | --- | --- | --- | --- |
| 1 | Pen | Stationery | 200 | 10 | 1 |
| 2 | Notebook | Stationery | 500 | 0 | 1 |
| 3 | Mug | Home | 800 | NULL | 2 |
| 4 | Bottle | Home | 800 | 5 | 2 |
| 5 | Pen | Stationery | 200 | 20 | NULL |


Products 1 and 5 share the name Pen. Their IDs distinguish them: names are not automatically unique. Stock 0 means we know there are none; NULL means the stock value is unknown or absent.

| Term | Meaning | In this example |
|---|---|---|
| Schema | Table structure, types and constraints | Products has six named columns |
| Primary key | Chosen unique, non-NULL row identifier | product_id |
| Candidate key | Any suitable unique, non-NULL identifier | A unique product code could also qualify |
| Composite key | A key made from multiple columns | An order-line table might use order_id + line_number |
| Foreign key | A reference to an eligible key in another table | supplier_id refers to Suppliers |
| Grain | What one row represents | One product |

Keep supplier details in Suppliers and reference its ID, rather than repeating its address in every product row. This reduces conflicting copies when a supplier changes. A join can retrieve the details when needed.

A foreign key does not make supplier_id unique in Products: many products may share one supplier. A nullable foreign key can be NULL. Constraints describe the permitted data; they are not substitutes for reading the question's assumptions.

## 2. Data types and NULL

Choose types based on meaning, not on how a value looks.

| Kind of value | SQLite practice | SQL Server |
|---|---|---|
| Count or identifier | INTEGER / INT | INT or BIGINT |
| Text such as a name or phone code | TEXT / VARCHAR | VARCHAR or NVARCHAR |
| Exact money in this example | Integer cents | Integer cents or DECIMAL(p,s) |
| Approximate measurement | REAL | FLOAT |
| Boolean flag | Integer 0 or 1, usually with CHECK | BIT |
| Date | Usually ISO text such as '2026-01-08' | DATE |
| Timestamp | ISO text or another documented representation | DATETIME2 |

Keep leading-zero codes such as '051' as text. Integer cents make these examples exact: 200 means 2 currency units. Floating-point types can introduce rounding differences.

SQLite normally uses flexible typing: a VARCHAR(40) declaration does not itself enforce a 40-character limit. SQL Server enforces its declared types and lengths. SQLite STRICT tables offer tighter rules, but use supported STRICT type names. [SQLite type differences](https://www.sqlite.org/quirks.html#flexible_typing)

NULL is a marker, not the text 'NULL', an empty string, or the number 0. Ordinary comparisons with NULL usually produce UNKNOWN. WHERE keeps only TRUE results.

```sql
SELECT product_id, product_name, stock
FROM Products
WHERE stock IS NULL
ORDER BY product_id;
```

**Result:**

| product_id | product_name | stock |
| --- | --- | --- |
| 3 | Mug | NULL |


Use IS NULL and IS NOT NULL. Writing stock = NULL does not ask whether stock is missing. Arithmetic with a NULL input generally returns NULL; decide whether replacing it with a default is justified rather than assuming every missing value means zero.

## 3. Read rows with SELECT

Start with the simplest shape: SELECT chooses columns, FROM chooses the table, and WHERE chooses rows.

```sql
SELECT product_id, product_name, stock
FROM Products
WHERE stock > 0
ORDER BY product_id;
```

**Result:**

| product_id | product_name | stock |
| --- | --- | --- |
| 1 | Pen | 10 |
| 4 | Bottle | 5 |
| 5 | Pen | 20 |


Only positive known stock passes. The Mug row is not selected because NULL > 0 is unknown. No data is changed by SELECT. ORDER BY product_id makes the displayed order predictable.

Use clear column lists for final answers. SELECT * is convenient when inspecting a new table, but it returns every column and can change shape when the table changes.

```sql
SELECT product_id, product_name,
       price_cents * 1.0 / 100 AS price
FROM Products
WHERE product_id <= 2
ORDER BY product_id;
```

**Result:**

| product_id | product_name | price |
| --- | --- | --- |
| 1 | Pen | 2 |
| 2 | Notebook | 5 |


AS gives a result column a name; it does not rename the stored column. Multiplication by 1.0 ensures decimal division rather than integer division. The displayed numeric value 2 may be formatted as 2.00 by a client; ROUND controls a numeric value, not necessarily its printed trailing zeros.

SQL keywords are conventionally uppercase, but this is a readability habit. Use single quotes for string literals and a semicolon to finish a statement. Avoid using double quotes as a substitute for string quotes: their standard purpose is quoting identifiers.

## 4. Written order and logical processing order

You write SELECT first, but reason about how rows become the result:

| Logical step | Job | Question to ask |
|---|---|---|
| FROM / JOIN / ON | Build source rows and matches | What does each row now represent? |
| WHERE | Keep qualifying individual rows | Which rows should participate? |
| GROUP BY | Form groups | What is one summary group? |
| HAVING | Keep qualifying groups | Which totals/counts qualify? |
| SELECT | Produce result expressions and aliases | Which columns are required? |
| DISTINCT | Remove duplicate result rows | Duplicate across which selected columns? |
| ORDER BY | Arrange the output | What are the tie-breakers? |
| Row limiting | Keep the requested portion | How many sorted rows? |

This is a logical model, not a promise about the engine's physical execution plan. The optimizer can rearrange work while preserving semantics. [SQL Server logical processing order](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-transact-sql?view=sql-server-ver17)

```sql
SELECT category, COUNT(*) AS product_count
FROM Products
WHERE stock IS NOT NULL
GROUP BY category
HAVING COUNT(*) >= 2
ORDER BY category;
```

**Result:**

| category | product_count |
| --- | --- |
| Stationery | 3 |


Read the example in stages: remove products with missing stock, group the four remaining products by category, then keep categories with at least two products. Stationery has three; Home has one and is removed.

COUNT(*) counts rows, including the Notebook whose stock is 0. This query does not ask for positive stock.

WHERE cannot directly test COUNT(*) because it filters before grouping. HAVING is only needed when groups need filtering. A select alias is normally available in ORDER BY; for portability, repeat an expression in WHERE or calculate it in a subquery. SQLite accepts some aliases in places SQL Server does not.

Window calculations happen after row filtering/grouping within their query level. They keep the rows at that level; filtering a calculated window value usually needs an outer query.

The existing [logical query processing note](<SQL Logical Query Processing Order.md>) gives a longer reference.

## 5. Constraints: let the table enforce rules

The setup uses these rules:

| Constraint | What it protects | Example |
|---|---|---|
| PRIMARY KEY | Identifying each row | product_id |
| NOT NULL | Required value | product_name |
| UNIQUE | No repeated constrained key value | A product_code, if required |
| CHECK | A permitted value condition | stock >= 0 |
| FOREIGN KEY | Valid relationship | supplier exists |
| DEFAULT | Value used when the column is omitted | A scratch quantity starts at 0 |

CHECK(stock >= 0) alone allows NULL because the check is not false. Add NOT NULL if the stock must always be known. A DEFAULT does not automatically replace an explicitly supplied NULL.

UNIQUE and PRIMARY KEY have different roles. UNIQUE constraints' treatment of NULL varies by database, so do not assume they enforce non-NULL values. The setup explicitly uses INT NOT NULL PRIMARY KEY for portability.

In ordinary SQLite tables, some primary-key declarations have historical NULL exceptions; INTEGER PRIMARY KEY has special row-ID behavior. SQL Server generates IDs with an explicit IDENTITY declaration when requested. Do not assume every integer primary key auto-generates values. [SQLite key caveats](https://www.sqlite.org/quirks.html#primary_keys_can_sometimes_contain_nulls)

**SQLite connection setting:** enable foreign-key enforcement before starting a transaction:
```sql
PRAGMA foreign_keys = ON;
```

This is SQLite-only; it must be enabled for each connection as appropriate. [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html#fk_enable)

If a rule rejects a row, investigate its values and the intended rule. Removing a constraint merely to make an insert succeed can admit invalid data.

## 6. Create, insert, update and delete

SQL statement families help you identify the action before running it:

| Family | Common statements | Purpose |
|---|---|---|
| DDL | CREATE, ALTER, DROP | Define/change database objects |
| DML | INSERT, UPDATE, DELETE | Change rows |
| Querying | SELECT | Read a result |
| Transaction control | BEGIN, COMMIT, ROLLBACK | Group changes into a unit |
| Access control | GRANT, REVOKE in SQL Server | Manage permissions; SQLite uses a different access model |

Run the following only in the scratch database. ScratchItems is separate from the Products example.

```sql
CREATE TABLE ScratchItems (
    item_id INT NOT NULL PRIMARY KEY,
    item_name VARCHAR(40) NOT NULL,
    quantity INT NOT NULL DEFAULT 0 CHECK (quantity >= 0)
);
INSERT INTO ScratchItems (item_id, item_name, quantity)
VALUES (1, 'Pen', 3);
UPDATE ScratchItems SET quantity = quantity + 2 WHERE item_id = 1;
ALTER TABLE ScratchItems ADD note VARCHAR(40);

SELECT item_id, item_name, quantity, note FROM ScratchItems;
```

**Result:**

| item_id | item_name | quantity | note |
| --- | --- | --- | --- |
| 1 | Pen | 5 | NULL |


INSERT names its columns so the intended mapping is clear. UPDATE changes only item 1 and computes 3 + 2 = 5. ALTER TABLE adds a column; it does not add another row. These CREATE/INSERT/UPDATE/ADD COLUMN forms are supported in both practice dialects.

Before a real UPDATE or DELETE, run a SELECT with the same WHERE and check the intended rows. Without WHERE, UPDATE or DELETE affects all rows in the table.

```sql
DELETE FROM ScratchItems WHERE item_id = 1;

SELECT COUNT(*) AS remaining_rows FROM ScratchItems;
```

**Result:**

| remaining_rows |
| --- |
| 0 |


DELETE removes selected rows while preserving the table. After the check, this removes the now-empty scratch object:
```sql
DROP TABLE ScratchItems;
```


DROP removes the object itself. SQL Server also offers TRUNCATE TABLE for clearing rows with restrictions; SQLite has no TRUNCATE statement. DELETE, TRUNCATE and DROP are not interchangeable operations.

## 7. Transactions: keep or undo a set of changes

A transaction treats related changes as one unit. COMMIT keeps them; ROLLBACK undoes uncommitted work. For example, transferring stock between two locations should not leave only one side updated.

This small demonstration temporarily changes the Pen stock, inspects it, and then restores it. Run the two blocks in the same connection:

```sql
BEGIN TRANSACTION;
UPDATE Products SET stock = 99 WHERE product_id = 1;

SELECT product_id, stock FROM Products WHERE product_id = 1;
```

**Result:**

| product_id | stock |
| --- | --- |
| 1 | 99 |

```sql
ROLLBACK;

SELECT product_id, stock FROM Products WHERE product_id = 1;
```

**Result:**

| product_id | stock |
| --- | --- |
| 1 | 10 |


The observed stock returns from 99 to 10. BEGIN TRANSACTION, COMMIT and ROLLBACK are available in SQLite and SQL Server for this example.

| ACID idea | Practical meaning |
|---|---|
| Atomicity | Related changes succeed or are undone together |
| Consistency | Enforced rules remain satisfied |
| Isolation | Concurrent work follows the database's isolation rules |
| Durability | Committed work survives according to the database's guarantees |

Isolation does not mean every database uses the same locking or isolation level. Do not infer that an error always rolls back an entire transaction: error behavior depends on the engine and statement.

SQLite BEGIN transactions do not nest; use SAVEPOINT when partial rollback is needed. Without an explicit transaction, SQLite automatically wraps statements as needed. [SQLite transaction rules](https://www.sqlite.org/lang_transaction.html)

Keep transactions short enough for the work they protect. Do not leave an interactive transaction open while you pause to study.

## 8. Views and indexes: two different tools

A regular view is a named query. It can simplify repeated selection logic, but it does not normally hold a separate copy of the rows.

```sql
CREATE VIEW AvailableProducts AS
SELECT product_id, product_name, stock
FROM Products
WHERE stock > 0;
```

```sql
SELECT * FROM AvailableProducts ORDER BY product_id;
```

**Result:**

| product_id | product_name | stock |
| --- | --- | --- |
| 1 | Pen | 10 |
| 4 | Bottle | 5 |
| 5 | Pen | 20 |


Updating the underlying Products data affects what a later query of this view sees. Use ORDER BY when selecting from the view if you need ordering; a view's existence does not guarantee row order. In SQL Server, execute CREATE VIEW as its own batch.

An index is an additional lookup structure that can help the engine locate rows without inspecting the whole table.

```sql
CREATE INDEX idx_products_category ON Products(category);
```


This may help queries that filter by category; the optimizer decides whether to use it. An ordinary index is not a uniqueness rule, does not automatically sort query output, and is not always faster on tiny tables. Indexes consume space and add maintenance work to writes. Learn to inspect a query plan after the query is correct.

A view changes how you name a query. An index changes available access paths. Neither replaces the logic in WHERE, GROUP BY or ORDER BY.

## 9. Quick revision

| Need | Start with |
|---|---|
| Choose result columns | SELECT |
| Keep individual rows | WHERE |
| Find missing values | IS NULL |
| Identify one row | A declared key |
| Enforce valid data | Constraints |
| Summarize rows | GROUP BY + aggregate |
| Filter summaries | HAVING |
| Guarantee result ordering | ORDER BY |
| Undo an uncommitted change | ROLLBACK |
| Reuse a named query | View |
| Help lookups | Index |

Before writing SQL, state: **one input row represents ___; one output row should represent ___.**

Five checks: correct table and columns; duplicate/key assumptions; NULL meaning; row-versus-group filtering; required output order. For writes, additionally confirm the target rows and transaction boundary.

## Optional: create the example tables

Run this once in a fresh scratch database before trying the examples in order. The table definitions and inserts below also work in SQL Server. In SQLite, enable `PRAGMA foreign_keys = ON;` for the connection if you want foreign keys enforced.

```sql
CREATE TABLE Suppliers (
    supplier_id INT NOT NULL PRIMARY KEY,
    supplier_name VARCHAR(40) NOT NULL
);
CREATE TABLE Products (
    product_id INT NOT NULL PRIMARY KEY,
    product_name VARCHAR(40) NOT NULL,
    category VARCHAR(30) NOT NULL,
    price_cents INT NOT NULL CHECK (price_cents >= 0),
    stock INT CHECK (stock >= 0),
    supplier_id INT,
    FOREIGN KEY (supplier_id) REFERENCES Suppliers(supplier_id)
);
INSERT INTO Suppliers VALUES (1, 'Acme'), (2, 'Bright');
INSERT INTO Products VALUES
(1, 'Pen',      'Stationery', 200, 10,   1),
(2, 'Notebook', 'Stationery', 500, 0,    1),
(3, 'Mug',      'Home',       800, NULL, 2),
(4, 'Bottle',   'Home',       800, 5,    2),
(5, 'Pen',      'Stationery', 200, 20,   NULL);
```

*Validation: SQLite examples were executed against the sample data. SQL Server adaptations were reviewed for syntax and behavior; they were not executed on a SQL Server instance.*
