# 12. SQL Weather Observation Stations

## Question and image

**6. Sql Weather Observation Stations**

Query the list of CITY names from STATION that either do not start with vowels or do not end with vowels. Your result cannot contain duplicates.

Input Format

The STATION table is described as follows:

| Field | Type |
|---|---|
| ID | NUMBER |
| CITY | VARCHAR2(21) |
| STATE | VARCHAR2(2) |
| LAT_N | NUMBER |
| LONG_W | NUMBER |

where LAT_N is the northern latitude and LONG_W is the western longitude.

**Output:**

## My solution — SQLite

```sql
SELECT DISTINCT CITY
FROM STATION
WHERE CITY NOT GLOB '[AEIOUaeiou]*'
   OR CITY NOT GLOB '*[AEIOUaeiou]';
```

### Step-by-step explanation with one example

**1. Define the output and read the input**

Return one column, `CITY`, with each qualifying city name once. A city qualifies when its first character is not a vowel OR its last character is not a vowel. Either condition is enough; both may also be true. No result ordering is required.

The same supplied STATION sample is used throughout the main walkthrough:

```sql
SELECT ID, CITY, STATE, LAT_N, LONG_W
FROM STATION;
```

| ID | CITY | STATE | LAT_N | LONG_W |
|---|---|---|---|---|
| 1 | ABC | CA | 10 | 20 |
| 2 | DEF | TX | 15 | 25 |
| 3 | BOSTON | MA | 20 | 30 |
| 4 | CHICAGO | IL | 30 | 40 |
| 5 | AUSTIN | TX | 25 | 35 |

The other columns describe the station, but only CITY is needed for this result. Rows in the tables below are displayed in sample order; the final query does not promise an order.

**2. Check whether the city does not start with a vowel**

`[AEIOUaeiou]` matches one of the listed vowels. Putting it before `*` tests the first character: the `*` can match the rest of the city name. `NOT GLOB` reverses the match.

```sql
SELECT
    CITY,
    CITY GLOB '[AEIOUaeiou]*' AS starts_with_vowel,
    CITY NOT GLOB '[AEIOUaeiou]*' AS not_start_vowel
FROM STATION;
```

| CITY | starts_with_vowel | not_start_vowel |
|---|---|---|
| ABC | 1 | 0 |
| DEF | 0 | 1 |
| BOSTON | 0 | 1 |
| CHICAGO | 0 | 1 |
| AUSTIN | 1 | 0 |

In these inspection columns, 1 means true and 0 means false. ABC and AUSTIN start with A, so their `not_start_vowel` value is 0. DEF, BOSTON, and CHICAGO have a value of 1.

**3. Check whether the city does not end with a vowel**

Putting `*` first allows the preceding characters to vary. The vowel group at the end must match the final character.

```sql
SELECT
    CITY,
    CITY GLOB '*[AEIOUaeiou]' AS ends_with_vowel,
    CITY NOT GLOB '*[AEIOUaeiou]' AS not_end_vowel
FROM STATION;
```

| CITY | ends_with_vowel | not_end_vowel |
|---|---|---|
| ABC | 0 | 1 |
| DEF | 0 | 1 |
| BOSTON | 0 | 1 |
| CHICAGO | 1 | 0 |
| AUSTIN | 0 | 1 |

CHICAGO ends with O, so its `not_end_vowel` value is 0. The other four sample names end with C, F, N, and N, giving a value of 1.

**4. Combine the two checks using OR**

```sql
SELECT
    CITY,
    CITY NOT GLOB '[AEIOUaeiou]*' AS not_start_vowel,
    CITY NOT GLOB '*[AEIOUaeiou]' AS not_end_vowel,
    (CITY NOT GLOB '[AEIOUaeiou]*'
     OR CITY NOT GLOB '*[AEIOUaeiou]') AS keep_city
FROM STATION;
```

| CITY | not_start_vowel | not_end_vowel | keep_city |
|---|---|---|---|
| ABC | 0 | 1 | 1 |
| DEF | 1 | 1 | 1 |
| BOSTON | 1 | 1 | 1 |
| CHICAGO | 1 | 0 | 1 |
| AUSTIN | 0 | 1 | 1 |

Every sample city has at least one true condition. ABC and AUSTIN qualify through their final characters. CHICAGO qualifies through its first character. DEF and BOSTON satisfy both conditions. The question uses OR, so it does not require both conditions to be true.

Apply that decision to filter rows:

```sql
SELECT CITY
FROM STATION
WHERE CITY NOT GLOB '[AEIOUaeiou]*'
   OR CITY NOT GLOB '*[AEIOUaeiou]';
```

| CITY |
|---|
| ABC |
| DEF |
| BOSTON |
| CHICAGO |
| AUSTIN |

All five sample names survive. A name is excluded by this logic when it starts AND ends with a vowel: then both NOT GLOB conditions are false.

**5. Remove duplicate names and assemble the final query**

```sql
SELECT DISTINCT CITY
FROM STATION
WHERE CITY NOT GLOB '[AEIOUaeiou]*'
   OR CITY NOT GLOB '*[AEIOUaeiou]';
```

| CITY |
|---|
| ABC |
| DEF |
| BOSTON |
| CHICAGO |
| AUSTIN |

`DISTINCT CITY` removes repetitions of the selected city name. The sample has no duplicate names, so the five-row output is unchanged. If two stations have the same qualifying CITY, the result still contains that city name once; different station IDs do not prevent name duplicates.

Manual check: all five sample cities meet at least one condition, all names are unique in the sample, and the output contains only CITY. No aggregate, join, GROUP BY, or ORDER BY is needed.

|---|---|---|---|

### GLOB, LIKE, and wildcard concepts

**1. Exact equality and pattern matching answer different questions**

`CITY = 'BOSTON'` compares the complete value with one fixed name. LIKE and GLOB let part of the name vary through wildcard symbols. Their patterns describe the complete string, so wildcard placement determines whether the fixed part must be at the start, end, or anywhere inside.

```sql
SELECT
    'BOSTON' = 'BOS%' AS exact_text,
    'BOSTON' LIKE 'BOS%' AS like_prefix,
    'BOSTON' GLOB 'BOS*' AS glob_prefix;
```

| exact_text | like_prefix | glob_prefix |
|---|---|---|
| 0 | 1 | 1 |

The percent sign is ordinary text for equality. The matching examples have different wildcard symbols because LIKE and GLOB use different pattern rules.

**2. SQLite LIKE versus SQLite GLOB**

| Feature | LIKE in SQLite | GLOB in SQLite |
|---|---|---|
| Zero or more characters | `%` | `*` |
| Exactly one character | `_` | `?` |
| A group such as `[AEIOU]` | Brackets are literal text | Matches one listed character |
| Letter case | ASCII letters are case-insensitive by default | Case-sensitive |
| Reverse the test | `NOT LIKE` | `NOT GLOB` |

The LIKE case rule above is for default SQLite ASCII matching; it is not a promise of case-insensitive matching for all Unicode letters or for every database. See the [SQLite LIKE and GLOB documentation](https://www.sqlite.org/lang_expr.html#the_like_glob_regexp_match_and_extract_operators). SQLite's [pattern-matching implementation notes](https://sqlite.org/src/doc/trunk/src/func.c) describe the GLOB wildcard and bracket rules.

**3. Percent and asterisk have corresponding roles in different operators**

In a LIKE pattern, `%` can cover any number of characters, including none. In a GLOB pattern, `*` has that role. They cannot be interchanged without changing the meaning.

```sql
SELECT
    'ABC' LIKE 'A%' AS like_many,
    'ABC' GLOB 'A*' AS glob_many,
    'A' LIKE 'A%' AS like_zero,
    'A' GLOB 'A*' AS glob_zero,
    'ABC' GLOB 'A%' AS percent_in_glob,
    'ABC' LIKE 'A*' AS star_in_like;
```

| like_many | glob_many | like_zero | glob_zero | percent_in_glob | star_in_like |
|---|---|---|---|---|---|
| 1 | 1 | 1 | 1 | 0 | 0 |

The two zero examples are true: the wildcard is allowed to consume nothing after A. The last two examples are false because GLOB treats `%` literally and LIKE treats `*` literally. Thus `GLOB 'A%'` can match the actual two-character value A%, while `LIKE 'A*'` can match the actual two-character value A*.

| Desired match | LIKE example | GLOB example |
|---|---|---|
| Starts with BOS | `CITY LIKE 'BOS%'` | `CITY GLOB 'BOS*'` |
| Ends with TON | `CITY LIKE '%TON'` | `CITY GLOB '*TON'` |
| Contains OST | `CITY LIKE '%OST%'` | `CITY GLOB '*OST*'` |

All six expressions above match BOSTON. Patterns without the leading wildcard constrain the start; without the trailing wildcard, they constrain the end.

These meanings apply inside the quoted pattern. In other SQL contexts, `SELECT *` selects columns, `COUNT(*)` counts rows, and `price * units` multiplies values; those asterisks are not GLOB wildcards.

**4. Exactly one character: underscore versus question mark**

```sql
SELECT
    'ABC' LIKE 'A_C' AS like_one,
    'ABC' GLOB 'A?C' AS glob_one,
    'AC' LIKE 'A_C' AS like_missing,
    'ABBC' GLOB 'A?C' AS glob_extra;
```

| like_one | glob_one | like_missing | glob_extra |
|---|---|---|---|
| 1 | 1 | 0 | 0 |

The first two tests have exactly one character between A and C. AC has none, and ABBC has two, so the other tests fail. Use `%` or `*` when that variable part may have any length.

**5. Bracket groups and case sensitivity**

```sql
SELECT
    'AUSTIN' LIKE '[AEIOU]%' AS like_brackets,
    'AUSTIN' GLOB '[AEIOU]*' AS glob_brackets,
    'austin' LIKE 'A%' AS like_case,
    'austin' GLOB 'A*' AS glob_case,
    'austin' GLOB '[AEIOUaeiou]*' AS glob_both_cases;
```

| like_brackets | glob_brackets | like_case | glob_case | glob_both_cases |
|---|---|---|---|---|
| 0 | 1 | 1 | 0 | 1 |

The first expression is false: SQLite LIKE expects the literal prefix [AEIOU], rather than one vowel. With GLOB, the bracket group consumes one character. The final `*` then accepts any remaining characters, not just more vowels. AUSTIN therefore matches even though USTIN contains consonants.

Lowercase a does not match uppercase A in GLOB. Listing both cases fixes the vowel test without changing the stored CITY value.

GLOB also supports ranges such as `[A-Z]` and negated sets such as `[^AEIOUaeiou]`. A negated set matches one character outside the list. It is not identical in every edge case to negating a whole pattern: the set still requires a character to exist.

**6. NOT GLOB and OR in the final solution**

`CITY NOT GLOB '[AEIOUaeiou]*'` asks whether the initial-vowel pattern fails. `CITY NOT GLOB '*[AEIOUaeiou]'` asks whether the final-vowel pattern fails.

| City | First condition | Second condition | OR result |
|---|---|---|---|
| AUSTIN | False | True | Keep |
| CHICAGO | True | False | Keep |
| BOSTON | True | True | Keep |
| OSLO | False | False | Exclude |

OR accepts either true condition, including when both are true. DISTINCT then keeps each selected city name once. Case handling, matching, and duplicate removal have separate roles.

**7. GLOB is not a regular expression**

In GLOB, `A*` means A followed by any text. It does not mean “repeat A.” A regex `A*` instead means zero or more repetitions of A. Regex anchors such as `^` and `$` are not needed to anchor a GLOB pattern; GLOB matches the whole string. The caret has a special role inside a GLOB negated set such as `[^A]`, not as a general start anchor.

**8. Matching a literal wildcard when needed**

```sql
SELECT
    '50%' LIKE '50!%' ESCAPE '!' AS literal_percent,
    'A*' GLOB 'A[*]' AS literal_star;
```

| literal_percent | literal_star |
|---|---|
| 1 | 1 |

LIKE supports an ESCAPE character to make `%` literal. In GLOB, a bracket group such as `[*]` matches an actual asterisk. Use the pattern rules for the selected operator; a backslash is not a universal escape in SQLite patterns.

**Revision reminder:** LIKE uses `%` and `_`; GLOB uses `*` and `?` and supports bracket groups. Use NOT to reverse the match, keep OR for this question, and use DISTINCT to remove duplicate city names.

## My solution — SQL Server

### Final solution

```sql
SELECT DISTINCT CITY
FROM STATION
WHERE CITY NOT LIKE '[AEIOUaeiou]%'
   OR CITY NOT LIKE '%[AEIOUaeiou]';
```

SQL Server LIKE supports bracket sets, so `[AEIOUaeiou]` matches one listed vowel and `%` matches zero or more characters. The OR condition and DISTINCT preserve the chosen approach. This version uses the CITY column's collation for comparisons and duplicate removal. See [SQL Server LIKE](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/like-transact-sql?view=sql-server-ver17).

The SQLite solution above uses `NOT GLOB` with `*`. SQLite LIKE does not interpret brackets as a character group, so this SQL Server LIKE version should be run in SQL Server.

### Explicit collation variant

```sql
SELECT DISTINCT CITY COLLATE Latin1_General_100_BIN2 AS CITY
FROM STATION
WHERE CITY COLLATE Latin1_General_100_BIN2 NOT LIKE N'[AEIOUaeiou]%'
   OR CITY COLLATE Latin1_General_100_BIN2 NOT LIKE N'%[AEIOUaeiou]';
```

`COLLATE Latin1_General_100_BIN2` makes the character comparisons explicit: case and accent variants are not automatically equated. Applying it to the selected value also keeps differently cased city names distinct, consistent with SQLite's default binary text collation for these examples. The output column remains CITY. SQL Server collation rules can otherwise change pattern matching and DISTINCT; see [Microsoft's collation explanation](https://learn.microsoft.com/en-us/sql/relational-databases/collations/collation-and-unicode-support?view=sql-server-ver17).

The N prefix makes the patterns Unicode, keeping trailing spaces significant when matching the final character.
