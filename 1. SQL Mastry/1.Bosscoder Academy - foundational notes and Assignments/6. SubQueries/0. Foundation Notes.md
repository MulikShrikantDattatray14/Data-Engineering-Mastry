# Subqueries - Quick Revision Notes

**A subquery is a query inside another SQL statement.** Use its result as a value, a set of values, a temporary row source, or an existence test. First decide what shape the inner result must have; then choose the operator around it.

Read in this order: **result shape -> one value -> lists and existence -> correlation -> grouped results -> NULL and empty cases**. Examples use SQLite first; SQL Server differences are labelled. Optional fixture setup is at the end.

## 1. Choose the result shape

| Inner result | Typical use | What to check |
|---|---|---|
| One column, at most one row | `salary > (SELECT AVG(...))` | A scalar value is expected |
| One column, possibly many rows | `department_id IN (SELECT ...)` | Membership, not one equality comparison |
| Several columns/rows | `FROM (SELECT ...) AS summary` | Treat the result as a table with named columns |
| Whether any rows exist | `EXISTS (SELECT 1 ...)` | Returned values are irrelevant; row presence matters |

“Correlated” describes a different property: the inner query refers to the current outer row. A scalar, membership or existence subquery can be correlated. A multirow result does not always require `IN`, `ANY` or `ALL`: it can also be used as a derived table or inside `EXISTS`.

Use these small teaching tables throughout:

| EmployeeID | Name | Salary | DepartmentID |
|---|---|---:|---:|
| 1 | Asha | 90000 | 10 |
| 2 | Ben | 60000 | 10 |
| 3 | Chen | 80000 | 20 |
| 4 | Diya | 40000 | 20 |
| 5 | Evan | 90000 | 30 |
| 6 | Farah | 50000 | 30 |

| DepartmentID | DepartmentName | Location |
|---|---|---|
| 10 | Engineering | New York |
| 20 | Sales | London |
| 30 | Finance | New York |
| 40 | HR | Paris |

One employee belongs to one department. The department table also contains HR, which has no employees in this fixture.

## 2. Scalar subqueries: one value

Task: employees above the overall average salary.

```sql
SELECT EmployeeID, Name, Salary
FROM Employees
WHERE Salary > (SELECT AVG(1.0 * Salary) FROM Employees)
ORDER BY EmployeeID;
```

The inner result is `410000 / 6 = 68333.333...`. The outer query compares each salary with that one benchmark.

| EmployeeID | Name | Salary |
|---|---|---:|
| 1 | Asha | 90000 |
| 3 | Chen | 80000 |
| 5 | Evan | 90000 |

`AVG(1.0 * Salary)` preserves decimals in both SQLite and SQL Server. Keep the benchmark unrounded for comparison. [SQL Server AVG return types](https://learn.microsoft.com/en-us/sql/t-sql/functions/avg-transact-sql)

Another scalar example preserves ties:

```sql
SELECT Name, Salary
FROM Employees
WHERE Salary = (SELECT MAX(Salary) FROM Employees)
ORDER BY EmployeeID;
```

| Name | Salary |
|---|---:|
| Asha | 90000 |
| Evan | 90000 |

The scalar maximum is one value, but several employees can equal it. `ORDER BY Salary DESC LIMIT 1` would return only one row unless ties were handled separately.

### Scalar edge cases

| Inner result | Consequence |
|---|---|
| One row, one column | Use that value |
| No rows | Scalar result is NULL |
| Multiple rows | SQL Server raises an error; SQLite takes the first row |
| Multiple columns | Cannot use it as a single scalar value |

Do not depend on SQLite quietly selecting a first row to repair ambiguous logic. Without deterministic ordering, that choice is not a reliable business rule. If the requirement truly selects one ranked value, order explicitly and use SQLite `LIMIT 1` or SQL Server `TOP (1)`. Otherwise use the correct membership or existence operator. [SQLite scalar subqueries](https://www.sqlite.org/lang_expr.html#subquery_expressions), [Microsoft subquery rules](https://learn.microsoft.com/en-us/sql/relational-databases/performance/subqueries)

An aggregate without `GROUP BY`, such as `SELECT MAX(Salary) FROM Employees`, returns one row even for empty input; the maximum in that row is NULL. Comparing a salary with NULL is unknown, so `WHERE` will not retain the row.

## 3. IN and NOT IN: membership

Task: employees in New York departments.

```sql
SELECT EmployeeID, Name
FROM Employees
WHERE DepartmentID IN (
    SELECT DepartmentID
    FROM Departments
    WHERE Location = 'New York'
)
ORDER BY EmployeeID;
```

Inner result: department IDs `10, 30`. Outer result:

| EmployeeID | Name |
|---|---|
| 1 | Asha |
| 2 | Ben |
| 5 | Evan |
| 6 | Farah |

`IN` asks whether the employee's department matches at least one returned ID. Duplicate inner IDs would not duplicate an employee; membership is still a true/false/unknown test. If the inner query returns just `10`, membership still works. If it returns no IDs, no employee matches.

`NOT IN` reverses membership, but NULL requires care. Use a tiny separate fixture, `ProbeValues(value) = 10, 20, NULL`:

```sql
SELECT
    10 IN (SELECT value FROM ProbeValues) AS match_in,
    30 IN (SELECT value FROM ProbeValues) AS missing_in,
    30 NOT IN (SELECT value FROM ProbeValues) AS missing_not_in;
```

| match_in | missing_in | missing_not_in |
|---:|---|---|
| 1 | NULL | NULL |

`10` has a definite match. For `30`, the NULL could represent an unknown value, so SQL cannot establish either membership or non-membership. **WHERE keeps only true; it drops false and unknown.**

| Candidate | IN `(10,20,NULL)` | NOT IN `(10,20,NULL)` |
|---|---|---|
| 10 | True | False |
| 30 | Unknown | Unknown |
| NULL | Unknown | Unknown |

If your rule excludes missing candidates and ignores missing lookup values, say both explicitly:

```sql
SELECT candidate
FROM ProbeInputs
WHERE candidate IS NOT NULL
  AND candidate NOT IN (
      SELECT value FROM ProbeValues WHERE value IS NOT NULL
  )
ORDER BY candidate;
```

For candidates `10,30,NULL`, the result is only `30`. Removing inner NULLs fixes their interference; the outer NULL rule is a separate decision.

**Empty result:** `x IN (empty subquery)` is false; `x NOT IN (empty subquery)` is true, including when `x` is NULL. This means an explicit outer `IS NOT NULL` can matter. SQLite accepts the literal empty list `IN ()`; SQL Server does not, so use an actual empty subquery when testing this behavior. [SQLite IN semantics](https://www.sqlite.org/lang_expr.html#the_in_and_not_in_operators), [SQL Server IN and NULL caution](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/in-transact-sql)

## 4. EXISTS and NOT EXISTS: matching rows

Task: departments containing at least one employee.

```sql
SELECT d.DepartmentID, d.DepartmentName
FROM Departments AS d
WHERE EXISTS (
    SELECT 1
    FROM Employees AS e
    WHERE e.DepartmentID = d.DepartmentID
)
ORDER BY d.DepartmentID;
```

| DepartmentID | DepartmentName |
|---|---|
| 10 | Engineering |
| 20 | Sales |
| 30 | Finance |

`EXISTS` needs at least one matching row. `SELECT 1` is a convention: it neither counts rows nor limits the inner query to one row. Even `EXISTS (SELECT NULL)` is true because that query returns a row. `NOT EXISTS` is true when the inner query returns no rows. [Microsoft EXISTS](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/exists-transact-sql)

Changing `EXISTS` to `NOT EXISTS` above returns only `40, HR`.

For the probe fixture:

```sql
SELECT p.candidate
FROM ProbeInputs AS p
WHERE NOT EXISTS (
    SELECT 1 FROM ProbeValues AS v
    WHERE v.value = p.candidate
)
ORDER BY p.candidate;
```

Result: `NULL`, then `30`. Inner NULLs do not poison unrelated matches. However, an outer NULL also has no equality match, so it is included. Add `p.candidate IS NOT NULL AND ...` if missing candidates should be excluded.

For students with missing departments, compare `d.id = s.department_id`, not `d.id = s.id`. The student ID identifies the student; the department ID identifies the relationship. If an unassigned department should not count as a departed department, require `s.department_id IS NOT NULL` too.

Two important traps:

- `EXISTS (SELECT COUNT(*) FROM ...)` is normally true even when there are zero matching rows: an ungrouped count returns one row containing zero.
- `EXISTS (SELECT CASE ... THEN 1 ELSE 0 END FROM ...)` tests whether rows exist, not whether the selected number is 1. Put a qualifying condition in `WHERE` when you want to test matching rows.

## 5. Correlated subqueries

A correlated subquery uses an outer alias. Task: compare employees with the average **of their own department**.

```sql
SELECT e.EmployeeID, e.Name, e.Salary
FROM Employees AS e
WHERE e.Salary > (
    SELECT AVG(1.0 * i.Salary)
    FROM Employees AS i
    WHERE i.DepartmentID = e.DepartmentID
)
ORDER BY e.EmployeeID;
```

| DepartmentID | Inner average | Employees above it |
|---|---:|---|
| 10 | 75000 | Asha |
| 20 | 60000 | Chen |
| 30 | 70000 | Evan |

The final employee rows happen to match the overall-average example, but the logic differs: Ben's benchmark is 75000, while Diya's is 60000. Different data can produce different answers.

`i` identifies rows examined inside; `e` identifies the current outer employee. Qualify shared column names so an accidental inner reference does not remove the correlation. Think “for this employee's department” to understand the result, without assuming the optimizer literally reruns the subquery once per employee or that correlation is always slower.

A scalar subquery can also appear in `SELECT`:

```sql
SELECT e.EmployeeID, e.Name,
       (SELECT AVG(1.0 * i.Salary)
        FROM Employees AS i
        WHERE i.DepartmentID = e.DepartmentID) AS department_average
FROM Employees AS e
ORDER BY e.EmployeeID;
```

| EmployeeID | Name | department_average |
|---|---|---:|
| 1 | Asha | 75000 |
| 2 | Ben | 75000 |
| 3 | Chen | 60000 |
| 4 | Diya | 60000 |
| 5 | Evan | 70000 |
| 6 | Farah | 70000 |

This adds a calculated value to each employee row. It does not collapse employees into department groups.

## 6. FROM and HAVING subqueries

A subquery in `FROM` is a **derived table**. Its output becomes the input of the outer query.

```sql
SELECT s.DepartmentID, s.average_salary
FROM (
    SELECT DepartmentID, AVG(1.0 * Salary) AS average_salary
    FROM Employees
    GROUP BY DepartmentID
) AS s
WHERE s.average_salary >= 70000
ORDER BY s.DepartmentID;
```

| DepartmentID | average_salary |
|---|---:|
| 10 | 75000 |
| 30 | 70000 |

The inner query produces three department rows; the outer filter retains two. Alias `s` names the derived table, and `average_salary` names a column it exposes. The outer query cannot select `s.Name`: that column was not returned. Always supply a derived-table alias for portable SQL; SQL Server requires it.

`HAVING` can compare a completed group with a scalar subquery:

```sql
SELECT DepartmentID, AVG(1.0 * Salary) AS average_salary
FROM Employees
GROUP BY DepartmentID
HAVING AVG(1.0 * Salary) > (SELECT AVG(1.0 * Salary) FROM Employees)
ORDER BY DepartmentID;
```

This also returns departments 10 and 30, because both group averages exceed the overall benchmark 68333.333.... Here the scalar average and grouped averages use different populations. `WHERE Salary > overall_average` would filter individual employees before forming groups, which answers a different question.

## 7. Pairs and ANY or ALL

### Match a pair together

For allowed coordinate pairs `(10,20)` and `(30,40)`, `(10,40)` is not allowed even though its latitude and longitude each appear somewhere.

```sql
-- SQLite: compare complete rows of values
SELECT lat, lon
FROM Locations
WHERE (lat, lon) IN (SELECT lat, lon FROM AllowedLocations)
ORDER BY lat, lon;
```

With candidate rows `(10,20), (10,40), (30,40)`, output is `(10,20), (30,40)`.

Portable SQLite/SQL Server form for non-NULL coordinates:

```sql
SELECT l.lat, l.lon
FROM Locations AS l
WHERE EXISTS (
    SELECT 1 FROM AllowedLocations AS a
    WHERE a.lat = l.lat AND a.lon = l.lon
)
ORDER BY l.lat, l.lon;
```

SQL Server does not support the SQLite tuple-`IN` syntax. If coordinates may be NULL, define whether two missing components should count as equal; ordinary `=` does not do that. Do not split the pair into separate `lat IN (...) AND lon IN (...)` tests. [SQLite row values](https://www.sqlite.org/rowvalue.html)

### ANY and ALL: SQL Server, not SQLite

With inner values `40,60,90`, `70 > ANY (...)` is true because at least one comparison succeeds; `70 > ALL (...)` is false because 70 is not greater than 90. `SOME` is a synonym for `ANY`.

```sqlserver
-- SQL Server; not SQLite syntax
SELECT
    CASE WHEN 70 > ANY (SELECT amount FROM PayValues) THEN 1 ELSE 0 END
        AS greater_than_any,
    CASE WHEN 70 > ALL (SELECT amount FROM PayValues) THEN 1 ELSE 0 END
        AS greater_than_all;
```

Expected output: `1, 0`. `CASE ... ELSE 0` combines false and unknown into 0, so this display alone cannot distinguish them.

| Inner values | `70 > ANY` | `70 > ALL` |
|---|---|---|
| 40, 60, 90 | True | False |
| 40, NULL | True | Unknown |
| 90, NULL | Unknown | False |
| No rows | False | True |

For a **nonempty, non-NULL** set, `x > ANY` is equivalent to `x > MIN`, and `x > ALL` to `x > MAX`. Do not generalize blindly: MIN/MAX ignore NULL and return NULL for empty input, so those rewrites can change behavior. [SQL Server ANY/SOME](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/some-any-transact-sql), [SQL Server ALL](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/all-transact-sql)

## 8. Filtering, joins and safe reuse

**Put a filter where its population belongs.** In “low-paid employees whose managers left,” the low-salary condition filters outer employees. The inner manager lookup must still contain **all current employees**; filtering it to low-paid employees would wrongly mark a high-paid manager as absent. A NULL manager means no assigned manager, not evidence of a departure.

In “shared investment value but unique city,” compute repeated values and unique coordinate pairs against the full Insurance table independently. Removing rows for one condition before checking the other can turn a genuinely shared city into an apparently unique city.

| Form | Good use | Important difference |
|---|---|---|
| IN / EXISTS | Keep rows with a qualifying relationship | Inner duplicates do not multiply outer rows |
| JOIN | Bring related columns into the result | Several matches can multiply outer rows |
| Scalar subquery | Attach or compare one value | Must satisfy scalar cardinality |
| Derived table | Use an intermediate row source once | Define its output columns clearly |
| CTE | Name multiple steps or reuse a result in one statement | Same logical problem; no automatic speed advantage |

A join to department averages can reproduce the correlated-average comparison. Select the form that explains the required result clearly, then use actual plans and data for performance decisions.

Subqueries also work in modification statements. In a scratch database, preview the target rows using the same predicate before an update or delete:

```sql
SELECT EmployeeID, Name
FROM Employees
WHERE DepartmentID IN (
    SELECT DepartmentID FROM Departments WHERE Location = 'London'
);
```

Preview result: Chen and Diya. A subsequent `UPDATE ... WHERE` or `DELETE ... WHERE` using this predicate targets those employees. Use a transaction or a resettable fixture while learning; the examples above are read-only and do not change stored data.

## 9. Revision sheet and practice map

| Question to ask | Decision it guides |
|---|---|
| One value, a list, a row source, or existence? | Scalar comparison, IN, FROM, or EXISTS |
| Does the inner logic need the current outer row? | Correlate with explicit aliases |
| What if the inner result is empty or multirow? | Check cardinality and the operator's rules |
| Can either compared value be NULL? | Test unknown results and the outer business rule |
| Do two attributes belong together? | Compare pairs, not independent lists |
| Does a condition apply to rows or groups? | WHERE versus HAVING |
| Could a join duplicate the outer entity? | Use membership/existence or aggregate first |

Run once in an empty practice database.

```sql
    EmployeeID INTEGER PRIMARY KEY, Name TEXT, Salary INTEGER, DepartmentID INTEGER

    (4,'Diya',40000,20),(5,'Evan',90000,30),(6,'Farah',50000,30);

    DepartmentID INTEGER PRIMARY KEY, DepartmentName TEXT, Location TEXT
);
INSERT INTO Departments VALUES
    (10,'Engineering','New York'),(20,'Sales','London'),
    (30,'Finance','New York'),(40,'HR','Paris');
CREATE TABLE ProbeValues (value INTEGER);
INSERT INTO ProbeValues VALUES (10),(20),(NULL);
CREATE TABLE ProbeInputs (candidate INTEGER);
INSERT INTO ProbeInputs VALUES (10),(30),(NULL);
CREATE TABLE Locations (lat INTEGER, lon INTEGER);
INSERT INTO Locations VALUES (10,20),(10,40),(30,40);
CREATE TABLE AllowedLocations (lat INTEGER, lon INTEGER);
INSERT INTO AllowedLocations VALUES (10,20),(30,40);
```
