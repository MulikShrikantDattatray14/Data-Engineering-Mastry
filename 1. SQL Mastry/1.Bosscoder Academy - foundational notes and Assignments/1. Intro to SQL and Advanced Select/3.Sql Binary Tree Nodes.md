# 3. SQL Binary Tree Nodes

![SOLVED](<../../_badges/solved.svg>) ![UNRATED](<../../_badges/unrated.svg>) · Solved (recorded): 2026-10-26

## Question and image

`BST` contains one row for each node of a binary tree. `N` is the node's value and `P` is the value of its parent. A missing `P` is `NULL`.

Report each node's type as `Root`, `Inner`, or `Leaf`, ordered by `N` ascending:

- **Root:** the node has no parent.
- **Inner:** the node is neither the root nor a leaf.
- **Leaf:** the node has no children.

**Example 1**

Input — `BST`:

| N | P |
|---:|---:|
| 1 | 2 |
| 3 | 2 |
| 6 | 8 |
| 9 | 8 |
| 2 | 5 |
| 8 | 5 |
| 5 | NULL |

The supplied diagram shows the same relationships:

![Example binary tree with node 5 at the root](assets/3-binary-tree-nodes.png)

Expected output:

| N | NodeType |
|---:|---|
| 1 | Leaf |
| 2 | Inner |
| 3 | Leaf |
| 5 | Root |
| 6 | Leaf |
| 8 | Inner |
| 9 | Leaf |

Node 5 has no parent, so it is the root. Nodes 2 and 8 have children and are inner nodes. Nodes 1, 3, 6, and 9 have no children, so they are leaves.

## Schema

`BST`:

| Column Name | Type |
|---|---|
| N | Integer |
| P | Integer |

`N` is the value of a node. `P` is the value of its parent, or `NULL` for the root.

## My solution — SQLite

### Solution 1 — Check the root, then inner nodes

```sql
SELECT N,
       CASE
           WHEN P IS NULL THEN 'Root'
           WHEN N IN (SELECT DISTINCT P FROM BST WHERE P IS NOT NULL) THEN 'Inner'
           ELSE 'Leaf'
       END AS NodeType
FROM BST
ORDER BY N;
```

This follows the classification directly: no parent means root; a node appearing in the parent column has at least one child; anything left is a leaf.

### Solution 2 — Check the root, then leaves

```sql
SELECT N,
       CASE
           WHEN P IS NULL THEN 'Root'
           WHEN N NOT IN (SELECT DISTINCT P FROM BST WHERE P IS NOT NULL) THEN 'Leaf'
           ELSE 'Inner'
       END AS NodeType
FROM BST
ORDER BY N;
```

Here, a node **absent** from the non-NULL parent list is a leaf. `WHERE P IS NOT NULL` matters for `NOT IN`: leaving `NULL` in that list could prevent nonmatching nodes from satisfying the leaf test.

### Solution 3 — IN with the NULL parent included

```sql
SELECT N,
       CASE
           WHEN P IS NULL THEN 'Root'
           WHEN N IN (SELECT DISTINCT P FROM BST) THEN 'Inner'
           ELSE 'Leaf'
       END AS NodeType
FROM BST
ORDER BY N;
```

This also works **inside this CASE**. The `IN` list includes `NULL`; an exact parent match is still true, and a nonmatch becomes unknown. `CASE WHEN` uses a branch only when its condition is true, so an unknown nonmatch reaches `ELSE 'Leaf'`. This reasoning does **not** make `NOT IN (SELECT P FROM BST)` safe when `P` contains `NULL`.

### Step-by-step explanation with one example

**Starting data.** Each `N` is a node; `P` points to its parent. The question's diagram shows 5 above 2 and 8, and 2 and 8 above the four leaves.

| N | P |
|---:|---:|
| 1 | 2 |
| 2 | 5 |
| 3 | 2 |
| 5 | NULL |
| 6 | 8 |
| 8 | 5 |
| 9 | 8 |

**1. Find the root.** A node with no parent has `P IS NULL`:

```sql
SELECT N, P
FROM BST
WHERE P IS NULL;
```

| N | P |
|---:|---:|
| 5 | NULL |

Node 5 is the root. It also has children, so the root check must come **before** the inner-node check in `CASE`.

**2. Find values used as parents.** A node has a child when its `N` appears as another row's `P`.

```sql
SELECT DISTINCT P
FROM BST
WHERE P IS NOT NULL
ORDER BY P;
```

| P |
|---:|
| 2 |
| 5 |
| 8 |

Node 2 is parent to 1 and 3; 8 is parent to 6 and 9; 5 is parent to 2 and 8. `DISTINCT` only shortens this displayed list. Membership with `IN` would give the same answer even if repeated parent values were kept.

**3. Compare each node with that list.** The middle column shows the `IN` condition in Solution 1.

```sql
SELECT N, P,
       N IN (SELECT DISTINCT P FROM BST WHERE P IS NOT NULL) AS has_child
FROM BST
ORDER BY N;
```

| N | P | has_child |
|---:|---:|---:|
| 1 | 2 | 0 |
| 2 | 5 | 1 |
| 3 | 2 | 0 |
| 5 | NULL | 1 |
| 6 | 8 | 0 |
| 8 | 5 | 1 |
| 9 | 8 | 0 |

SQLite displays true as `1` and false as `0`. Root 5 also has `has_child = 1`, which is why `WHEN P IS NULL` must be tested first. Nodes 2 and 8 become `Inner`; nodes 1, 3, 6, and 9 become `Leaf`.

**4. Classify in that order.** `CASE` stops at the first true branch for each row:

```sql
SELECT N,
       CASE
           WHEN P IS NULL THEN 'Root'
           WHEN N IN (SELECT DISTINCT P FROM BST WHERE P IS NOT NULL) THEN 'Inner'
           ELSE 'Leaf'
       END AS NodeType
FROM BST
ORDER BY N;
```

| N | NodeType |
|---:|---|
| 1 | Leaf |
| 2 | Inner |
| 3 | Leaf |
| 5 | Root |
| 6 | Leaf |
| 8 | Inner |
| 9 | Leaf |

**Why Solution 3 still works:** Without `WHERE P IS NOT NULL`, its distinct parent list is `2, 5, 8, NULL`. For `N = 2`, `IN` finds an exact match and is true. For `N = 1`, no value matches, but the `NULL` makes the result unknown; `CASE WHEN` skips that branch and chooses `ELSE 'Leaf'`. In contrast, Solution 2 must keep `WHERE P IS NOT NULL`: `1 NOT IN (2, 5, 8, NULL)` is unknown, so its leaf branch would be skipped.

## Official solution

The supplied handout's query uses the leaf-first check from Solution 2:

```sql
SELECT N,
       CASE
           WHEN P IS NULL THEN 'Root'
           WHEN N NOT IN (SELECT DISTINCT P FROM BST WHERE P IS NOT NULL) THEN 'Leaf'
           ELSE 'Inner'
       END AS NodeType
FROM BST
ORDER BY N;
```

**What this tests:** `CASE`, parent-child membership with a subquery, and `NULL` behavior.

**The approach:** Test the root first, test whether the node is absent from the non-NULL parent list, and label any remaining node as inner.

**Why this way:** Every node belongs to exactly one of the three categories. Removing `NULL` from the `NOT IN` subquery lets leaf nodes satisfy that test.

**Common mistakes:** Checking for inner nodes before the root, forgetting `P IS NOT NULL` in a `NOT IN` subquery, or assuming `DISTINCT` is necessary for `IN` membership.
