# Subqueries and Set Operations — Quick Revision Notes

**Main idea:** a subquery supplies a value, a list, or an existence answer to another query. Set operations stack or compare complete result sets. First decide which shape you need, then check duplicates and NULLs.

These invented teaching rows use employees and departments from the advanced deck's shared schema. They do not provide a solution to any practice prompt.

## 1. Read the example tables

| dept_id | dept_name | location |
|---:|---|---|
| 1 | Sales | Mumbai |
| 2 | Support | Delhi |
| 3 | Ops | Pune |

| emp_id | emp_name | dept_id | salary | city |
|---:|---|---:|---:|---|
| 11 | Dee | 1 | 100 | Mumbai |
| 12 | Eli | 1 | 90 | Delhi |
| 13 | Fox | 2 | 50 | Delhi |

Ops has no employee. Employee salaries are 100, 90, and 50.

## 2. A scalar subquery returns one value

The overall salary average is (100 + 90 + 50) / 3 = 80. A subquery can calculate that one value for a comparison:

    SELECT emp_name, salary
    FROM employees
    WHERE salary > (SELECT AVG(1.0 * salary) FROM employees)
    ORDER BY salary DESC;

| emp_name | salary |
|---|---:|
| Dee | 100 |
| Eli | 90 |

Fox's 50 is below 80. A **scalar** subquery must produce one column and at most one row. If it unexpectedly produces several rows, it cannot be used as a single comparison value.

## 3. A correlated subquery uses the current outer row

This query counts employees in each employee's department. The inner query refers to e.dept_id from the outer row:

    SELECT e.emp_name, e.dept_id,
           (SELECT COUNT(*)
            FROM employees AS colleague
            WHERE colleague.dept_id = e.dept_id) AS team_size
    FROM employees AS e
    ORDER BY e.emp_id;

| emp_name | dept_id | team_size |
|---|---:|---:|
| Dee | 1 | 2 |
| Eli | 1 | 2 |
| Fox | 2 | 1 |

For Dee, the inner filter uses department 1; for Fox, it uses department 2. This is the meaning of **correlated**. The database optimizer may transform the execution, so do not assume it literally scans the inner table once per outer row. A grouped join or a window can sometimes express the same calculation more clearly.

## 4. IN asks whether a value belongs to a returned list

    SELECT emp_name, dept_id
    FROM employees
    WHERE dept_id IN (
        SELECT dept_id
        FROM departments
        WHERE location = 'Delhi'
    );

The inner query returns department 2, so the result is Fox, department 2. Duplicates in the inner list do not create duplicate outer rows. IN compares membership; a JOIN combines matching rows and can multiply them.

## 5. EXISTS and NOT EXISTS ask whether a matching row is present

    SELECT d.dept_name
    FROM departments AS d
    WHERE EXISTS (
        SELECT 1
        FROM employees AS e
        WHERE e.dept_id = d.dept_id
          AND e.city = 'Delhi'
    )
    ORDER BY d.dept_id;

| dept_name |
|---|
| Sales |
| Support |

Sales qualifies through Eli, Support through Fox, and Ops has no matching employee. The inner SELECT 1 is conventional: EXISTS cares whether a row exists, not which value it selects. Replacing EXISTS with NOT EXISTS in this teaching example would keep Ops. No department is repeated because the outer table supplies one row per department.

### The NOT IN plus NULL trap

Consider the expression 5 NOT IN (1, NULL). SQL cannot determine whether 5 differs from the unknown value, so the result is **UNKNOWN**, not TRUE. A WHERE clause keeps only TRUE. If the inner list can contain NULL, filter it explicitly or use a correlated NOT EXISTS test. A positive IN list with a matching non-NULL value can still return TRUE.

## 6. Set operations compare result rows

Use two small teaching lists:

| PriorMembers.member_id | CurrentMembers.member_id |
|---:|---:|
| 1 | 2 |
| 2 | 3 |
| 3 | 4 |

| Operation | Result after sorting | Meaning |
|---|---|---|
| UNION ALL | 1, 2, 2, 3, 3, 4 | Stack every row, including repeats |
| UNION | 1, 2, 3, 4 | Stack and remove duplicate rows |
| INTERSECT | 2, 3 | Values present in both lists |
| EXCEPT | 1 | Values in the first list but not the second |

For example:

    SELECT member_id FROM PriorMembers
    INTERSECT
    SELECT member_id FROM CurrentMembers
    ORDER BY member_id;

The output is 2 and 3. Reverse the sides of EXCEPT and its result changes: CurrentMembers EXCEPT PriorMembers gives 4. UNION compares the full selected row, not just a convenient key; two rows with the same ID but different selected labels are different rows.

Every branch of a set operation must return the same number of columns in compatible positions. Put ORDER BY at the end for the combined result; table or branch order is not a guaranteed result order. UNION ALL avoids duplicate-removal work when duplicates are valid.

## 7. Pick the right shape

| Requirement | Often useful |
|---|---|
| Compare with one computed value | Scalar subquery |
| Compare with a value calculated for the current row | Correlated subquery |
| Keep rows whose key is in a set | IN |
| Keep rows when any related row exists | EXISTS |
| Keep rows with no related match | NOT EXISTS |
| Combine both result sets | UNION ALL or UNION |
| Keep the overlap | INTERSECT |
| Keep first-set rows absent from the second | EXCEPT |

A CTE can name an intermediate result when the logic becomes hard to read. A CTE is a readability tool first; it does not automatically mean that a database stores the intermediate rows. Keep the output grain and NULL behaviour clear whichever form you choose.

## Quick check

1. Does the inner query return one value, a list, or matching rows?
2. Which outer column makes the subquery correlated?
3. Can NULL enter a NOT IN list?
4. Could a JOIN duplicate rows where EXISTS would not?
5. For a set operation, are columns aligned and is duplicate removal intended?
