# Window Functions - Quick Revision Notes

**A window function calculates across related rows while keeping each original row visible.** Read `OVER (...)` in three parts: **partition → order → frame**.

## 1. Keep rows and partition

Use the same tiny `Events` table throughout. One row is one event.

| event_id | user_id | score |
|---:|---|---:|
| 1 | A | 50 |
| 2 | A | 50 |
| 3 | A | 30 |
| 4 | B | 40 |

`GROUP BY user_id` would reduce four rows to two. A window keeps four rows and writes each user's total beside each event:

```sql
SELECT event_id, user_id, score,
       SUM(score) OVER (PARTITION BY user_id) AS user_total
FROM Events
ORDER BY event_id;
```

| event_id | user_id | score | user_total |
|---:|---|---:|---:|
| 1 | A | 50 | 130 |
| 2 | A | 50 | 130 |
| 3 | A | 30 | 130 |
| 4 | B | 40 | 40 |

For A, `50 + 50 + 30 = 130`. `PARTITION BY` restarts the calculation at B. No `PARTITION BY` would use all four events.

## 2. Rank rows and handle ties

Here the order **inside** `OVER` determines rank; an outer `ORDER BY` only changes display order.

```sql
SELECT event_id, user_id, score,
       ROW_NUMBER() OVER (
           PARTITION BY user_id ORDER BY score DESC, event_id
       ) AS rn,
       RANK() OVER (
           PARTITION BY user_id ORDER BY score DESC
       ) AS rnk,
       DENSE_RANK() OVER (
           PARTITION BY user_id ORDER BY score DESC
       ) AS dense_rnk
FROM Events
ORDER BY user_id, score DESC, event_id;
```

| event_id | user_id | score | rn | rnk | dense_rnk |
|---:|---|---:|---:|---:|---:|
| 1 | A | 50 | 1 | 1 | 1 |
| 2 | A | 50 | 2 | 1 | 1 |
| 3 | A | 30 | 3 | 3 | 2 |
| 4 | B | 40 | 1 | 1 | 1 |

`ROW_NUMBER` always assigns different numbers. `RANK` gives equal scores the same rank and leaves a gap (1, 1, 3). `DENSE_RANK` gives equal scores the same rank without a gap (1, 1, 2). Add a tie-break to `ROW_NUMBER` when exactly one predictable row must be chosen. Do **not** add `event_id` to the `RANK` ordering if equal scores must remain tied.

`NTILE(2) OVER (ORDER BY score DESC, event_id)` splits sorted rows into two nearly equal buckets. A bucket can cut through equal values, so it is not a tie-preserving rank. `PERCENT_RANK` gives relative rank from 0 to 1; its formulas and percentile/median functions differ among SQL engines.

## 3. Compare neighbours

`LAG` reads the previous ordered row and `LEAD` reads the next one, inside each user's partition:

```sql
SELECT event_id, user_id, score,
       LAG(score) OVER (
           PARTITION BY user_id ORDER BY event_id
       ) AS previous_score,
       LEAD(score) OVER (
           PARTITION BY user_id ORDER BY event_id
       ) AS next_score
FROM Events
ORDER BY event_id;
```

| event_id | user_id | score | previous_score | next_score |
|---:|---|---:|---:|---:|
| 1 | A | 50 | NULL | 50 |
| 2 | A | 50 | 50 | 30 |
| 3 | A | 30 | 50 | NULL |
| 4 | B | 40 | NULL | NULL |

A's row 3 looks back to A's row 2; it does not look across the partition boundary to B. The first row has no previous row; the last has no next row.

## 4. Running and moving calculations

To follow event sequence, put `ORDER BY event_id` **inside** `OVER` and choose the frame explicitly:

```sql
SELECT event_id, user_id, score,
       SUM(score) OVER (
           PARTITION BY user_id
           ORDER BY event_id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_score,
       AVG(1.0 * score) OVER (
           PARTITION BY user_id
           ORDER BY event_id
           ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
       ) AS two_event_average
FROM Events
ORDER BY event_id;
```

| event_id | user_id | score | running_score | two_event_average |
|---:|---|---:|---:|---:|
| 1 | A | 50 | 50 | 50 |
| 2 | A | 50 | 100 | 50 |
| 3 | A | 30 | 130 | 40 |
| 4 | B | 40 | 40 | 40 |

For A's third row, running total is `50 + 50 + 30 = 130`. The two-row average is `(50 + 30) / 2 = 40`; the older first row is outside that frame. `ROWS` counts physical rows. If one row can contain an entire day's amount, aggregate to one row per day **before** applying a seven-day row window.

## 5. ROWS versus RANGE

Ties matter when the window orders by a value that repeats. For A, sorting by score gives **30, 50, 50**.

| score | `ROWS` running total | `RANGE` running total |
|---:|---:|---:|
| 30 | 30 | 30 |
| 50 (first row) | 80 | 130 |
| 50 (second row) | 130 | 130 |

With `ROWS`, the frame ends at the current **row**. With `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, both rows with score 50 are peers, so both see `30 + 50 + 50 = 130`. Many databases use a peer-aware `RANGE` default when `ORDER BY` is present; write `ROWS` explicitly for a row-by-row running total.

## 6. Filter after calculating and quick checks

A window result cannot be filtered in the same query's `WHERE`. Put it in a CTE, then filter:

```sql
WITH ranked AS (
    SELECT event_id, user_id, score,
           ROW_NUMBER() OVER (
               PARTITION BY user_id ORDER BY score DESC, event_id
           ) AS rn
    FROM Events
)
SELECT event_id, user_id, score
FROM ranked
WHERE rn = 1
ORDER BY user_id;
```

This keeps event 1 for A and event 4 for B. Before using any window, check: **what is one input row, which rows belong together, what order is meaningful, how should ties behave, and which frame is intended?**
