## 2. Know what one row represents

The PrepNPlaced commerce data has eight tables. The row counts below are the expected counts after loading the supplied CSVs.

| Table | One row represents | Key | Rows |
|---|---|---|---:|
| Suppliers | One supplier | SupplierID | 18 |
| Products | One catalogue product | ProductID | 22,088 |
| Category | One category | CategoryID | 12 |
| Shippers | One courier | ShipperID | 10 |
| Payments | One payment method | PaymentID | 10 |
| Customers | One customer account | CustomerID | 5,072 |
| Orders | One order header | OrderID | 46,438 |
| OrderDetails | One product line on an order | OrderDetailID | 168,567 |

**A row is not always a whole order.** An order can have several OrderDetails rows. State the intended result grain before writing SQL: one row per customer, order, order line, product, day, or another unit.

The advanced volume has its own tables: employees, departments, customers, orders, order_items, products, and payments. Its orders and order_items have the same header-and-line relationship in principle, but they are not the commerce CSV tables.

## 3. Follow keys before writing joins

Useful commerce relationships:

| Starting table | Matching table | Key comparison | Match pattern |
|---|---|---|---|
| Orders | Customers | Orders.CustomerID = Customers.CustomerID | Many orders may belong to one customer |
| Orders | Payments | Orders.PaymentID = Payments.PaymentID | Many orders may name one method |
| Orders | Shippers | Orders.ShipperID = Shippers.ShipperID | Many orders may name one courier |
| OrderDetails | Orders | OrderDetails.OrderID = Orders.OrderID | Many lines may belong to one order |
| OrderDetails | Products | OrderDetails.ProductID = Products.ProductID | Many lines may refer to one product |
| OrderDetails | Suppliers | OrderDetails.SupplierID = Suppliers.SupplierID | Many lines may refer to one supplier |
| Products | Category | Products.CategoryID = Category.CategoryID | Many products may share one category |

These are *logical* relationships; the load script does not enforce foreign keys. Some keys are missing or do not match. Choose INNER JOIN or LEFT JOIN based on which original rows the question asks you to keep.

## 4. Check row grain before calculating money

Use this small illustration. It is separate from the supplied dataset:

| OrderID | CustomerID | Total_Order_Amount |
|---:|---:|---:|
| 101 | 1 | 100 |
| 102 | 1 | 50 |

| OrderDetailID | OrderID | ProductID | Quantity |
|---:|---:|---:|---:|
| 1 | 101 | 10 | 2 |
| 2 | 101 | 11 | 1 |
| 3 | 102 | 10 | 1 |

After joining Orders to OrderDetails, Order 101 appears twice:

| OrderID | Total_Order_Amount | OrderDetailID |
|---:|---:|---:|
| 101 | 100 | 1 |
| 101 | 100 | 2 |
| 102 | 50 | 3 |

Adding the header amount **after** that join gives 100 + 100 + 50 = 250. The actual total of the two order headers is 100 + 50 = 150. If the question asks for header revenue, work at one row per order before summing. If it asks for line-level units or product-level quantities, use OrderDetails.

The source distinguishes **net order value** (Orders.Total_Order_Amount) from **list-price value** (Quantity multiplied by the current Products.Sale_Price). They answer different questions and need not match.

## 5. Read the commerce dataset correctly

- Orders run from 2023 to 28 December 2025. December 2025 is incomplete. For a repeatable “latest” period, anchor to the dataset's maximum OrderDate rather than today's date.
- Orders has no status column. The interview book treats each Orders row as a placed order; an unshipped order still exists.
- When a problem uses “late delivery,” the book defines it as more than seven days from order to delivery. Check each question's wording.
- Product catalogue names and prices are sourced from a real store. Customers, orders, suppliers, couriers, transactions, and ratings are generated for practice. Ratings do not describe real brands.
- The dataset deliberately retains NULLs, orphan keys, duplicate accounts/lines, mixed spellings, inconsistent flags, and invalid dates. Do not clean them away while loading or assume every relationship matches.
- Products.Rating is NULL for unrated products. A missing value is not automatically zero.
- Dates in Orders.csv are DD-MM-YYYY text. Customers.DateEntered can be YYYY/MM/DD, DD-MM-YYYY, YYYY-MM-DD, or blank. The provided PostgreSQL loader parses these before making DATE columns.

## 6. Load and inspect the source data

The original loader is [data/load_dataset_v2.sql](<../Source Materials/PrepNPlaced_SQL_100_v2/data/load_dataset_v2.sql>). It uses PostgreSQL commands, including \copy. Run it from the folder containing the eight CSVs, as explained in the [bundle README](<../Source Materials/PrepNPlaced_SQL_100_v2/README.md>). Its final row-count query should match the table above.

It is **not** a SQLite loader. When practicing in SQLite, dates, casts, \copy, FILTER, DATE_TRUNC, and other PostgreSQL syntax may need an equivalent. Keep the original source unchanged. The advanced PDF's MySQL queries also need dialect translation when you test them in SQLite.

A quick post-load check:

~~~sql
SELECT COUNT(*) AS order_rows
FROM Orders;
~~~

Expected count on the supplied commerce CSVs: 46,438. A count alone does not prove that date parsing or joins are correct; also inspect a few dates and keys.

## 7. A small SQL workflow

1. Say what one output row represents.
2. Name the required tables and their keys.
3. Identify rows that must survive even when a match is absent.
4. Filter or aggregate at the correct grain.
5. Inspect intermediate rows, especially after a one-to-many join.
6. Check NULLs, ties, date boundaries, sorting, and the source dialect.

For practice, open a question from the topic index, attempt it before opening the source book's answer, and then compare the result with the book where sample data is available.
