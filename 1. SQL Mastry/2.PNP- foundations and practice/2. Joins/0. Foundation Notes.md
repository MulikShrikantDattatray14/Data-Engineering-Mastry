# Joins — Quick Revision Notes

**Main idea:** decide which rows must survive and what one result row represents before writing a join. The same key can match several rows, so a join can multiply rows.

These small teaching examples use the seven-table schema introduced in the advanced SQL deck: customers, orders, order_items, products, payments, employees, and departments. The sample rows below are invented for revision; they are not the answers or input data for a practice question.

## 1. Start with the row grain

| customers.cust_id | cust_name |
|---:|---|
| 1 | Ada |
| 2 | Ben |
| 3 | Cara |

| orders.order_id | cust_id | status | amount |
|---:|---:|---|---:|
| 101 | 1 | DELIVERED | 60 |
| 102 | 1 | CANCELLED | 20 |
| 103 | 2 | DELIVERED | 30 |

A customer can have many orders. Joining these tables produces **one row per matching order**, not one row per customer. Ada therefore appears twice.

## 2. INNER JOIN keeps matching pairs

    SELECT c.cust_name, o.order_id, o.status
    FROM customers AS c
    JOIN orders AS o ON o.cust_id = c.cust_id
    ORDER BY o.order_id;

| cust_name | order_id | status |
|---|---:|---|
| Ada | 101 | DELIVERED |
| Ada | 102 | CANCELLED |
| Ben | 103 | DELIVERED |

Cara has no order, so there is no matching pair to return. The key compares values, not the row positions of two tables.

## 3. LEFT JOIN keeps every left row

    SELECT c.cust_name, o.order_id
    FROM customers AS c
    LEFT JOIN orders AS o ON o.cust_id = c.cust_id
    ORDER BY c.cust_id, o.order_id;

| cust_name | order_id |
|---|---:|
| Ada | 101 |
| Ada | 102 |
| Ben | 103 |
| Cara | NULL |

Cara survives because customers is on the left. The right columns are NULL where no order matched. A LEFT JOIN does **not** guarantee one output row per customer: Ada still has two matches.

| Need | Starting point |
|---|---|
| Only matched pairs | INNER JOIN |
| Every row from the first table | LEFT JOIN |
| Every row from the second table | RIGHT JOIN, or swap the tables and use LEFT JOIN |
| Every row from both sides | FULL OUTER JOIN, where supported |
| Every possible pair | CROSS JOIN |

A FULL JOIN may require a dialect-specific workaround. Learn what rows it must keep before choosing syntax.

## 4. ON versus WHERE changes a LEFT JOIN

Suppose we want every customer beside any delivered order. Put the delivered condition in ON:

    SELECT c.cust_name, o.order_id
    FROM customers AS c
    LEFT JOIN orders AS o
      ON o.cust_id = c.cust_id
     AND o.status = 'DELIVERED'
    ORDER BY c.cust_id;

| cust_name | order_id |
|---|---:|
| Ada | 101 |
| Ben | 103 |
| Cara | NULL |

The join tries to match delivered orders, then supplies NULL when none exists. If the status condition moves to WHERE, Cara's NULL row fails the filter and disappears. Ask: **am I filtering matches, or filtering the finished result?**

## 5. Existence and absence

Use EXISTS when the question asks whether a related row exists, rather than asking to display every matching pair. For example, this teaching query lists departments with an employee in Delhi:

    SELECT d.dept_name
    FROM departments AS d
    WHERE EXISTS (
        SELECT 1
        FROM employees AS e
        WHERE e.dept_id = d.dept_id
          AND e.city = 'Delhi'
    );

The inner query refers to the current department through d.dept_id. A department appears once even if several employees qualify. NOT EXISTS reverses the test. A LEFT JOIN followed by a check that a non-null right-side key IS NULL can also find missing matches; choose a key that cannot be NULL on a real match.

## 6. Self, cross, and range joins

A self join assigns different roles to two copies of one table. Here e means employee and m means manager:

    SELECT e.emp_name, m.emp_name AS manager_name
    FROM employees AS e
    LEFT JOIN employees AS m ON e.manager_id = m.emp_id;

| e.emp_name | e.manager_id | manager_name |
|---|---:|---|
| Dee | NULL | NULL |
| Eli | 1 | Dee |
| Fox | 1 | Dee |

A CROSS JOIN makes every combination. Two shirt sizes crossed with three colours make 2 × 3 = 6 pairs. Use it when you intentionally need a complete grid, then attach any matching facts.

A non-equi join uses a condition such as a price range instead of equality. Prefer non-overlapping bounds: [0, 50) and [50, 100) put price 50 in exactly one band. The join condition is price >= lower_bound AND price < upper_bound.

## 7. Check multiplication before adding totals

For order 101, imagine two order_items and two payment rows. Joining orders to both child tables creates 2 × 2 = 4 rows for that one order. Summing its order amount after that join would count the same 60 four times.

| stage | rows for order 101 |
|---|---:|
| orders alone | 1 |
| orders joined to two items | 2 |
| items also joined to two payments | 4 |

If you need one output row per order, aggregate items and payments separately **to order_id first**, then join those one-row-per-order summaries. Before summing, say what one input row contributes and count rows after each join.

## Quick check

1. Which table must keep unmatched rows?
2. What does one output row mean after the join?
3. Is the key unique on either side? Can NULLs occur?
4. Could multiple child tables multiply amounts or counts?
5. Does a condition belong in ON to restrict matches, or in WHERE to remove finished rows?
