# PNP Q008. Price band labels

![SOLVED](<../../_badges/solved.svg>) · Solved (recorded): 2026-10-27 ![EASY](<../../_badges/easy.svg>)

## Question and image

**Source:** [100 SQL Interview Questions](<../Source Materials/Updated_100_SQL_Interview_Questions.pdf>), question 8, pp. 20–21. **Difficulty:** Easy.

**Primary topic:** CASE WHEN. **Also covers:** Condition order, NULL branch.

**Business scenario.** Merchandising is adding a "Shop by budget" filter to the app. Each product must carry exactly one band based on its current Sale_Price : Budget below 200, Mid from 200 up to 699, Premium from 700. A product with no price should show Unknown so it can be fixed, not disappear from the filter.

**Task.** Label every product with a price band. Mid means 200 or more and less than 700, so a price of 699.50 is Mid. Sort by ProductID .

**Expected output (as supplied):**

```text
ProductID
Product
Sale_Price
price_band : Budget , Mid , Premium or Unknown
```

**Tables required:** Products.

**SQL concepts named in the source:** CASE WHEN, order of conditions, NULL handling, boundaries on decimal values.

The source is a text-based PDF; no separate question image was supplied.

## My solution — SQLite

```sql
SELECT
    ProductID,
    Product,
    Sale_Price,
    CASE
        WHEN Sale_Price < 200 THEN 'Budget'
        WHEN Sale_Price >= 200 AND Sale_Price < 700 THEN 'Mid'
        WHEN Sale_Price >= 700 THEN 'Premium'
        ELSE 'Unknown'
    END AS price_band
FROM Products
ORDER BY ProductID;
```

### Step-by-step explanation with one example

**Starting data.** Use the five illustrative `Products` rows from the question. Each product needs one output row and one price label.

| ProductID | Product | Sale_Price |
|---:|---|---:|
| 1 | Pen | 199 |
| 2 | Book | 200 |
| 3 | Bag | 699.50 |
| 4 | Watch | 700 |
| 5 | Mystery | NULL |

**1. Check the boundaries in order.** `CASE` tries its `WHEN` conditions from top to bottom and returns the label for the first true condition. `Sale_Price < 200` includes 199. The next condition starts at 200 and uses `< 700`, so it includes 699.50 but excludes 700. The third condition includes 700 and every higher price.

```sql
SELECT
    ProductID,
    Sale_Price,
    CASE
        WHEN Sale_Price < 200 THEN 'Budget'
        WHEN Sale_Price >= 200 AND Sale_Price < 700 THEN 'Mid'
        WHEN Sale_Price >= 700 THEN 'Premium'
        ELSE 'Unknown'
    END AS price_band
FROM Products
ORDER BY ProductID;
```

| ProductID | Sale_Price | First matching branch | price_band |
|---:|---:|---|---|
| 1 | 199 | `< 200` | Budget |
| 2 | 200 | `>= 200 AND < 700` | Mid |
| 3 | 699.50 | `>= 200 AND < 700` | Mid |
| 4 | 700 | `>= 700` | Premium |
| 5 | NULL | No `WHEN` is true | Unknown |

For product 5, each comparison with `NULL` is unknown rather than true. The `ELSE` supplies `Unknown`, keeping the product in the result.

**2. Return the requested columns in ID order.** The full query adds `Product` to the calculated result. `ORDER BY ProductID` arranges the final rows by product ID.

```sql

    ProductID,
    Product,
    Sale_Price,
    CASE
        WHEN Sale_Price < 200 THEN 'Budget'
        WHEN Sale_Price >= 200 AND Sale_Price < 700 THEN 'Mid'
        WHEN Sale_Price >= 700 THEN 'Premium'
        ELSE 'Unknown'
    END AS price_band
FROM Products
ORDER BY ProductID;
```

| ProductID | Product | Sale_Price | price_band |
|---:|---|---:|---|
| 1 | Pen | 199 | Budget |
| 2 | Book | 200 | Mid |
| 3 | Bag | 699.50 | Mid |
| 4 | Watch | 700 | Premium |
| 5 | Mystery | NULL | Unknown |

## Official solution

**Source:** [provided SQL answer key](<../Source Materials/PrepNPlaced_SQL_100_v2/sql/all_100_solutions.sql>), question 8.

```sql
SELECT p.ProductID,
       p.Product,
       p.Sale_Price,
       CASE
           WHEN p.Sale_Price IS NULL THEN 'Unknown'
           WHEN p.Sale_Price < 200   THEN 'Budget'
           WHEN p.Sale_Price < 700   THEN 'Mid'
           ELSE 'Premium'
       END AS price_band
FROM Products AS p
ORDER BY p.ProductID;
```

**What this tests.** Ordered `CASE` conditions, decimal price boundaries, and handling a missing price.

**The approach.** The source tests `NULL` explicitly first, then checks ascending price thresholds. After prices below 200 and below 700 are handled, every remaining non-null price is Premium.

**Why this way.** Each `WHEN` is evaluated in order, so later branches can use simpler threshold checks. Your explicit ranges and `ELSE 'Unknown'` produce the same labels for the given numeric price column.

**Common mistakes.** `<= 699` misses values such as 699.50, `<= 700` wrongly puts 700 in Mid, and omitting the missing-price branch leaves a `NULL` label.
